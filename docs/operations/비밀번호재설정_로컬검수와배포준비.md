# 비밀번호 재설정 로컬 검수와 배포 준비

새 격리 Compose가 필요하면 [공통 시험 서버 기동](2026-11-17_실연동검수계획.md#0-powershell에서-시험-서버-준비)부터 한다. 아래 명령은 이미 기동한 팀 제한 HTTPS 시험 배포에서 실행한다.

## 관람자 흐름

- **로그인 도움 → 비밀번호 재설정 → 이메일 입력 → 편지함의 링크 → 새 비밀번호 → 다시 로그인** 순서다. 재설정 설정이 비어 있으면 로그인 도움에 준비 상태가 표시된다.
- 등록 주소와 미등록 주소의 유효한 요청은 동일한 빈 `204`와 같은 화면 안내를 받는다. 이메일 발송은 별도 명령에서 진행한다. 요청 빈도는 IP와 정규화한 이메일 기준으로 제한한다.
- 링크 만료는 요청 시각부터 30분이다. 성공하면 같은 계정의 모든 재설정 링크와 로그인 세션을 폐기한다. 기존 취향·영수증·카카오 연결은 같은 계정에서 계속 이용할 수 있다. 관리자는 회원용 이메일 복구 대상에서 제외한다.
- 링크는 `/password/reset#token=…`을 사용한다. 브라우저에서 링크 값을 읽은 뒤 주소에서 제거한다. DB에는 공개 링크 전체나 메일 원문을 저장하지 않는다. 준비 항목은 Django 메일과 OWASP 기준을 따른다. [Django 메일](https://docs.djangoproject.com/en/5.2/topics/email/) · [OWASP 비밀번호 재설정](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

## 로컬 검수

1. `ARTI_ENV=test`와 `ALLOW_TEST_FIXTURES=true`를 설정하고, `arti_visit_boundaries_*` 합성 PostgreSQL에 `migrate`와 `load_test_fixture`를 적용한다. 준비한 빌드 경로는 `ARTI_BROWSER_DIST`로 지정한다. 실행기가 루프백 메모리 메일함을 켠다. [시험 환경 기본 절차](2026-11-11_main_시연복구체크리스트.md#모의-도슨트-성공과-실패-복구)
2. 저장소 루트에서 `python backend-django/manage.py test arti.tests.test_password_reset --noinput`과 `node frontend/tests/runVisitBoundaries.browser.mjs password-reset`을 실행한다. Chrome 실행기는 `ARTI_BOOTSTRAP_PASSWORD`에 합성 값이 필요하다.
3. Django는 만료·변조·재사용·동시 제출, 이전 계정 세션 무효화와 다른 계정 유지, 기존 영수증·카카오 연결 보존을 확인한다. Chrome은 요청부터 모의 편지함, 새 비밀번호 입력, 재로그인까지 따라간다.
4. PR의 **Account Chrome (password reset)**은 전용 합성 PostgreSQL `arti_visit_boundaries_password_ci`와 메모리 편지함을 쓴다. 실제 발신 주소를 넣을 환경은 이 CI와 분리한다.
5. Django 시험에서 발송 작업 두 개를 동시에 시작해 같은 대기 건 하나를 두고 경합시킨다. 첫 작업이 잡은 건을 두 번째 작업이 건너뛰고 메일이 한 통만 도착해야 한다. 배포 시에도 재시도·중복과 메일 제공자의 발송 확인을 함께 본다.

## 1. SMTP 제공자와 시험 계정 준비

1. 준억님이나 팀 운영 담당자가 SMTP 제공자 콘솔에서 **발신 주소 또는 도메인 검증**을 완료한다. 자체 도메인을 사용하면 제공자가 안내한 DNS 레코드를 반영하고 SPF·DKIM 상태와 DMARC 정책을 확인한다. 샌드박스 계정에 수신 제한이 있으면 팀 시험 수신함을 허용 목록에 추가한다. [Google 발신자 가이드](https://support.google.com/a/answer/81126) · [Django SMTP 설정](https://docs.djangoproject.com/en/5.2/topics/email/)
2. 제공자에서 SMTP 호스트·포트·TLS 방식과 SMTP 전용 인증값을 확인한다. 서버가 SMTP 포트로 나갈 수 있어야 한다. 시험 HTTPS 주소에서 계정 A를 만든 뒤 A의 이메일을 팀 시험 수신함으로 설정하고 영수증 한 건을 저장한다.
3. 배포 중인 Git 제외 환경 파일에 아래 값을 넣는다. 시험 주소에 경로와 끝 `/`를 붙이지 않는다. `DJANGO_ALLOWED_HOSTS`에는 기존 값과 시험 호스트명을 넣는다. 값이 있는 환경 파일이나 전체 Compose 설정을 채팅에 붙이지 않는다.

```dotenv
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,api,staging.arti.example
ARTI_PASSWORD_RESET_ORIGIN=https://staging.arti.example
ARTI_PASSWORD_RESET_FROM=reset@your-verified-domain.example
EMAIL_HOST=smtp.your-provider.example
EMAIL_PORT=587
EMAIL_HOST_USER=SMTP_사용자명
EMAIL_HOST_PASSWORD=SMTP_전용_비밀번호
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
```

암시적 TLS를 요구하는 제공자는 `EMAIL_PORT=465`, `EMAIL_USE_TLS=false`, `EMAIL_USE_SSL=true`로 바꾼다. TLS와 SSL을 동시에 켜면 설정 검사에서 실패한다. [Django TLS/SSL 설정](https://docs.djangoproject.com/en/5.2/ref/settings/#email-use-tls)

### Gmail로 시작하는 경우

1. 발송을 맡을 Google 계정에서 2단계 인증을 켜고 [앱 비밀번호 관리](https://myaccount.google.com/apppasswords)에서 시험용 앱 비밀번호를 발급한다. 보안 키만 사용하도록 설정한 계정, 고급 보호 계정, 조직 정책이 제한한 회사·학교 계정에서는 발급 메뉴가 보이지 않을 수 있다. Google 계정 비밀번호를 변경하면 발급한 앱 비밀번호가 폐기되므로 새 앱 비밀번호를 서버에 적용한다. [Google 앱 비밀번호 도움말](https://support.google.com/accounts/answer/185833?hl=ko)
2. Git에서 제외된 배포 환경 파일의 SMTP 항목을 아래처럼 설정한다. 전체 Gmail 주소와 16자리 앱 비밀번호는 발송 서버의 비공개 설정에 넣는다. `ARTI_PASSWORD_RESET_ORIGIN`과 `DJANGO_ALLOWED_HOSTS`는 앞의 HTTPS 시험 환경 설정을 따른다. [Google SMTP 서버 설정](https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app)

```dotenv
ARTI_PASSWORD_RESET_FROM=발송에_사용하는_Gmail_전체_주소
EMAIL_HOST=smtp.gmail.com
EMAIL_PORT=587
EMAIL_HOST_USER=발송에_사용하는_Gmail_전체_주소
EMAIL_HOST_PASSWORD=발급받은_앱_비밀번호
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
```

3. 아래 2절에서 팀 시험 수신함으로 한 통을 확인한 뒤 3절의 `reset-mail` 프로필을 켠다. 재설정 요청은 기존 DB 큐에 들어가고 워커가 Gmail SMTP에 인증해 주기적으로 발송한다. 여러 번 배포할 때도 같은 API·워커 환경에 최신 값을 적용한다.

## 2. API 적용과 첫 메일 한 통

배포에 쓰는 PowerShell 7에서 아래 세 예시 값을 팀 배포 값으로 바꾼다. Nginx 오버레이나 추가 Compose 파일을 사용하는 배포라면 `$artiCompose`에 기존 `-f` 인자를 순서대로 포함한다. 기존 프로젝트를 확인해 같은 DB·미디어를 사용한다.

```powershell
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $true
$artiOrigin = 'https://staging.arti.example'
$artiEnv = '.env.compose.staging'
$artiCompose = @('--env-file', $artiEnv, '-f', 'compose.yaml', '-p', 'arti-staging')
docker compose @artiCompose config --quiet
docker compose @artiCompose build api migrate
docker compose @artiCompose run --rm --no-deps -T api python manage.py check_live_config mail --origin $artiOrigin
docker compose @artiCompose run --rm migrate
docker compose @artiCompose up -d --no-deps --force-recreate --wait api
python scripts/probe_account_https.py $artiOrigin mail
```

설정 검사는 시크릿 출력·외부 요청 없이 값을 점검한다. HTTPS 검사는 `/api/ready`, 비밀번호 재설정 상태와 `/password/reset`의 보호 헤더 및 HTML까지 확인한다. 이 검사는 SMTP 발송에 성공했다는 뜻은 아니다.

1. 예약 워커를 켜기 전에 A의 이메일로 **로그인 → 로그인 도움 → 비밀번호 재설정**에서 한 번 요청한다. 미등록 주소 비교가 필요하면 팀 시험용으로 통제하는 다른 주소 한 개로 요청한다. 두 응답 모두 `204`다.
2. 같은 PowerShell에서 아래 세 줄을 한 번 실행한다. `ready`에는 가입 여부를 숨기기 위해 큐에 넣은 미등록 주소 요청도 포함될 수 있다. 발송 결과는 승인된 수신함 A와 제공자 기록으로 확인한다.

```powershell
docker compose @artiCompose exec -T api python manage.py send_password_reset_mail --status
docker compose @artiCompose exec -T api python manage.py send_password_reset_mail
docker compose @artiCompose exec -T api python manage.py send_password_reset_mail --status
```

3. A의 편지함에서 발신 주소와 도착 시각, 링크의 HTTPS 호스트를 확인한다. 새 비밀번호를 설정해 이전 세션 `401`, 링크 재사용 실패, 새 비밀번호로 같은 영수증 접근을 확인한다. 제공자의 승인·반송 확인 방법이 있으면 함께 기록한다.

## 3. 주기 발송과 복귀

수동 발송과 계정 검수가 통과한 다음 `reset-mail` 프로필을 켠다. 워커는 같은 DB를 사용해 한 번에 최대 20건을 처리하고 60초 뒤 다시 확인한다. SMTP가 실패하면 해당 건을 2분 뒤 재시도 대기 상태로 옮긴다. 링크 유효 시간 30분이 지나면 대기열에서 제거한다. 외부 스케줄러가 같은 작업을 이미 실행하면 운영자는 어느 쪽을 사용할지 정한다.

```powershell
docker compose @artiCompose --profile reset-mail up -d --build --no-deps reset-mail
docker compose @artiCompose --profile reset-mail ps reset-mail
docker compose @artiCompose --profile reset-mail logs --since 10m reset-mail
docker compose @artiCompose exec -T api python manage.py send_password_reset_mail --status
```

| 확인 결과 | 처리 |
| --- | --- |
| `ready`가 계속 쌓임 | 워커 실행·DB 공유와 마지막 로그를 확인한다. `--status`는 메일을 발송하거나 큐를 수정하지 않는다. |
| `deferred`와 발송 실패 로그가 증가 | 제공자 대시보드에서 호스트·포트, SMTP 인증, TLS 모드, 발신 주소 검증, 수신 제한, 할당량을 확인한다. 서버 로그에는 일반적인 실패 메시지만 남긴다. |
| 발송 성공인데 도착하지 않음 | 제공자에서 수락·반송을 구분하고 시험 계정의 편지함과 스팸함을 본다. 수락 직후 응답을 잃으면 동일 링크가 재발송될 수 있다. 두 사본으로 비밀번호 변경은 한 번만 가능해야 한다. |
| 기능을 내려야 함 | `docker compose @artiCompose --profile reset-mail stop reset-mail` 뒤 환경 파일의 `ARTI_PASSWORD_RESET_ORIGIN`·`ARTI_PASSWORD_RESET_FROM`을 비우고 `docker compose @artiCompose up -d --no-deps --force-recreate --wait api`를 실행한다. `python scripts/probe_account_https.py $artiOrigin mail --expect-disabled`와 기존 이메일 로그인·영수증으로 복귀를 확인한다. |

재설정 링크·메일 주소·인증값은 회신과 프록시·앱 로그에서 제외한다. 공개 전 팀 운영 담당이 기존 가입 주소의 소유를 어떻게 확인할지, 발송·반송 문의와 보유·파기를 누가 맡을지 정한다.

| 시험 순서 | 담당 및 통과 기준 |
| --- | --- |
| 발송 전 | 운영 담당이 발신 주소와 SMTP, 비밀번호 재설정 링크가 열릴 HTTPS 주소를 정한다. 팀이 등록 주소의 소유 확인 기준을 정한다. |
| 대기열·편지함 | 설정 후 발송 작업을 기동한다. 등록 주소와 미등록 주소 요청은 둘 다 `204`이고, 테스트 편지함에는 등록 주소의 메일 한 건만 도착한다. |
| 만료와 복구 | 임시 SMTP 오류 후 발송 작업이 다시 처리한다. 메일을 수락한 뒤 발송 응답이 끊기면 같은 링크가 두 통 도착할 수 있다. 두 사본 중 처음 한 번만 비밀번호를 바꿀 수 있어야 한다. 만료 링크 안내와 변경 뒤 이전 세션 `401`도 확인한다. |
| 제품 데이터 | 새 비밀번호로 같은 회원과 영수증을 열어 확인한다. 카카오 시험 앱을 연결한 이후에는 같은 계정의 카카오 재로그인까지 검수한다. |
