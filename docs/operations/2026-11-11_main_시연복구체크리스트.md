## DB·미디어 복원과 전환

1. 원본 API 쓰기를 멈춘 뒤 PostgreSQL custom dump(`pg_dump -Fc`), 미디어 tar, 파일별 SHA-256, 커밋을 한 세트로 보관한다. 실제 자료를 인수하는 날에는 공개 범위와 백업 접근 권한을 먼저 확인한다.
2. 새 프로젝트에 **테이블이 없는 DB와 빈 미디어 볼륨**을 준비한다. 같은 PostgreSQL 메이저 버전에서 `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`로 복원한다. 미디어는 manifest에 있는 일반 파일만 풀고 파일 해시와 앱 UID 10001 소유권을 확인한다. [Compose 명령 예시](../execution-plan/2026-11-07/records/backup-restore/2026-11-09/commands.md)
3. 복원한 API를 기동하고 200 준비 응답, 작품·도면 접근, 미검수 작품·보호 이미지 비노출을 확인한다. 같은 회원으로 **새 브라우저 세션**에서 로그인하고 마이페이지에서 과거 영수증을 연다.
4. 기존 관람과 같은 요청은 200과 같은 영수증을 돌려주는지, 같은 관람 ID에 다른 내용은 409인지 확인한다. 다른 회원과 비로그인 사용자의 조회가 각각 403과 401인지 확인한다. 시험 원본과 복원본의 관람·반응 행 수와 내용 해시를 대조한다.
5. 복원본 API와 DB를 재시작하고 준비 응답·행·파일을 다시 확인한다. 원본 전환이 필요할 때만 새 주소를 사용한다. 실패하면 기존 백업과 원본을 보존하고 복원 대상에서 원인을 확인한다. 리허설이 끝나면 시험 프로젝트만 `down`하고 볼륨을 유지한다.

5. 새 영수증 화면 상단에 뒤로가기 화살표가 없는지 본다. 브라우저 뒤로가기에서 종료 확인이 뜨면 **머무르기**를 눌러 같은 영수증으로 돌아간다. **이미지 저장·공유**로 PNG를 받아 열어 보고, **관람 완료 → 마이페이지**에서 기록 한 건을 연다. 과거 영수증의 상단 화살표를 누르면 마이페이지로 돌아와야 한다. 네트워크에서 회원의 첫 저장은 201이고, 복귀로 재전송되면 같은 영수증 ID의 200이다.
6. 시크릿 창에서 같은 전시를 열고 **비회원으로 계속**을 선택한다. 다섯 쌍을 선택한 뒤 **이 취향으로 계속**을 누른다. DevTools 네트워크에서 **Preserve log**를 켜고 기록을 비운 뒤 관람을 완주한다. 작품에서 **좋아요**를 누르고 이유 창을 닫은 뒤 선택이 유지되는지 본다. 비회원 영수증이 표시되고 `POST /api/visits`는 0건이어야 한다.
7. 원본 주소의 `/admin/login`을 별도 탭에서 열고 `demo-admin`으로 로그인한다. **회원 조회 → demo-member@example.test**에서 날짜와 작품 3점, **평가**에서 `색감이 좋아요`를 확인한다. PostgreSQL 관람 행은 여전히 한 건이어야 한다. 백업 전에 시험 탭을 닫고 원본에서 쓰기 작업을 끝낸다.

### 3. 새 DB·미디어로 복원

원본 명령을 실행한 PowerShell에 이어 붙인다. 2단계에서 생성한 계정 2개와 관람·반응 각 한 건을 재현한다. 덤프와 미디어를 복사한 다음 원본 시험 프로젝트를 내린다. 원본 볼륨은 남기고, 해제된 Docker 네트워크를 확보한 뒤 새 프로젝트를 기동한다. 운영형 검수 기록의 회원 두 명과 관람 두 건은 별도의 합성 백업을 사용한 결과다.

```powershell
$env:ARTI_DEMO_PORT = "$restorePort"
$db = "$dst-db-1"
$hashCommand = 'cd /app/media && sha256sum fixture-public.png fixture-private.png'
$before = docker compose @source exec -T api sh -ec $hashCommand
docker compose @source exec -T db pg_dump -U arti -d arti -Fc -f /tmp/team-demo.dump
docker compose @source exec -T api tar -C /app/media -cf /tmp/team-demo-media.tar fixture-public.png fixture-private.png
docker cp "${src}-db-1:/tmp/team-demo.dump" (Join-Path $dir 'arti.dump')
docker cp "${src}-api-1:/tmp/team-demo-media.tar" (Join-Path $dir 'media.tar')
Get-FileHash -Algorithm SHA256 -LiteralPath @((Join-Path $dir 'arti.dump'), (Join-Path $dir 'media.tar'))
docker compose @source down
docker compose @restore up -d --wait db
$tables = docker exec $db psql -U arti -d arti -tAc "select count(*) from pg_tables where schemaname='public'"
if ($tables -ne '0') { throw '비어 있는 새 DB가 필요합니다.' }
docker cp (Join-Path $dir 'arti.dump') "${db}:/tmp/arti.dump"
docker exec $db pg_restore -U arti -d arti --exit-on-error --single-transaction --no-owner --no-acl /tmp/arti.dump
docker compose @restore build api migrate
docker compose @restore create api
docker compose @restore run --rm --no-deps -T --user 0 -v "${dir}:/backup:ro" api sh -ec 'test -z "$(ls -A /app/media)" && tar -xf /backup/media.tar -C /app/media fixture-public.png fixture-private.png && chown 10001:10001 /app/media /app/media/fixture-public.png /app/media/fixture-private.png'
docker compose @restore up -d --no-build --wait web
docker compose @restore logs migrate
docker inspect --format '{{.Name}} {{.Image}}' "$dst-api-1" "$dst-web-1"
docker compose @restore exec -T api python manage.py migrate --check
$after = docker compose @restore exec -T api sh -ec $hashCommand
if (Compare-Object $before $after) { throw '복원 미디어 해시 불일치' }
$sql = "select (select count(*) from arti_account), (select count(*) from arti_visit), (select count(*) from arti_visitreaction)"
$expected = docker exec $db psql -U arti -d arti -tAc $sql
if ($expected -ne '2|1|1') { throw "예상과 다른 계정·관람·반응 수 $expected" }
(Invoke-RestMethod "$restoreUrl/api/ready").database
```

복원 `migrate` 로그에서 `No migrations to apply`를 확인한다. 새 Chrome 세션에서 복원 주소의 `/mypage`로 들어가 같은 회원으로 로그인한다. 영수증 한 건을 열어 3점과 좋아요를 확인한 뒤 새로고침한다. 관리자 로그인 뒤 `/admin/members`에서 같은 회원의 관람기록과 `/admin/reactions` 화면의 반응 사유를 대조한다. 공개 `/api/uploads/fixture-public.png`는 200, 비공개 `/api/uploads/fixture-private.png`는 404여야 한다. 관리자 작품 관리의 **검증용 작품 13** (`/admin/artworks/fixture-art13`)에서 이미지 미리보기를 확인한다.

복원 후 아래 권한 대조까지 마치고 [팀 회신 양식](#팀-회신-양식)에 적는다. [운영형 검수 기록](../작업기록/2026-11-15_운영형로컬기동과합성복원.md)

11/15 문서 검수에서 이 기동·복원 명령으로 새 프로젝트 두 개를 만들고, PC Chrome에서 회원·비회원 관람과 복원 후 조회를 확인했다. 계정 2개, 관람 1건, 반응 1건과 미디어 해시가 기대한 값과 일치했다. 작성자 외 팀원 재현 결과는 회신을 받으면 추가한다.

11/16에는 `ee189e8`과 같은 앱 코드로 갱신된 회원·비회원 관람, 뒤로가기, 도슨트 503 후 복귀, PNG 저장을 재현했다. 원본 시험 프로젝트를 내린 뒤 문서의 복원 명령을 다시 실행해 `2|1|1` 집계, 미디어 해시 두 개, 같은 영수증 ID와 관리자 반응을 확인했다. 복원 권한과 회신용 증거 수집까지 마치면 이번 시험 PowerShell에서 `docker compose @restore down`으로 복원 컨테이너를 내린다.

### 복원 후 영수증 접근 권한 확인

3단계의 `2|1|1` 확인 뒤 같은 PowerShell에서 아래 명령을 실행한다. 회원 A는 원본 회원이다. 회원 B는 **복원본에서만** 새로 만들며, 다시 실행할 때는 이미 만든 B로 로그인하거나 새 시험 주소를 쓴다. 아래 출력은 성공·차단 결과와 합성 영수증 ID만 남긴다.

```powershell
function Send-DemoJson($path, $body) {
    Invoke-RestMethod -Method Post -Uri "$restoreUrl$path" -ContentType 'application/json' -Body ($body | ConvertTo-Json -Compress)
}
function Assert-DemoStatus($path, $headers, $expectedCode) {
    $code = [int](Invoke-WebRequest -Uri "$restoreUrl$path" -Headers $headers -SkipHttpErrorCheck).StatusCode
    if ($code -ne $expectedCode) { throw "$path returned $code, expected $expectedCode" }
    "$code $path"
}
$owner = Send-DemoJson '/api/auth/login' @{ email = 'demo-member@example.test'; password = $password }
$termsVersion = docker compose @restore exec -T api python manage.py shell --verbosity 0 -c 'from arti.member import SIGNUP_TERMS_VERSION; print(SIGNUP_TERMS_VERSION)'
if ($LASTEXITCODE -ne 0 -or !$termsVersion) { throw 'Could not read the deployed signup terms version.' }
$other = Send-DemoJson '/api/auth/signup' @{
    email = 'demo-other@example.test'; password = $password; nickname = '합성 비교 회원'
    termsAccepted = $true; termsVersion = $termsVersion
}
$admin = Send-DemoJson '/api/admin/login' @{ id = 'demo-admin'; password = $password }
$ownerHeaders = @{ Authorization = "Bearer $($owner.token)" }
$otherHeaders = @{ Authorization = "Bearer $($other.token)" }
$adminHeaders = @{ 'X-Admin-Token' = $admin.token }
$ownerList = "/api/users/$($owner.user.id)/visits"
$adminList = "/api/admin/members/$($owner.user.id)/visits"
$visits = Invoke-RestMethod "$restoreUrl$ownerList" -Headers $ownerHeaders
$otherVisits = Invoke-RestMethod "$restoreUrl/api/users/$($other.user.id)/visits" -Headers $otherHeaders
$adminVisits = Invoke-RestMethod "$restoreUrl$adminList" -Headers $adminHeaders
if ($visits.Count -ne 1 -or $otherVisits.Count -ne 0 -or $adminVisits.Count -ne 1 -or $adminVisits[0].id -ne $visits[0].id) {
    throw '복원된 회원·관리자 목록이 일치하지 않습니다.'
}
$receiptId = $visits[0].id
$receiptPath = "/api/visits/$receiptId"
$ownerDetail = Invoke-RestMethod "$restoreUrl$receiptPath" -Headers $ownerHeaders
$adminDetail = Invoke-RestMethod "$restoreUrl/api/admin/visits/$receiptId" -Headers $adminHeaders
$order = 'fixture-art01,fixture-art03,fixture-art05'
if ($ownerDetail.id -ne $receiptId -or $adminDetail.id -ne $receiptId -or
    ($ownerDetail.viewedArtworkIds -join ',') -ne $order -or ($adminDetail.viewedArtworkIds -join ',') -ne $order) {
    throw '복원된 영수증 ID 또는 관람 순서가 다릅니다.'
}
Assert-DemoStatus $ownerList $otherHeaders 403
Assert-DemoStatus $receiptPath $otherHeaders 403
Assert-DemoStatus $ownerList @{} 401
Assert-DemoStatus $receiptPath @{} 401
Assert-DemoStatus $receiptPath @{ Authorization = "Bearer $($admin.token)" } 401
Assert-DemoStatus "/api/admin/visits/$receiptId" @{ 'X-Admin-Token' = $owner.token } 401
Assert-DemoStatus '/api/uploads/fixture-public.png' @{} 200
Assert-DemoStatus '/api/uploads/fixture-private.png' $ownerHeaders 404
Assert-DemoStatus '/api/admin/uploads/fixture-private.png' $adminHeaders 200
"PASS 복원 영수증 $receiptId, 회원 A 1건, 회원 B 0건, 관리자 1건"
```

Chrome에서도 같은 주소를 확인한다. 회원 A·회원 B·비회원은 각각 다른 Chrome 프로필을 쓰거나, 각 역할을 끝낼 때 시크릿 창을 모두 닫고 새 세션으로 이어간다. `$restoreUrl/receipt/$receiptId`의 주소를 회원별로 직접 열고 새로고침한다. 관리자는 웹에서도 관람·반응·비공개 도판을 확인한다.

| 확인 주체 | 실행과 기대 결과 |
| --- | --- |
| 회원 A | `/api/users/<A ID>/visits`에 한 건. `/api/visits/<영수증 ID>`는 200. PC Chrome에서 `/receipt/<영수증 ID>`를 직접 열고 새로고침해도 감상 작품을 확인할 수 있다. |
| 회원 B | 자기 목록은 빈 배열. A의 목록과 영수증 상세 API는 403. A의 영수증 화면 주소를 직접 열고 새로고침해도 안내와 재시도만 표시되고 영수증 본문은 보이지 않는다. |
| 비회원 | A의 목록과 상세 API는 401. 영수증 화면 주소는 로그인으로 이동한다. |
| 관리자 | `/api/admin/members/<A ID>/visits`의 한 건과 `/api/admin/visits/<영수증 ID>` 상세를 A의 조회 결과와 대조한다. 관리자의 토큰을 회원용 `Authorization: Bearer`로 보내거나 회원 토큰을 `X-Admin-Token`으로 보내면 401이다. 비공개 미디어는 회원 주소에서 404, 관리자 주소에서 200이다. |

`e2f8127` 운영형 빌드를 새 Compose 프로젝트로 복원해 위 네 역할을 모두 확인했다. API는 Nginx 경유 응답으로 대조했고, 영수증 주소 직접 진입·새로고침은 PC Chrome에서 실행했다. 복원 회원 A의 시험 비밀번호는 그 복원본에서만 재설정했다. 사용한 합성 백업은 [Compose 복구 기록](../작업기록/2026-11-16_Compose기동실패와Nginx복구.md)에 적힌 자료다.

`429beaa`와 같은 제품 트리에서 원본·복원 Compose 명령과 새 권한 대조 명령을 실행했다. 원본에 합성 회원의 관람·반응 각 한 건을 API로 만든 뒤 복원했다. 덤프·미디어 SHA-256, 복원 후 `2|1|1` 집계, 같은 영수증 ID, 다른 회원 403·비회원 401, 미디어 200/404/200을 확인했다. 팀원은 위 브라우저 관람 단계까지 포함해 자기 PC 결과를 회신한다.

## 운영 인수 · Nginx HTTPS 콜백과 로그

기동·복원·권한·HTTPS를 한 번에 재현하려면 운영형 배포 전 검사기를 사용한다. 지정 커밋을 아카이브해 만든 API·웹 이미지를 두 Compose 프로젝트와 별도 HTTPS 시험에서 사용한다. 팀 PC의 화면 조작과 회신은 이 문서의 관람 순서대로 진행한다. [자동 실행과 결과 읽기](../작업기록/2026-11-16_운영형배포전검사.md#실행과-결과)

1. 운영 담당은 새 PowerShell 세션과 별도 HTTPS 포트를 쓴다. `429beaa`의 프론트 의존성을 설치한 뒤 Django 대상 정적 빌드와 API 이미지를 만든다. 스크립트가 기동 대기 중 `pg_isready`의 종료 코드를 직접 판정하므로 새 셸에서 `$PSNativeCommandUseErrorActionPreference = $false`로 실행한다. 준비한 PostgreSQL 17·Nginx 1.28 이미지로 `frontend/tests/runKakaoNginx.browser.ps1 -ApiImage <시험용 API 이미지> -HttpsPort 5623`을 실행한다. 시험은 루프백의 임시 인증서, 합성 DB와 카카오 모의를 쓴다. [빌드와 실행 명령](../작업기록/2026-11-16_NginxHTTPS카카오콜백로그.md#재현)
2. 정상 콜백 **302·같은 출처 복귀**와 흐름 쿠키의 `Secure`, `HttpOnly`, `SameSite=Lax`를 확인한다. 취소 뒤 기존 세션, 재로그인 뒤 같은 회원·V2·영수증 한 건을 확인한다. 오래된 완료는 400이어야 한다.
3. 업스트림을 닫으면 콜백 **502**에 `Cache-Control: no-store`, `Referrer-Policy: no-referrer`가 있어야 한다. Nginx 로그에서 정상·장애 콜백의 `code`·`state`가 검출되지 않고, Gunicorn에는 경로와 응답 코드만 남아야 한다. 일반 `/api/ready`의 502는 로그에 남아야 한다. 스크립트가 내는 두 `PASS HTTPS …` 줄과 시험 커밋·이미지를 회신에 남긴다.
4. 실제 운영 주소와 앱 담당이 정해지면 대상 TLS 종료 지점과 모든 수집 로그의 콜백 설정을 대조하고, 승인 후 등록한 주소에서 취소·연결·재로그인·장애·복구를 확인한다. 실제 주소·카카오 앱·공유 로그의 판정은 운영 인수 결과로 따로 기록한다. [운영과 예산 결정](W12_운영구성과예산결정안.md) · [가입 안내와 카카오 준비](2026-11-14_가입안내와OAuth준비.md)

현재 제품 트리의 로컬 재검수에서 정상·장애 두 `PASS HTTPS`를 확인했다. PC Chrome은 모의 카카오를 사용했고, 루프백 Nginx가 제품 프록시 설정을 읽었다.

## 팀 회신 양식

실행자는 한 항목씩 `통과 / 실패 / 미실행`으로 적는다. 실패·미실행 항목에는 해당 화면 또는 단계, 누른 버튼, 기대 결과와 실제 결과, 응답 코드 또는 차단 이유를 적는다. 화면·로그 사본에서 비밀번호, 세션 토큰, 인가 코드·상태값은 가린다.

```text
실행자 / 일시(KST) / 커밋 / OS·Chrome / PowerShell·Docker·Compose 버전:
```
