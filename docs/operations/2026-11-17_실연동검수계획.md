# 실제 모델·메일·카카오 첫 시험 가이드

## 공통 준비

- 팀이 정한 HTTPS 시험 주소에 검수 대상 커밋을 고정한다. 적용 전 합성 PostgreSQL과 미디어를 백업하고, `migrate --plan` → `migrate --noinput` → `GET /api/ready` 200 순서로 확인한다. 외부 연결은 아래 단계마다 따로 켠다. 시험용 계정 2개 중 A에만 회원 영수증을 한 건 만들어 검수 기준을 잡는다.
- 준억 또는 서비스 소유자가 시험 프로젝트·계정과 발신 주소를 정하고 서버 비밀 설정에 값을 넣는다. 실연동 시간에는 합성 작품·회원과 팀이 통제하는 편지함만 사용한다. 링크와 API 키는 회신 양식에 적지 않는다.
- 모델과 SMTP는 서로 다른 시험 설정에서 동시에 진행할 수 있다. 카카오는 마지막에 시험하고, 카카오 로그인이 되면 메일과 이어서 한 번 더 확인한다. 각 단계에서 시간, 배포 커밋, 단계, HTTP 코드, ARTI 요청 ID와 통과 여부를 남긴다.

### 0. PowerShell에서 시험 서버 준비

저장소 루트의 새 PowerShell에서 실행한다. 같은 명령을 새 시험 이름으로 한 번 더 실행하고 `ARTI_TRIAL_WEB_PORT`를 다르게 주면 모델·메일에 별도 DB를 쓸 수 있다. 팀이 기존에 만든 시험 환경이 있으면 그 환경의 프로젝트·설정 파일·HTTPS 주소를 사용하고 아래 새 환경 생성은 건너뛴다.

```powershell
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $true
$artiTrial = 'arti-live-' + (Get-Date -Format 'yyyyMMddHHmmss')
$artiDir = Join-Path (Get-Location) "data/private/$artiTrial"
New-Item -ItemType Directory -Path $artiDir | Out-Null
$artiEnv = Join-Path $artiDir 'compose.env'
$artiOverride = Join-Path $artiDir 'reverse-proxy.yaml'
@"
ARTI_DB_PASSWORD=$([guid]::NewGuid().ToString('N'))
DJANGO_SECRET_KEY=$([guid]::NewGuid().ToString('N'))$([guid]::NewGuid().ToString('N'))
ARTI_ENV=test
ALLOW_TEST_FIXTURES=true
ARTI_TASTE_PROFILE_V2_ENABLED=true
ARTI_TRIAL_WEB_PORT=5189
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,api
ARTI_LLM_PROVIDER=disabled
"@ | Set-Content -LiteralPath $artiEnv -Encoding utf8NoBOM
@'
services:
  api:
    ports: !reset []
  web:
    build:
      context: ./frontend
      dockerfile: Dockerfile.static
    depends_on:
      api:
        condition: service_healthy
    ports:
      - "127.0.0.1:${ARTI_TRIAL_WEB_PORT}:80"
'@ | Set-Content -LiteralPath $artiOverride -Encoding utf8NoBOM
$artiCompose = @('--env-file', $artiEnv, '-f', 'compose.yaml', '-f', $artiOverride, '-p', $artiTrial)
docker compose @artiCompose config --quiet
docker compose @artiCompose build api migrate web
docker compose @artiCompose run --rm migrate python manage.py migrate --plan
docker compose @artiCompose up -d --wait web
docker compose @artiCompose exec -T api python manage.py migrate --check
docker compose @artiCompose exec -T api python manage.py load_test_fixture
docker compose @artiCompose exec api python manage.py bootstrap_admin --login-id trial-admin --name '합성 검수 관리자'
(Invoke-WebRequest 'http://127.0.0.1:5189/api/ready').StatusCode
```

- 응답 `200` 뒤 PC에서 `http://127.0.0.1:5189/admin`과 `http://127.0.0.1:5189/exhibitions/fixture-ex01`을 연다. 공통 Compose는 직접 관람 플래그 기본값을 꺼 둔다. 팀 지도 검수에서 직접 관람도 볼 때만 시험 파일에서 `ARTI_EXHIBITION_ORDER_DEMO_ENABLED=true`를 켠다.
- 메일과 카카오 시험 전에 HTTPS 프록시를 같은 호스트의 `127.0.0.1:5189`로 연결한다. 시험 호스트 이름을 `DJANGO_ALLOWED_HOSTS`에 추가하고, 브라우저 주소와 `/api`·`/auth/kakao/complete`·`/password/reset`이 같은 호스트를 쓰도록 한다. `$artiOrigin = 'https://staging.arti.example'`는 팀이 쓸 주소로 바꾼다. 브라우저가 실제로 신뢰하는 인증서와 `GET /api/ready` 200을 확인한다. 포트나 호스트를 바꿨으면 아래 예제의 주소도 바꾼다.
- `notepad $artiEnv`로 시험 파일을 열어 아래 파트별 설정을 추가하거나 기존 값을 바꾼다. 같은 이름의 줄은 하나만 둔다. `check_live_config`는 외부에 접속하지 않고 키 값을 출력하지 않는다. 설정이 맞으면 `docker compose @artiCompose up -d --no-deps --force-recreate --wait api`로 API에 반영한다. 기존 DB·미디어는 같은 프로젝트 볼륨을 사용한다.
- 메일·카카오는 HTTPS 주소의 `/signup`에서 계정 A와 B를 만든다. A에만 시험 수신함을 등록해 로그인하고 `/exhibitions/fixture-ex01`에서 감상을 한 번 마친다. `/mypage`에 기록이 한 건 뜨면 해당 영수증을 연다. B는 다른 ARTI 계정으로 연결이 막히는지 확인할 때 쓴다.

## 1. Luna와 Kanana

1. 팀 소유의 시험용 OpenAI 프로젝트 키를 `OPENAI_API_KEY`에 넣고, `ARTI_LLM_PROVIDER=openai_compatible`, `OPENAI_MODEL=gpt-6-luna`, `ARTI_DRAFT_PROVIDER=default`를 시험 배포에 적용한다. 요약·가이드별 모델이 따로 설정되어 있으면 이번에 확인할 모델로 맞춘다. 관리자 **작품 관리 → 합성 작품 → AI 분석 · 요약 · 가이드**에서 **쉬운 요약 다시 생성**과 **관람가이드 다시 생성**을 한 번씩 누른다. 원문만 비교할 때는 이미지 분석 체크를 끈다. 생성 상태, 내용의 근거 일치, 질문 1~3개와 짝이 맞는 힌트, 제안 확인 중 기존 공개본 유지를 본다. 확정 뒤 관람자의 작품해설·관람가이드에서 새 내용을 열고 도슨트에 같은 질문을 한 번 보낸다. 사용량에 표시된 모델 이름은 가격·사용량 대조에 별도로 기록한다. [AI 설정과 모델 선택](AI_설정과모델선택.md)
2. Kanana는 이 노트북의 WSL에서 고정 리비전으로 기동한다. 서버는 루프백에 열고 시험 Django가 접근 가능한 경로를 확인한다. `/v1/models`와 A-04 원문 한 건부터 확인하고, 같은 원문으로 Luna와 같은 두 작업을 실행한다. 구조화 출력·지연·메모리를 기록한다. 기동이 안 되면 오류 원인을 기록한다. 1.3B로 진행하는 경우 별도 시험으로 기록하고 다시 평가표를 고정한다. [Kanana 3B 고정 리비전](https://huggingface.co/kakaocorp/kanana-2-3b-instruct/commit/6a5d7889964c4c590299d16e309eabab1f73f8a9) · [기동 명령과 A-04 전용 연결](2026-11-17_도슨트모델과관리자운영검토.md)
3. 두 모델의 첫 결과를 확인한 뒤, 합성 작품 3점 × 2작업 × 2회 × 2모델을 같은 원문 버전으로 실행한다. 작업 전에 `scripts/prepare_draft_model_comparison.py --product-revision <시험커밋>`으로 X/Y 대응표를 발급해 비공개로 보관한다. 채점자에게는 `--review-template`과 답안만 전달한다. 채점 종료 뒤 `--summarize-review <채점표.json> --private-plan <비공개대응표.json>`으로 12쌍을 모델·작업별로 집계한다. 전송 실패로 답안이 없으면 실패 건으로 남긴다. 근거를 잘못 붙이거나 다른 작품 정보가 섞이면 해당 모델의 적용을 보류한다. Luna 도판의 효용은 원문만·원문+도판으로 따로 비교한다. [판정표와 원문·도판 해시](../review/docent-2026-11-15/luna-fixtures)
4. 팀의 시험 프로젝트만 대상으로 사용량을 모델별로 뽑는다. OpenAI 사용량의 시간 경계와 청구 비용의 일 단위 경계에 ARTI 집계 구간을 맞춘다. 두 입력의 구간과 통화가 맞으면 아래 대조 도구를 실행한다. 도판·서비스 등급 등 단가가 달라지는 항목이 섞이면 일치 여부와 실제 청구액을 기록하고 텍스트 단가만으로 차액을 해석하지 않는다. [OpenAI 사용량](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/completions) · [OpenAI 비용](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs)

장애 시 시험용 모델 연결을 내리고 A-04에서 확정된 기존 공개본과 관람 흐름을 확인한다. Kanana만 문제면 `ARTI_DRAFT_PROVIDER=default`로 복귀한다. Gemini·Gemma 등 다른 모델 후보는 같은 원문과 판정표로 평가할 수 있다.

```dotenv
ARTI_LLM_PROVIDER=openai_compatible
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_API_KEY=시험_프로젝트에서_발급한_키
OPENAI_MODEL=gpt-6-luna
ARTI_DRAFT_PROVIDER=default
```

```powershell
# 시험 파일에서 Luna 값을 설정한 뒤 관리자 화면을 열기 전에 실행합니다.
docker compose @artiCompose run --rm --no-deps -T api python manage.py check_live_config luna
docker compose @artiCompose up -d --no-deps --force-recreate --wait api
# 배정표와 채점표를 같은 검수 커밋에 고정합니다.
$artiRevision = git rev-parse HEAD
python -X utf8 scripts/prepare_draft_model_comparison.py --product-revision $artiRevision |
    Set-Content -Encoding utf8NoBOM (Join-Path $artiDir 'draft-private-plan.json')
python -X utf8 scripts/prepare_draft_model_comparison.py --product-revision $artiRevision --review-template |
    Set-Content -Encoding utf8NoBOM (Join-Path $artiDir 'draft-review.json')
# 답안과 점수를 채운 뒤 원래 대응표로 집계합니다.
python -X utf8 scripts/prepare_draft_model_comparison.py --product-revision $artiRevision `
    --summarize-review (Join-Path $artiDir 'draft-review.json') `
    --private-plan (Join-Path $artiDir 'draft-private-plan.json')
```

Kanana는 이 노트북의 Ubuntu WSL에서 `python3`를 확인했다. 검사 시 사용 가능 메모리는 약 9GiB였고 기본 Python 환경에 `torch`, `transformers`, `vllm`은 없었다. `wsl -d Ubuntu`에서 CPU 런타임의 요구조건을 확인해 설치한 뒤, [고정 리비전과 시작 명령](2026-11-17_도슨트모델과관리자운영검토.md#kanana-2-초안-연결-재현)으로 먼저 한 건을 재현한다. Django와 Kanana를 같은 WSL에서 띄울 때는 `http://127.0.0.1:8010/v1`을 쓸 수 있다. Compose에서 WSL 또는 별도 호스트로 연결할 때 Django의 제공자 검사는 `http://host.docker.internal:8010/v1`을 허용하지 않으므로, 제한된 HTTPS를 구성하거나 Django 시험 프로세스를 WSL 쪽에 띄운다. 그 환경에서 `python backend-django/manage.py check_live_config kanana`를 먼저 실행한다. [vLLM CPU 설치](https://docs.vllm.ai/en/latest/getting_started/installation/cpu/)

### 작업·모델별 비용 대조

`python scripts/compare_model_costs.py <ARTI집계.json> <제공자집계.json>`을 저장소 루트에서 실행한다. 두 파일은 키·응답 원문 없이 집계 값만 담고, 프로젝트 식별자 `project`와 오프셋이 있는 ISO 시각 `start`, `end`를 같은 범위로 맞춘다. `inputTokens`는 캐시 입력을 포함한 전체 입력 값으로 정규화한다. ARTI의 집계가 기간 전체를 실제로 덮는지 확인한다.

| 파일 | 필드 |
| --- | --- |
| ARTI | `rows`에 관리자 `textModelUsageByTaskModel`의 `task`, `model`, `inputTokens`, `outputTokens`, `cachedInputTokens`, `missing`, `cacheMissing` |
| 제공자 | 프로젝트 `currency`, `billedCost`, `rows`에 모델별 같은 세 토큰 값과 적용 가능한 경우의 `ratesPerMillion` (`input`, `cachedInput`, `output`). 모델 별칭은 파일을 만들 때 동일하게 맞춘다. |

대시보드의 ‘오늘’ 집계는 한국 시각 기준이다. 청구 내역과 기간을 맞추려면 아래 날짜를 종료된 실제 시험 구간으로 바꿔 내보낸다. `--start`는 포함, `--end`는 제외다. `--project`는 대조용 식별자이므로 해당 프로젝트만 호출한 시험 서버에서 실행한다.

```powershell
$artiUsage = Join-Path $artiDir 'arti-model-usage.json'
$vendorUsage = Join-Path $artiDir 'provider-model-usage.json'
docker compose @artiCompose exec -T api python manage.py export_model_usage `
    --project '시험 프로젝트 식별자' --start '2026-11-16T00:00:00Z' --end '2026-11-17T00:00:00Z' |
    Set-Content -LiteralPath $artiUsage -Encoding utf8NoBOM
# 표의 제공자 필드대로 $vendorUsage 파일을 만든 뒤 실행합니다.
python -X utf8 scripts/compare_model_costs.py $artiUsage $vendorUsage
```

OpenAI는 프로젝트와 모델로 Usage를 필터·그룹화하고 `input_tokens`, `input_cached_tokens`, `output_tokens`를 사용한다. `billedCost`는 같은 프로젝트·기간의 비용으로 채우고 자료가 없으면 `null`을 쓴다. 비용과 단가는 소수 문자열 또는 정수로 넣는다. 작업·모델 계측 도입 전 호출이 잡히면 `ungroupedAttempts`가 표시된다. 누락이나 토큰 불일치가 있으면 프로젝트 추정 비용과 청구 차액은 비워 둔다. [Usage 필드](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/completions) · [Costs 집계](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs)

## 2. 실제 SMTP와 수신함

1. 팀 발신 주소, 합성 계정 A 소유의 시험용 수신함, 전용 SMTP 연결을 준비한다. `ARTI_PASSWORD_RESET_ORIGIN`과 `ARTI_PASSWORD_RESET_FROM`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, 제공자가 요구하는 TLS 설정을 적용하고 `python manage.py send_password_reset_mail`을 시험 배포의 같은 환경에서 실행한다. [설정과 배포 절차](비밀번호재설정_로컬검수와배포준비.md) · [Django SMTP 설정](https://docs.djangoproject.com/en/5.2/topics/email/)
2. 등록·미등록 요청은 둘 다 `204`이고 시험 수신함에는 등록 요청의 메일이 도착해야 한다. 도착 시각, 보낸 주소, HTTPS 호스트, 스팸 분류와 제공자 발송 상태를 확인한다. 해당 제공자가 반송 시뮬레이터를 제공하면 반송 상태도 확인한다.
3. 링크를 열어 비밀번호를 바꾼 뒤 이전 세션 `401`, 링크 재사용 실패, 새 비밀번호로 같은 회원·영수증 접근 성공을 확인한다. SMTP가 수락 후 응답을 잃는 경계에서는 같은 링크가 여러 통 도착할 수 있으므로 한 번만 쓸 수 있는지를 본다. 원문·링크·이메일 주소가 앱·프록시 로그에 노출되면 시험을 멈춘다.

도착이 지연되면 발송 작업과 제공자 수락 상태부터 확인한다. 인증 오류가 반복되면 발송 작업을 멈추고 시험 API에서 재설정 설정을 내린다. 기존 이메일 로그인과 영수증 접근을 확인한다.

```dotenv
ARTI_PASSWORD_RESET_ORIGIN=https://staging.arti.example
ARTI_PASSWORD_RESET_FROM=검증한_발신주소
EMAIL_HOST=SMTP_제공자_호스트
EMAIL_PORT=587
EMAIL_HOST_USER=SMTP_사용자명
EMAIL_HOST_PASSWORD=SMTP_자격증명
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
```

```powershell
# SMTP 설정을 파일에 넣은 뒤 실행합니다. 예: $artiOrigin = 'https://stage.example.org'
docker compose @artiCompose run --rm --no-deps -T api python manage.py check_live_config mail --origin $artiOrigin
docker compose @artiCompose up -d --no-deps --force-recreate --wait api
(Invoke-RestMethod "$artiOrigin/api/auth/password-reset/status").enabled
# 브라우저에서 계정 A 이메일로 재설정을 한 번 요청한 다음 발송합니다.
docker compose @artiCompose exec -T api python manage.py send_password_reset_mail
```

STARTTLS는 일반적으로 `EMAIL_PORT=587`, `EMAIL_USE_TLS=true`, `EMAIL_USE_SSL=false`를 사용한다. 암시적 TLS는 제공자 안내에 따라 `EMAIL_PORT=465`, `EMAIL_USE_TLS=false`, `EMAIL_USE_SSL=true`를 사용한다. 이메일이 도착하면 링크를 UI에서 연다. 하루 이상 유지할 시험 서버에서는 배포 담당자가 같은 명령에 발송 주기를 지정한다. [Django TLS 설정](https://docs.djangoproject.com/en/5.2/ref/settings/#email-use-tls)

## 3. 카카오 첫 연결과 복구

1. 팀 앱 소유자가 고정 HTTPS 주소와 시험 앱을 만들고 REST 키에 `/api/auth/kakao/callback`까지 일치하는 URI를 등록한다. 로그인과 OIDC를 활성화하고 서버 설정을 적용한다. `GET /api/auth/kakao/status`의 `enabled: true`를 확인한다. [카카오 공식 설정](https://developers.kakao.com/docs/ko/kakaologin/prerequisite) · [ARTI 설정·검수 순서](카카오로그인_첫연동가이드.md)
2. 계정 A로 이메일 로그인한 뒤 마이페이지에서 ARTI 비밀번호를 다시 입력해 카카오를 연결한다. 로그아웃 후 카카오로 로그인해 같은 회원 ID와 영수증 ID 한 건을 확인한다. 계정 B에서는 같은 카카오 식별자 중복 연결이 막혀야 한다. 취소와 콜백 재사용도 확인하고, 프록시 로그에서 콜백 코드·토큰 노출 여부를 확인한다.
3. 카카오 연결이 된 A의 비밀번호를 SMTP로 다시 설정하고 카카오로 재로그인한다. 같은 회원·영수증을 확인한다. 기능을 내려야 하면 카카오 환경값을 비운 시험 API에서 이메일 로그인으로 돌아가 동일한 영수증을 연다. 공개 전에는 운영 앱, 계정의 소유 확인 및 연결 해제·탈퇴 정책을 별도로 확인한다.

```dotenv
ARTI_KAKAO_CLIENT_ID=콘솔의_REST_API_키
ARTI_KAKAO_CLIENT_SECRET=해당_REST_키의_클라이언트_시크릿
ARTI_KAKAO_CALLBACK_URL=https://staging.arti.example/api/auth/kakao/callback
```

```powershell
# 콘솔에 이 주소를 등록한 뒤 ARTI_KAKAO_CALLBACK_URL에도 같은 문자열을 넣습니다.
"$artiOrigin/api/auth/kakao/callback"
docker compose @artiCompose run --rm --no-deps -T api python manage.py check_live_config kakao --origin $artiOrigin
docker compose @artiCompose up -d --no-deps --force-recreate --wait api
(Invoke-RestMethod "$artiOrigin/api/auth/kakao/status").enabled
```

콘솔에서 확인할 순서는 **앱 → REST API 키 → 리다이렉트 URI**, **카카오 로그인 사용 설정**, **OpenID Connect**다. PC에서 주소를 처음 열어 `enabled`가 `True`이면 합성 계정으로 2번 절차를 진행한다. 시험을 막는 설정 오류는 `check_live_config`와 카카오 오류 코드를 함께 보고, 첫 실패의 단계·상태 코드·요청 ID만 회신한다. [카카오 오류 코드](https://developers.kakao.com/docs/ko/kakaologin/trouble-shooting)
