# 전시·작품 자료와 DB의 확장 방향

2026-11-09 / 코드4a9dbe9 / 유영국 인수표 작성 중 사용자의 확장성 의견을 현재 코드와 대조했다. **여러 전시·작가·전시관을 수용하는 방향은 적절하다. 이번에는 자료 경계를 정리하고 후속 적재 설계의 기준으로 남기며 DB migration/API 계약 변경은 하지 않는다.**

## 현재 가능한 것과 제한

- [Exhibition 모델](../../backend-django/arti/models.py)은 전시별ID·기간·상태·venue 문자열·rooms·floor_plan·입구·버전을 가진다. 여러 전시 행을 만들 수 있으며 방과 도면은 전시마다 다르게 구성할 수 있다.
- [Artwork 모델](../../backend-django/arti/models.py)은 전시를 ForeignKey로 참조한다. 작품ID는 제목/연도와 별도이며 작품은 한 전시에만 속한다. 출처·근거 버전·검수·AI 상태와 해당 전시의 방/좌표도 이 행에 있다.
- [공개 API](../../backend-django/arti/views.py)는 running 전시/approved 작품을 필터링하고 전시ID를 받아 조회한다. 유영국 한 전시 전용 스키마는 아니다.
- venue는 공통 전시관 엔티티가 아니라 문자열이다. rooms/floor_plan은 전시별 JSON이며 건물/층/상설 전시실을 독립적으로 관리하지 않는다. 동일한 작품을 여러 전시에 재출품할 때 작품 공통정보와 배치를 공유하는 관계도 없다. 현재 구조가 이런 확장까지 이미 구현했다고 설명하면 안 된다.
- [기존 importer](../../backend-django/arti/management/commands/import_capture_bundle.py)는 ex-capture·40점 전용이다. 이 제한을 실제 서비스 DB의 전체 수용 능력과 혼동하지 않는다. 유영국16점은 이 형식의 입력이 아니다.

## 이번 자료부터 적용하는 경계

1. **자료 파일과 작품을 구분:** 인수 recordId/assetId/파일 해시는 파일·전달 기록을 추적한다. DB 작품ID나 공식 관리번호와 동일하지 않다. 제목·연도·파일명은 고유키로 쓰지 않는다. 새 사진/크롭은 같은 작품일 수도 있고, 같은 판화 도상은 서로 다른 개별 판본일 수도 있다.
2. **작품 정보와 출품을 구분:** 작가·제목·재료·치수·식별 근거는 작품 후보 정보다. 어느 전시에 출품했는지와 해당 전시의 해설/방/좌표는 별도 관계다. 이번 인수표의 exhibitionAssignments는 전부 비어 있으며 실제 출품을 추정하지 않는다.
3. **전시관과 전시를 구분:** 소장처, 건물/기관, 특정 전시, 전시실/배치가 각각 무엇을 가리키는지 기록한다. MMCA 소장이라는 근거를 서울시립미술관 전시 출품이나 특정 방의 좌표 근거로 전용하지 않는다.
4. **근거와 승인을 구분:** 공식 후보 레코드와 시각 대응, 사람 검수, 콘텐츠 확정, 이미지 이용 조건을 독립적으로 관리한다. 공식 링크가 있다고 일괄 approved로 올리지 않는다. 새 설명/이미지/출처로 바꿀 때 기존 sourceVersion/contentVersion 및 stale 정책을 보존한다.

이는 [유영국 인수표](../../data/intake/2026-11-09-yoo-youngkuk/README.md)의 연구 자료 형식에 적용한 경계이며 현행 API에 필드를 추가한 것이 아니다. 새로운 importer를 바로 만들거나 기존40점/DB를 변경하지 않았다.

## 후속 적재 단계의 최소 요구

- 전시ID/작품 매핑/원본 asset 참조를 입력으로 받고 유영국·16점·기간·방 이름을 코드 상수로 고정하지 않는다. 현재 capture40 importer는 원래 목적과 검증 근거를 보존한다.
- 건수/ID/해시/참조/중복·충돌을 검증하고 dry-run 후 명시 적재한다. 타 전시 자료를 덮어쓰지 않고 draft/source_check에서 시작한다. 재적재 시 무조건 덮어쓰거나 사람 검수를 자동 유지하지 않는다.
- 실제 출품 또는 시연용 재구성 여부와 근거 없는 방/좌표를 구분한다. 실제 도면 없는 좌표를 실내 길찾기 정확성의 근거로 쓰지 않는다.
- 미확정 작품/판본과 미검수 설명은 공개 목록에 섞이지 않는다. 복원/실패 시 파일·DB 관계와 기존 승인·기록이 유지되는지 확인한다.
- 전시2개를 시험 데이터로 사용해 공개 목록/관리자 변경/추천/지도/도슨트 문맥/관람 기록이 전시를 넘어 섞이지 않는지 확인한다. 실제 이미지를 추가 공개할 필요 없이 fixture로 관계를 검사할 수 있다.

## DB 관계 분리가 필요해질 때

같은 작품을 여러 전시에 재사용하거나 전시관별 방·층·도면을 공유해야 할 요구가 생기면 다음 관계를 후보로 검토한다.

| 개념 | 책임 | 분리 시 주의 |
| --- | --- | --- |
| 작품 원장(CatalogueWork) | 작품 자체의 식별·작가·연도·매체·치수·근거 | 판화 도상과 개별 판본 구분을 요구에 맞춰 정의. 제목으로 병합 금지 |
| 전시 출품(ExhibitionArtwork) | 전시-작품 연결·전시별 설명·배치·노출 | 현재 Artwork와 DTO/기록/AI캐시 식별자의 매핑 필요. 작품 공통 근거 승인과 전시별 배치 승인을 구분 |
| 전시관(Venue)·공간 | 기관/건물/층/방/도면의 재사용 | 실제 관리 요구가 생길 때 도입. 기존 전시별 rooms/floor_plan의 변환·버전 정책 필요 |
| 자료/근거(Asset·Source) | 파일·이용 조건·원 출처·확인 기록 | 해시/URL 변경 시 어떤 콘텐츠·승인에 영향을 주는지 연결 |

현재 전시 하나를 인수하는 데 이 테이블을 모두 먼저 만들 필요는 없다. 관계 분리를 결정할 때 기존 Artwork ID, Visit/VisitReaction의 참조, 저장된 snapshot, 도슨트 문맥·버전·캐시, 프론트 DTO를 함께 검토하고 별도 과업·migration/되돌리기·회귀 기준을 확정한다. 무검토 M:N 추가나 현재 승인/기록 계약의 전면 교체는 하지 않는다.

## 결정과 다음 순서

확장 방향은 **자료 인수부터 작품/파일/출품/전시관을 구분하고, 현재 전시ID 기반 구조를 재사용하면서 필요한 범위만 구현**하는 것으로 제안한다. 유영국 유지와16점 인수표 작성은 사용자 결정/수행 사항이고, 작품 원장·전시관 테이블 분리는 후속 설계 후보다.

이번 과업 다음에는 핵심3점 콘텐츠 검수와07번 원 출처 확보를 진행할 수 있다. DB 반영 전 백업/복원 확인 → 인수 형식과 현재 계약 차이 확인 → 적재 기능 범위 결정 순서를 유지한다. AI 키·모델 확장·하네스 논의는 기존처럼 추후로 남긴다.
