# AWS 첫 배포와 GitHub Actions CI/CD

팀 제한 HTTPS 시연 주소를 목표로 한다. GitHub Actions가 검증된 `main`의 소스로 Django·정적 Nginx 이미지를 만들고 ECR로 보낸다. EC2 한 대는 두 이미지의 digest를 받아 Compose로 실행한다. Nginx의 외부 TLS와 영속 PostgreSQL·미디어는 기존 배포 구성으로 관리한다. [Compose·HTTPS 인수와 복원](2026-11-18_공유HTTPS배포와이미지복귀.md)

부트캠프 예제처럼 서버의 최초 환경과 자동 배포 단계를 분리했다. ARTI는 현재 Compose를 그대로 사용하며, GitHub는 OIDC로 임시 권한을 받고 EC2의 SSM 문서를 호출한다. 백엔드·웹 이미지를 이전 digest로 돌릴 수 있고, 사진과 DB 볼륨을 기존 프로젝트에 유지한다. [부트캠프 배포 워크플로](https://github.com/skn29teacher/aws_server/blob/main/.github/workflows/deploy.yml) · [GitHub AWS OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)

## 팀 결정과 비용

- 준억님 AWS 계정의 Free Tier 자격·크레딧을 Billing에서 확인한다. 팀은 총예산 상한과 종료일, 배포·복원 담당, HTTPS에 사용할 도메인 또는 할당받을 서브도메인을 정한다.
- AWS는 자격이 있는 신규 고객에게 가입 시 $100과 추가 과제에 따른 크레딧을 안내한다. 기존·과거 AWS 고객은 신규 고객 혜택 대상에서 제외된다. Free Plan의 서비스 범위, 크레딧 적용과 종료일은 계정별로 확인한다. AWS Budgets에는 예상·실제 사용 알림을 설정하며 종료일에는 운영자가 자원을 점검한다. [Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/) · [AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)
- 처음에는 서울 리전의 x86 EC2 한 대에서 Nginx·Django·PostgreSQL을 실행한다. 모델 실행 서버가 빠진 기존 시험의 2GB 후보를 실제 호스트에서 검증한다. 인스턴스, EBS, 공인 IPv4, ECR 저장량, 분리 백업과 도메인을 비용에 포함한다. AWS 쪽 저사양 수치는 사전 컨테이너 시험 근거다. [W12 용량·비용 검토](W12_저사양용량검증과AWS_Core.md) · [AWS Free Tier](https://aws.amazon.com/free/) · [EC2 요금](https://aws.amazon.com/ec2/pricing/on-demand/)
- 학교·팀이 관리하는 기존 도메인에서 서브도메인을 받을 수 있는지 먼저 확인한다. 기관 할당이나 구매가 확정되면 DNS 변경 담당, 인증서 발급·갱신 담당, 외부 검수 기간을 함께 남긴다.
- 종료일에 백업과 결과를 먼저 인수하고 EC2, 분리된 공인 IP, EBS 스냅샷, ECR 보관 항목을 비용 화면과 대조한다. 시연 후보와 이전 정상 이미지의 digest를 기록해 둔다.

## AWS와 GitHub 준비

1. 서울 리전에 `arti-api`, `arti-web` 두 개의 프라이빗 ECR 저장소를 만든다. 이미지 태그를 immutable로 설정해도 된다. 워크플로는 실행과 재시도별로 고유 태그를 사용하고 배포에는 digest를 넣는다. [ECR 이미지 게시](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html)
2. EC2는 Linux x86_64를 사용한다. 시스템에 Docker Engine·Compose v2.35 이상, AWS CLI v2, SSM Agent 3.3.2746.0 이상, Nginx, curl, Bash와 flock을 준비한다. 호스트 역할로 SSM 관리 노드 권한과 두 ECR 저장소 pull 권한을 부여한다. 접속 허용 범위에 맞춰 HTTPS를 열며, 앱·DB 포트는 배포 Compose가 내부에 둔다. 콘솔에서 SSM 관리 노드가 온라인인지 확인한다. [SSM Agent 환경 변수 요건](https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-troubleshooting.html)
3. IAM에 GitHub OIDC 제공자 `https://token.actions.githubusercontent.com`과 대상 `sts.amazonaws.com`을 등록한다. 신뢰 정책에서 `aud`를 `sts.amazonaws.com`, `sub`를 `repo:2026-2-zolp@343662137/arti@1422562616:environment:arti-staging`으로 제한한다. 2026-10-16 생성된 저장소의 기본 subject 규칙과 GitHub API의 소유자·저장소 ID를 적용한 값이다. GitHub 환경의 허용 배포 브랜치를 `main`으로 설정한다. 환경에 검토자를 지정하면 각 배포가 검토를 기다린다. [GitHub OIDC subject 규칙](https://docs.github.com/en/actions/reference/security/oidc)
4. GitHub 역할의 권한은 아래 표 범위로 제한한다. AWS에서 [SSM 명령 문서](../../ops/aws/ARTI-DeployRelease.json)를 `ARTI-DeployRelease`, 유형 `Command`의 버전 1로 등록한다. 지원되는 SSM Agent에서 세 인자를 환경 변수로 전달한다. 워크플로에 이 문서의 수정 권한을 부여할 필요는 없다. [SSM Run Command 권한](https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command-setting-up.html) · [SSM 문서 플러그인](https://docs.aws.amazon.com/systems-manager/latest/userguide/documents-command-ssm-plugin-reference.html)

| 역할 | 필요한 권한 |
| --- | --- |
| GitHub `arti-staging` | ECR `GetAuthorizationToken` · 지정 두 저장소의 `BatchCheckLayerAvailability`, `InitiateLayerUpload`, `UploadLayerPart`, `CompleteLayerUpload`, `PutImage`, `BatchGetImage` · 지정 EC2와 지정 SSM 문서에 대한 `ssm:SendCommand` · `ssm:GetCommandInvocation`으로 결과 조회 |
| EC2 인스턴스 역할 | `AmazonSSMManagedInstanceCore` · ECR `GetAuthorizationToken` · 지정 두 저장소의 `BatchGetImage`, `GetDownloadUrlForLayer`, `BatchCheckLayerAvailability` |

5. GitHub Actions의 `arti-staging` 환경 변수에 `ARTI_AWS_ROLE_ARN`, `ARTI_AWS_ACCOUNT_ID`, `ARTI_AWS_INSTANCE_ID`, `ARTI_AWS_REGION`을 입력한다. **저장소 변수** `ARTI_AWS_CD_ENABLED`는 준비·검수 뒤에 `true`로 설정한다. 장기 AWS 키와 SSH 개인키는 워크플로 입력에 필요하지 않다.

## 서버 최초 설정

호스트 관리자가 검토한 저장소 복제본에서 아래 파일을 설치한다. Nginx와 HTTPS 연결을 [배포 설정 가이드](2026-11-18_공유HTTPS배포와이미지복귀.md)대로 구성하고 `nginx -t`로 확인한다.

```bash
sudo install -d -m 0700 /opt/arti /opt/arti/bin
sudo install -m 0644 compose.yaml compose.deploy.yaml /opt/arti/
sudo install -m 0755 ops/aws/deploy-release.sh /opt/arti/bin/deploy-release.sh
sudo install -m 0644 scripts/check_release_schema.py /opt/arti/bin/
```

| 서버 파일 | 값 |
| --- | --- |
| `/opt/arti/ecr-registry` | `<계정 ID>.dkr.ecr.ap-northeast-2.amazonaws.com` |
| `/opt/arti/https-origin` | `https://<시연 호스트명>` 한 줄 |
| `/opt/arti/compose.env` | 권한 `0600`. `ARTI_DB_IMAGE`는 PostgreSQL 17 digest. `ARTI_DB_PASSWORD`, `DJANGO_SECRET_KEY`와 필요 시 `ARTI_DEPLOY_HTTP_PORT`를 설정한다. `DJANGO_ALLOWED_HOSTS`는 `<시연 호스트명>,localhost,127.0.0.1,api`를 입력한다. 초기 배포에서는 외부 모델·SMTP·카카오 설정을 비워 둔다. |

정적 Nginx가 열 로컬 포트와 외부 Nginx의 upstream을 맞춘다. HTTPS 인증서는 브라우저에서 신뢰할 수 있어야 한다. 관리자는 승인된 전시 데이터를 별도 인수 절차로 반영한다. W06 실제 도판의 사용 범위가 대기인 동안 외부 검수는 합성 전시로 한다.

## 첫 실행과 복귀

1. 워크플로가 `main`에 들어가고 CI가 통과하면 GitHub Actions에서 **ARTI AWS Release**를 `main`으로 수동 실행한다. 자동 실행은 동일 저장소의 `main` push CI 성공에 연결된다. 두 경로 모두 배포하려는 SHA가 최신 `main`이며 해당 SHA의 CI가 성공했는지 확인한다. 배포는 GitHub 환경과 EC2 잠금으로 직렬화한다. [릴리스 워크플로](../../.github/workflows/aws-release.yml)
2. 새 DB에서는 첫 마이그레이션을 적용한다. 기존 DB에서는 마이그레이션 이력이 같을 때 이미지 전환을 한다. 새 스키마가 필요한 릴리스는 운영자가 백업과 호환성을 확인하고 마이그레이션을 적용한 뒤 다시 실행한다. Compose와 배포 스크립트 변경은 관리자 승인 후 호스트 파일에도 반영한다.
3. 호스트에서 같은 HTTPS 진입점의 인증서, PostgreSQL 준비 응답, 정적 번들, 재설정 응답 보호 헤더와 실제 API·웹 이미지 ID를 확인한다. 성공 시 `state/current`에 커밋과 두 digest가 남는다. 전환 후 검증 실패 시 같은 스키마의 직전 이미지로 복귀하고 Actions는 실패를 표시한다. 이전 이미지와도 DB 이력이 맞지 않으면 복원 담당이 기존 백업과 복귀 기준을 확인한다. [호스트 배포 스크립트](../../ops/aws/deploy-release.sh)
4. 호스트의 HTTPS 확인이 끝나면 승인된 외부 PC에서 고정 주소를 연다. 합성 전시, 영수증 1건·권한 확인, 종료일을 기록하고 실제 배포 결과에 포함한다. 카카오 실연동과 실기기는 이후 지정한 회차에 검수한다.

실행 증거로 Actions 실행 주소, SSM Command ID, 커밋 SHA, 두 이미지 digest, 외부 HTTPS 확인 결과를 남긴다.
