# AWS 첫 배포와 GitHub Actions CI/CD

팀 제한 HTTPS 시연 주소를 목표로 한다. GitHub Actions가 검증된 `main`의 소스로 Django·정적 Nginx 이미지를 만들고 ECR로 보낸다. EC2 한 대는 두 이미지의 digest를 받아 Compose로 실행한다. Nginx의 외부 TLS와 영속 PostgreSQL·미디어는 기존 배포 구성으로 관리한다. [Compose·HTTPS 인수와 복원](2026-11-18_공유HTTPS배포와이미지복귀.md)

[Route 53 요금](https://aws.amazon.com/route53/pricing/) · [Let's Encrypt IP 인증서와 Certbot](https://letsencrypt.org/2026/03/11/shorter-certs-certbot) · [CloudFront 기본 HTTPS](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-https-viewers-to-cloudfront.html) · [CloudFront 플랜](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html) · [카카오 리다이렉트 URI](https://developers.kakao.com/docs/ko/kakaologin/prerequisite)

학교·팀 주소의 DNS 담당이 시연 전에 A 레코드를 연결할 수 있으면 해당 주소를 사용한다. 같은 URL을 제출 후에도 유지해야 하고 서브도메인을 받을 수 없으면 팀 소유 도메인을 등록한다. 제출 일정이 먼저 오면 고정 IP로 합성 시연을 준비한다.

IP 경로에서는 Certbot 5.4 이상으로 HTTP-01 webroot를 사용한다. Nginx의 80번 포트에서 ACME 경로를 제공하고, 시험 발급 → 공인 발급 → 443의 기본 TLS 서버에 인증서 적용 → 자동 갱신과 `nginx -t`·reload 훅 → 외부 PC 인증서 확인 순서로 검증한다. 배포 호스트와 Django 허용 호스트에 동일한 IPv4를 설정한다. 호스트명 방식에서는 DNS 권한과 방화벽 범위에 맞춰 HTTP-01 또는 DNS-01을 선택한다. [Certbot IP webroot와 갱신](https://letsencrypt.org/2026/03/11/shorter-certs-certbot) · [ACME 검증 유형](https://letsencrypt.org/docs/challenge-types/)

## 첫 배포 전에 준억님이 확인할 순서

1. **AWS 계정과 Billing** · 개인 계정의 MFA를 확인하고, Billing → Credits에서 사용 가능한 잔액·만료일과 Free Tier 적용 여부를 확인한다. 총예산, 운영 종료일, 알림 수신자, 배포·복원 담당을 정한다. 승인된 비용 기준으로 Billing → Budgets에서 Actual 50·80·100%, Forecast 100% 알림을 설정한다. [Free Tier 자격](https://aws.amazon.com/free/free-tier-faqs/) · [예산 만들기](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-create.html)
2. **주소 선택** · 학교·팀 DNS 담당의 연결 가능 일정을 먼저 확인한다. 신규 도메인 방식은 Route 53 → Registered domains에서 이름·최초 등록가·갱신가를 확인한다. 구매 전에 고정 주소와 관리 담당을 정한다. [Route 53 도메인 등록](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/domain-register.html)
3. **서울 리전과 호스트 역할** · 승인 뒤 서울에서 ECR → Private repositories에 `arti-api`·`arti-web`을 만든다. IAM → Roles에서 EC2 호스트 역할에 SSM 관리 노드와 두 ECR 저장소의 pull 권한을 연결한다. S3 백업을 쓸 때는 서울의 비공개 버킷과 별도 백업 경로를 만들고 해당 경로에만 접근을 부여한다. 현재와 이전 릴리스 digest가 ECR에서 함께 유지되는지 확인한다. [권한 상세](#aws와-github-준비)
4. **EC2와 Elastic IP** · EC2 → Launch instances에서 Linux x86_64, `t3a.small`, 온디맨드, Standard CPU 크레딧, 암호화 gp3 20 GiB, IMDSv2 필수, 앞 단계의 IAM 역할을 선택한다. 외부 HTTPS와 인증서 발급에 필요한 포트만 허용하고 SSH·API·DB 인바운드는 열지 않는다. 인터넷 게이트웨이 경로와 outbound HTTPS가 있는 퍼블릭 서브넷을 사용한다. EC2 → Elastic IPs에서 주소 하나를 연결하고 도메인 방식이면 A 레코드를 지정한다. Systems Manager → Session Manager에서 관리 노드가 온라인인지 확인한다. [SSM 연결 요건](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-create-vpc.html)
5. **SSM 배포와 GitHub 연결** · Systems Manager → Documents에 `ARTI-DeployRelease`를 등록한다. IAM에서 GitHub OIDC 배포 역할을 지정 저장소·환경·EC2·문서로 제한한다. GitHub Settings → Environments에서 `arti-staging`, `main` 조건과 환경 변수를 채운다. 호스트에서 [서버 최초 설정](#서버-최초-설정)을 적용하고 인증서와 `nginx -t`를 확인한다. [GitHub OIDC의 환경 및 subject](https://docs.github.com/en/actions/reference/security/oidc)
6. **승인된 첫 실행** · AWS 준비 변경이 `main`에 반영되고 해당 SHA의 CI와 호스트 준비가 확인되면 `ARTI_AWS_CD_ENABLED`를 켜고 **ARTI AWS Release**를 수동 실행한다. 다음 승인 릴리스에서 자동 경로를 확인한다. 합성 전시와 합성 계정으로 [배포 후 인수 체크리스트](#배포-후-인수-체크리스트)를 마친 다음 실제 자료·계정의 운영 범위를 확정한다.

## AWS Core로 지원할 수 있는 범위

Codex의 현재 플러그인 검색에는 AWS Data Analytics가 반환됐다. AWS 공식 **AWS Core**는 별도 플러그인으로 제공된다. AWS MCP Server를 Codex에 설치하고 준억님이 AWS CLI의 SSO·임시 자격으로 인증하면, 부여된 권한 범위에서 서울 리전의 EC2·ECR·SSM 구성을 조회하고 변경 계획을 검토할 수 있다. 리소스 생성·수정은 그 목적의 IAM 권한과 실행 승인이 있을 때 가능하다. 읽기 전용 역할로 먼저 연결해 계정·대상 리전을 확인한다. 계정 로그인·MFA, 결제·예산 결정, 도메인 소유 확인은 계정 담당이 한다. AWS CLI v2만으로도 같은 구성안을 검토하고 승인된 작업을 실행할 수 있다. [AWS Core 플러그인](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/plugins.html) · [Codex용 AWS MCP 설정](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/getting-started-aws-mcp-server.html) · [MCP의 IAM 권한](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/security_iam_service-with-iam.html)

## AWS와 GitHub 준비

1. 서울 리전에 `arti-api`, `arti-web` 두 개의 프라이빗 ECR 저장소를 만든다. 이미지 태그를 immutable로 설정해도 된다. 워크플로는 실행과 재시도별로 고유 태그를 사용하고 배포에는 digest를 넣는다. [ECR 이미지 게시](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html)
2. EC2는 Linux x86_64를 사용한다. 시스템에 Docker Engine·Compose v2.35 이상, AWS CLI v2, SSM Agent 3.3.2746.0 이상, Nginx, curl, Bash와 flock을 준비한다. 호스트 역할로 SSM 관리 노드 권한과 두 ECR 저장소 pull 권한을 부여한다. 접속 허용 범위에 맞춰 HTTPS를 열며, 앱·DB 포트는 배포 Compose가 내부에 둔다. 콘솔에서 SSM 관리 노드가 온라인인지 확인한다. [SSM Agent 환경 변수 요건](https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-troubleshooting.html)
3. IAM에 GitHub OIDC 제공자 `https://token.actions.githubusercontent.com`과 대상 `sts.amazonaws.com`을 등록한다. 신뢰 정책에서 `aud`를 `sts.amazonaws.com`, `sub`를 `repo:2026-2-zolp@343662137/arti@1422562616:environment:arti-staging`으로 제한한다. 2026-10-16 생성된 저장소의 기본 subject 규칙과 GitHub API의 소유자·저장소 ID를 적용한 값이다. GitHub 환경의 허용 배포 브랜치를 `main`으로 설정한다. 환경에 검토자를 지정하면 각 배포가 검토를 기다린다. [GitHub OIDC subject 규칙](https://docs.github.com/en/actions/reference/security/oidc)
4. GitHub 역할의 권한은 아래 표 범위로 제한한다. AWS에서 [SSM 명령 문서](../../ops/aws/ARTI-DeployRelease.json)를 `ARTI-DeployRelease`, 유형 `Command`의 버전 1로 등록한다. 지원되는 SSM Agent에서 세 인자를 환경 변수로 전달한다. 워크플로에 이 문서의 수정 권한을 부여할 필요는 없다. | GitHub `arti-staging` | ECR `GetAuthorizationToken` · 지정 두 저장소의 `BatchCheckLayerAvailability`, `InitiateLayerUpload`, `UploadLayerPart`, `CompleteLayerUpload`, `PutImage`, `BatchGetImage` · 지정 EC2와 지정 SSM 문서에 대한 `ssm:SendCommand` · `ssm:GetCommandInvocation`으로 결과 조회 |

5. GitHub Actions의 `arti-staging` 환경 변수에 `ARTI_AWS_ROLE_ARN`, `ARTI_AWS_ACCOUNT_ID`, `ARTI_AWS_INSTANCE_ID`, `ARTI_AWS_REGION`을 입력한다. **저장소 변수** `ARTI_AWS_CD_ENABLED`는 준비·검수 뒤에 `true`로 설정한다. 장기 AWS 키와 SSH 개인키는 워크플로 입력에 필요하지 않다.

## 서버 최초 설정

호스트 관리자가 검토한 저장소 복제본에서 아래 파일을 설치한다. Nginx와 HTTPS 연결을 [배포 설정 가이드](2026-11-18_공유HTTPS배포와이미지복귀.md)대로 구성하고 `nginx -t`로 확인한다.

```bash
sudo install -d -m 0700 /opt/arti /opt/arti/bin
sudo install -m 0644 compose.yaml compose.deploy.yaml /opt/arti/
sudo install -m 0755 ops/aws/deploy-release.sh /opt/arti/bin/deploy-release.sh
sudo install -m 0644 scripts/check_release_schema.py /opt/arti/bin/
```

| 서버 파일 | 값 |
| --- | --- |
| `/opt/arti/ecr-registry` | `<계정 ID>.dkr.ecr.ap-northeast-2.amazonaws.com` |
| `/opt/arti/https-origin` | `https://<시연 호스트명>` 또는 `https://<고정 IPv4>` 한 줄 |
| `/opt/arti/compose.env` | 권한 `0600`. `ARTI_DB_IMAGE`는 PostgreSQL 17 digest. `ARTI_DB_PASSWORD`, `DJANGO_SECRET_KEY`와 필요 시 `ARTI_DEPLOY_HTTP_PORT`를 설정한다. `DJANGO_ALLOWED_HOSTS`는 `<시연 호스트명>,localhost,127.0.0.1,api`를 입력한다. 초기 배포에서는 외부 모델·SMTP·카카오 설정을 비워 둔다. |

정적 Nginx가 열 로컬 포트와 외부 Nginx의 upstream을 맞춘다. HTTPS 인증서는 브라우저에서 신뢰할 수 있어야 한다. 관리자는 승인된 전시 데이터를 별도 인수 절차로 반영한다. W06 실제 도판의 사용 범위가 대기인 동안 외부 검수는 합성 전시로 한다.

배포 전에 호스트의 Nginx HTTPS를 기동한다. 자동 배포는 이미지 다운로드에 앞서 고정 호스트명의 인증서와 포트가 응답하는지 확인한다. 처음에는 웹 컨테이너가 없어 프록시 오류가 반환될 수 있다. 배포 직후에는 준비 API·정적 번들·재설정 보호 헤더를 별도로 검사한다.

## 첫 실행과 복귀

1. 워크플로가 `main`에 들어가고 CI가 통과하면 GitHub Actions에서 **ARTI AWS Release**를 `main`으로 수동 실행한다. 자동 실행은 동일 저장소의 `main` push CI 성공에 연결된다. 두 경로 모두 배포하려는 SHA가 최신 `main`이며 해당 SHA의 CI가 성공했는지 확인한다. 배포는 GitHub 환경과 EC2 잠금으로 직렬화한다. [릴리스 워크플로](../../.github/workflows/aws-release.yml)
2. 새 DB에서는 첫 마이그레이션을 적용한다. 기존 DB에서는 마이그레이션 이력이 같을 때 이미지 전환을 한다. 새 스키마가 필요한 릴리스는 운영자가 백업과 호환성을 확인하고 마이그레이션을 적용한 뒤 다시 실행한다. Compose와 배포 스크립트 변경은 관리자 승인 후 호스트 파일에도 반영한다.
   - API·웹 이미지의 OCI 커밋 라벨이 승인한 SHA와 일치해야 DB를 시작하고 스키마를 확인한다. 복귀할 때는 로컬에 남아 있는 이전 이미지 두 개를 먼저 확인한다. 이전 이미지가 로컬에 없으면 ECR에서 해당 digest를 가져온다. 시연 기간에는 이전 정상 이미지와 ECR digest를 보존한다.
3. 호스트에서 같은 HTTPS 진입점의 인증서, PostgreSQL 준비 응답, 정적 번들, 재설정 응답 보호 헤더와 실제 API·웹 이미지 ID를 확인한다. HTTPS의 첫 HTML은 현재 웹 컨테이너의 `index.html`과 같아야 한다. 프록시가 이전 빌드에 연결돼 200을 반환하는 경우도 전환 실패로 처리한다. 성공 시 `state/current`에 커밋과 두 digest가 남는다. 전환 후 검증 실패 시 같은 스키마의 직전 이미지로 복귀하고 Actions는 실패를 표시한다. 이전 이미지와도 DB 이력이 맞지 않으면 복원 담당이 기존 백업과 복귀 기준을 확인한다. [호스트 배포 스크립트](../../ops/aws/deploy-release.sh)
4. 새 DB의 첫 배포가 성공하면 호스트 관리자가 아래 명령으로 관리자 한 명을 만든다. 비밀번호는 명령에서 띄우는 프롬프트에 입력한다. 고정 HTTPS의 `/admin/login`에서 로그인해 팀 검수용 합성 자료를 반입한다. 운영 Compose에서는 시험 픽스처 적재를 차단한다. [합성 자료 반입 순서](#빈-운영형-환경에서-합성-전시-반입)
5. 승인된 외부 PC에서 그 전시를 연다. 회원 영수증 1건과 접근 권한, 비회원 저장 요청 0건, 종료일을 기록하고 실제 배포 결과에 포함한다. [배포 후 인수 체크리스트](#배포-후-인수-체크리스트)

```bash
cd /opt/arti
mapfile -t release < state/current
export ARTI_API_IMAGE="${release[1]}" ARTI_WEB_IMAGE="${release[2]}"
docker compose --env-file compose.env -p arti-shared -f compose.yaml -f compose.deploy.yaml \
  exec api python manage.py bootstrap_admin --login-id arti-operator --name 'ARTI 운영 담당'
```

실행 증거로 Actions 실행 주소, SSM Command ID, 커밋 SHA, 두 이미지 digest, 외부 HTTPS 확인 결과를 남긴다.

### 최초 배포가 중간에 끊긴 경우

- 호스트의 `state/first-pending`에서 커밋 SHA, API digest, 웹 digest 순서로 확인하고 Actions 요약의 후보 조합과 대조한다. 새 DB에는 비어 있음을 확인한 직후, 첫 마이그레이션을 시작하기 전에 후보를 기록한다. 스키마가 이미 일치하면 API·웹 기동 전에 기록한다.
- 배포 담당은 기록에 있는 조합으로 SSM 명령을 다시 실행한다. Actions의 일반 재실행은 이미지를 다시 빌드하므로 기존 digest가 필요한 재개에는 기록에 있는 조합을 사용한다. 호스트에 해당 이미지가 있으면 로컬에서 이어가고 마이그레이션 이력이 일치하면 그대로 기동한다. HTTPS 확인이 완료되면 `state/current`를 기록한다.
- 마이그레이션이 진행 중에 끊겨 테이블은 생겼지만 이력이 일치하지 않으면 배포가 멈춘다. 복원 담당이 DB 상태와 백업을 확인한 뒤 기존 이관 절차로 복구하고 같은 후보로 다시 실행한다.
- API·웹이 남아 있는데 진행 기록이나 활성 릴리스 기록이 없으면, 해당 Compose 프로젝트와 볼륨을 운영 인수 절차로 먼저 확인한다. 첫 배포의 다른 후보를 시작하려는 경우에는 이전 시도의 상태를 먼저 확인한다.
