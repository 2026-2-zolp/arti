## 발표에서 말할 내용

> ARTI는 처음 전시를 보는 사람이 취향에 맞는 작품을 고르고, 작품 앞에서 관찰을 이어가도록 돕습니다. 시연에서는 전시와 별도의 취향 조사에서 작품 다섯 쌍을 비교하고, 30분 관람을 선택해 추천 작품 세 점과 지도 순서를 봅니다. 관람가이드에서 질문을 보내면 도슨트가 지금 보고 있는 작품과 질문을 이어받습니다. 답변이 실패해도 질문이 남아 다시 보낼 수 있고, 관람을 계속해 아트 영수증까지 볼 수 있습니다.
>
> 합성 전시를 실제 Django·PostgreSQL로 운영하고 도슨트의 성공과 장애 응답은 모의 제공자로 재현했습니다. DB와 이미지 파일을 새 환경에 복원한 뒤에도 같은 영수증이 열렸고, 같은 관람을 다시 보내도 기록은 한 건이었습니다. 실제 유영국 작품의 설명·태그·배치와 현장 기기 검증은 인수 결과를 받아 최종본에 추가할 예정입니다.

시연 순서는 **취향 5쌍 → V2 취향 미리 확인 → 30분 추천·지도 → 관람가이드 질문 → 모의 502와 같은 질문의 재시도 200 → 다음 작품 → 영수증과 PNG**다. 운영형 원본에서 모델을 비활성화한 경우에는 503 후 같은 작품으로 돌아와 완주한다. 회원 저장 한 건과 비회원 저장 요청 0건을 확인한 뒤 DB·미디어를 복원한다. 회원 본인과 관리자가 동일 ID를 조회하고, 다른 회원과 비회원은 각각 403과 401을 받는다. ## 완료보고서 기술 검증 초안

ARTI는 작품 다섯 쌍에서 수집한 선택을 바탕으로 취향을 확인하고, 선택한 관람 시간에 맞춰 작품과 관람 순서를 제안한다. 관람객은 작품 해설과 관찰 질문을 보고, 선택적으로 도슨트와 대화하거나 반응을 남긴다. 회원은 지난 관람을 마이페이지에서 영수증으로 다시 열 수 있다.

- **관람 검증** · 취향 V2 합성 환경에서 후보가 충분한 3·5·7점과 부족한 2·4·6점 경로를 검수했다. 추천 목록·지도·감상·영수증의 순서가 일치했다. 부분 추천 회원의 영수증은 새로고침 뒤에도 같은 관람 ID로 한 건이었고 비회원 저장 요청은 0건이었다. 정상 경로의 PC Chrome에서는 영수증 PNG를 내려받았다. [부분 추천 작업기록](../작업기록/2026-11-16_세션만료와관람중변경Chrome회귀.md#1116-v2-추천-후보-부족과-관람-완료)
- **저장 V2 취향 검증** · 조사풀이 개정된 뒤에도 회원이 확인해 둔 동점 근거를 사용했다. 이번 관람에만 적용한 선택은 계정에 저장하지 않았다. 저장 응답 유실 뒤 같은 요청을 보내도 프로필 버전은 한 번만 증가했고, 다른 탭이 먼저 바꿨을 때는 409와 최신값 재조회로 복구했다. 두 경로 모두 기존 영수증을 유지했다. [저장 V2 Chrome](../작업기록/2026-11-16_저장V2취향재사용Chrome.md)
- **도슨트 복구** · PC Chrome에서 같은 작품을 다른 관람 ID로 연 두 탭의 초안·지연 답변·이력이 각각 유지됐다. 모의 제공자의 502 이후 같은 탭에서 같은 질문·이력·근거 버전으로 재시도해 200을 받았다. [도슨트 하네스 기록](../작업기록/2026-11-15_AI도슨트평가하네스.md#1116-두-탭에서-같은-작품을-연-경우)
- **영수증 해석 복구** · 격리 PostgreSQL과 모의 제공자에서 502 중 기존 해석이 유지됐고, 같은 요청을 다시 보내자 새 해석을 새로고침 후에도 볼 수 있었다. 회원 영수증은 같은 ID의 한 건에서 해석만 바뀌었고 비회원은 관람 저장 요청이 0건이었다. 다른 회원으로 전환한 뒤에는 이전 응답이 화면과 탭 캐시에 표시되지 않았다. [영수증 해석 작업기록](../작업기록/2026-11-16_영수증해석502통합회귀.md)
- **관리자 검증** · 전시를 등록·공개하고 도면 교체 후 입구와 작품 좌표를 다시 저장했다. 새 관람의 추천 순서는 A→B→C에서 C→B→A로 바뀌었고, 관람자 지도도 새 좌표를 표시했다. 이미지 주소를 비워 두면 새 작품 등록이 실패하는 결함을 수정했다. [관리자 검수 기록](../작업기록/2026-11-15_관리자전시등록과도면반영.md)
- **관리자 분석 복구** · 다른 탭에서 작품 원문과 확정 요약을 저장하는 동안 이전 분석 결과를 지연시켰다. Django는 이전 결과를 409로 거절했고 두 번째 탭의 최신 저장값이 유지됐다. 충돌 뒤 **최신 작품 다시 불러오기**를 제공하도록 고쳤다. 취소하면 첫 탭의 미저장 입력을 유지하고, 다시 불러온 뒤 분석하면 새 원문을 사용하며 이미 확정된 요약은 보존한다. [관리자 분석 작업기록](../작업기록/2026-11-16_관리자분석중작품변경Chrome.md)
- **운영과 복구** · 로컬 Nginx의 정적 화면과 Django API 연결, 빈 PostgreSQL의 마이그레이션 8개, 별도 볼륨 복원을 확인했다. 후보의 마이그레이션 실패 중에도 원본 조회가 유지됐다. 후보 API를 새 IP로 재생성하자 같은 Nginx에서 준비 응답이 복구됐고, 복원 회원·관리자 영수증과 미디어 두 파일의 SHA-256이 일치했다. 복원 환경에서 영수증에 대한 다른 회원의 접근은 403, 비회원 접근은 401을 반환했다. [Nginx 복구 기록](../작업기록/2026-11-16_Compose기동실패와Nginx복구.md) · [복원 후 계정별 검수](2026-11-11_main_시연복구체크리스트.md#복원-후-영수증-접근-권한-확인)
- **카카오 모의 연결과 HTTPS 로그** · 기존 이메일 계정에서 연결을 취소해도 세션이 유지됐고, 연결 후 재로그인에서는 같은 회원·저장 취향·영수증이 열렸다. 오래된 연결 완료는 400이었다. 별도 루프백 Nginx 시험에서 정상 콜백은 302였고 장애 콜백은 502에 `no-store`·`no-referrer`를 반환했다. 콜백 `code`·`state`는 Nginx·Gunicorn 로그에서 검출되지 않았고, 일반 API 장애는 로그에 남았다. [카카오 Chrome](../작업기록/2026-11-16_카카오모의연동Chrome.md) · [Nginx HTTPS 검수](../작업기록/2026-11-16_NginxHTTPS카카오콜백로그.md) · [운영 인수 순서](2026-11-11_main_시연복구체크리스트.md#운영-인수--nginx-https-콜백과-로그)
- **최종 확인 범위** · 실제 유영국 작품은 승인된 도판·문안·좌표와 도슨트 응답을 확인한다. 현장 시연 주소, 두 기기의 관람과 HTTPS PNG 공유, 대상 배포 환경 검증은 각각 시험 결과를 받아 최종본에 반영한다.
