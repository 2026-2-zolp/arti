# CLIP·mDeBERTa 로컬 운영 기준

2026-11-09. Django 기본 API와 분리된 분석 서비스의 로컬 운영 기준이다. AWS/고가용성·분산 대기열을 구축한 문서가 아니다. 새 Django는 분석 /analyze만 사용하고 GPT 텍스트·도슨트는 기존 OpenAI 호환 경로를 사용한다.

## 기동과 상태 확인

ai-service 가상환경과 모델 파일을 준비한 뒤 ai-service 폴더에서 실행한다. 현재 검증한 운영 단위는 uvicorn app.main:app --host 127.0.0.1 --port 8001 --workers 1 이다. ARTI_WRITER_ENABLED=false로 Kanana 작성 기능을 끄고, 모델명/파일 경로와 다운로드 방식을 먼저 정한다. 최초 다운로드는 로딩 시간과 구분한다. 이번 실측은 기존 고정 revision 파일·HF_HUB_OFFLINE=1·CPU4스레드였다.

- /health: 프로세스 응답200. modelsLoaded, modelState(not_loaded/loading/failed/ready), analysisBusy, busySeconds를 본다.200만으로 모델 준비/품질을 판정하지 않는다.
- /ready: 모델이 준비됐을 때200, 아직 준비되지 않으면503/Retry-After5다. 준비된 모델이 추론 중인 경우에도200이며 유휴 슬롯 보장이 아니다.
- 기본 PRELOAD=true는 시작 시 한 번 백그라운드 로딩한다. PRELOAD=false면 첫 /analyze가 로딩을 시작하고503을 반환한다. /ready 조회만으로 로딩을 시작하지 않는다.
- 로딩 실패는 failed로 표시하고 다음 요청의 재로딩까지 최소5초를 둔다. 로딩 중 다른 요청은 추가 로더를 만들거나 기다리지 않고503을 받는다.

Django의 /api/ready는 기존 API/DB 준비 상태로 모델 readiness와 다르다. Django ARTI_MODEL_SERVICE_URL은 접근 가능한 내부 분석 서비스 주소로 설정한다. Compose의 localhost는 호스트가 아니므로 호스트 서비스라면 http://host.docker.internal:8001 등의 실제 접근 경로를 선택한다. 일반 arti-dev의 설정/컨테이너는 이번 작업에서 재생성하지 않았다.

## 요청·장애 정책

분석은 프로세스당1건이다. 추론 슬롯이 차 있으면429/Retry-After1로 알리며 모델 작업을 대기열에 쌓지 않는다. 모델 상태/추론 lock은 프로세스 로컬이므로 workers를 늘리면 메모리·동시 추론도 늘어난다. 여러 모델 프로세스/호스트의 전역 제한을 구현했다고 주장하지 않는다. Django 관리자 분석은 기존 PostgreSQL advisory lock으로 요청을 제한한다.

Django는 같은 관리자 요청의 태그·감정에 성공 결과뿐 아니라 실패도 공유한다. 최초 호출이 timeout/503/429이면 다른 분석 필드를 위해 즉시 같은 호출을 반복하지 않는다. 다음 사용자 요청은 새 캐시로 시도할 수 있다. GPT 요약·가이드 경계와 기존 부분 성공 정책은 유지한다. 일부 텍스트 생성만 성공하면 그 부분은 기존 계약대로 suggested 저장될 수 있으므로 ‘모든 필드 전체 원자성’으로 설명하지 않는다.

30초는 분석 서비스 HTTP 한 번의 timeout이며, GPT 요약·가이드 등을 포함한 관리자 분석 전체의 총기한이 아니다. Django의 모델 HTTP timeout은30초이며, 테스트는 지연 주입에서 .05초로 단축해 같은 실패 경로를 확인했다. timeout 뒤 늦은 응답을 백그라운드 DB 작업으로 적용하지 않는다. 원문/버전이 그 사이 바뀌면 성공한 옛 응답도409로 거절한다. 모델 생성으로 confirmed/approved를 자동 설정하지 않는다.

caller가 timeout/연결을 끊어도 동기 native 추론이 즉시 취소되지는 않는다. 실제 계산이 끝날 때까지 모델 슬롯을 유지하고 그동안429를 반환한다. 다른 native 계산을 겹쳐 실행해 메모리를 늘리지 않는다. busySeconds가30초를 넘기는 등 지속 지연은 조사 대상이며 자동 강제취소/워치독 재시작 기능은 없다. native 계산이 멈춘 경우 운영자가 상태와 요청을 확인해 전용 모델 프로세스를 재시작해야 한다.

서비스가 중단되면 연결 실패503, 진행 중 연결이 끊기거나 응답이 잘리면 안전한502 등 명시 오류로 처리한다. 원문 앞부분·가짜 점수·GPT 태그로 성공을 대신하지 않는다. 재기동 후 /ready를 확인하고 명시 재시도한다. 기존 Django DB·미디어 볼륨을 삭제/초기화하지 않는다.

분석 서비스는 내부 주소로만 접근하게 운영한다. 애플리케이션 단일 추론 슬롯은 역방향 프록시/연결 수/요청 크기·인증 같은 배포 보호를 대체하지 않는다. 현재 요청 모델의 이미지/설명 제한은 유지했으며 큰 병렬 입력·AWS 프록시/다중 worker 수용량은 W12/W08 후속으로 확인한다. 레거시 /write를 켰을 때의 동시 자원 보호는 이번 분석 슬롯 범위가 아니므로 새 운영에서는 비활성으로 둔다.

[실제 검증 근거](../execution-plan/2026-11-07/records/W07-preparation/model-operations-2026-11-09/README.md). 운영 안정성 통과와 유영국 태그 정확도·팀원 검수·G5는 별도다.


## TP1a 점수 출처 전달 (2026-11-11)

분석 응답에 선택적 `tagEvidence`가 추가됐다. 구형 서비스의 필드 부재/null은 Django가 허용한다. 존재하는 근거는 실제 전송 이미지 SHA256·점수 hash·모델 ID/revision·signature/envelope hash·고정 정의를 검사하며 잘못되면502다. 이 hash는 서버 승인/사용자 인증 서명이 아니라 전달 무결성 검사다. 허용 signature 판정·DB 저장·동점 사용은 TP1b/TP2의 후속이다.

출처를 게시하려면 CLIP 모델명에 HF repo ID를 사용하고 FastAPI 프로세스의 `ARTI_CLIP_REVISION`에 확인한40자리 commit SHA를 명시해야 한다. 모델/processor가 같은 고정 cache snapshot에서 읽히고 로딩 전후 artifact 파일 hash가 같아야 한다. 누락된 tokenizer/processor·여러 weight 형식·로딩 중 변경·runtime 버전 미확인은 근거를 비워 둔다. 임의 로컬 폴더명이나 `main`을 commit 출처로 추정하지 않는다.

근거 조회 자체는 `try_to_load_from_cache`만 쓰고 다운로드하지 않는다. 불완전 cache에서는 기존 from_pretrained 로딩 경로를 유지하며,그 경로는 기존 운영 설정에 따라 다운로드할 수 있다. 테스트/격리 실행은 HF_HUB_OFFLINE/TRANSFORMERS_OFFLINE로 막는다. 처음 다운로드로 cache가 완성돼도 그 요청에서 출처를 추정하지 않고 다음의 명시 재기동/확인 전까지 null이다. 현재 일반 프로세스 env·모델·컨테이너를 이번 작업에서 재설정하지 않았다.

요청의 base64 원본 바이트를 디코드하면서 SHA를 계산한다. 점수는 그 요청에 복사한 실제 tag_thresholds와 결합한다. 텍스트만 분석하거나 외부 URL로 가져온 이미지·출처 없는 scorer는 기존 점수를 반환하되 tagEvidence=null이다. 분석 계산/보정값·태그 어휘는 바꾸지 않았다. 모델 artifact hash는 로딩 때만 계산하고,응답에 cache 경로나 원본 입력은 넣지 않는다. 실행 파일을 핫패치해서 계속 쓰지 않고 코드/설정 변경은 명시 재기동 대상으로 다룬다.

현재 Django 제공자는 검증된 새근거를 **아직 점수/감정 저장값에 포함하지 않는다**. 특히 감정 analysis JSON에 우회 저장하지 않도록 제외했다. 모델/DB 필드·migration·관리자 확정·조사풀 공개를 추가한 단계가 아니다. 다음 TP1b에서 score_revision/evidence와의 원자 저장/기존값 보호를 구현한다.

검수 기준과 실제 결과는 [TP1a 기록](../execution-plan/2026-11-07/records/taste-tie-implementation-results-2026-11-11/TP1a/README.md)을 따른다. 이 단계의 fake 로딩/전달 성공은 실제 cached 모델·태그 품질·사람 검수 통과와 구분한다.

## TP1b 점수 출처 저장 (2026-11-11)

위 TP1a의 미저장 경계 다음으로, `0003_tag_score_evidence`가 Artwork에 nullable `tag_score_evidence`와 기본 0인 `tag_score_revision`을 추가한다. 기존 행·점수·승인·계정/관람 snapshot·조사풀을 채우거나 활성화하는 data migration은 없다. 이번 적용·시험은 격리 PostgreSQL에 한정하며 일반 `arti-dev` DB와 API 컨테이너는 그대로 둔다. 일반 환경 반영은 별도 작업으로 진행해야 한다.

태그 분석 성공 시 점수·근거·revision 증가를 같은 행 잠금/트랜잭션에서 저장한다. 근거는 TP1a envelope 8필드에 서버가 `sourceVersion`과 `inputImageFile`을 덧붙인다. `evidenceSha256`은 원래 모델 envelope만의 checksum이며 이 두 서버 필드는 그 모델 checksum 대상이 아니다. 서버가 입력 version을 확인한 뒤 바인딩하며 클라이언트 편집값은 받지 않는다. 파일 token은 내부 저장용이고 공개/관리자 DTO에 새 근거 필드를 추가하지 않았다.

새 분석은 항상 suggested이며 사람 confirm과 signature 허용 판정은 별개다. 구형 응답의 근거 부재/null도 기존 점수 동작을 유지하면서 revision을 증가시키고 근거를 null로 저장한다. 예전 근거를 새 점수에 남기거나 추정해서 채우지 않는다. 실패한 tag는 세값을 유지하며 다른 종류의 독립 부분 성공 정책은 유지한다. 전체 예산 초과는 앞서 받은 결과까지 저장하지 않는다.

분석 네트워크 호출은 저장 transaction 밖에서 한다. 저장 직전 version을 재확인하고 해당 transaction의 lock_timeout만 2초로 제한한다. 잠금 대기 초과는 전체 rollback 후 retryable 503 `TEMPORARY_UNAVAILABLE`, 먼저 저장된 수정과의 충돌은 409다. 자동 재시도/중복 저장은 하지 않으며 사용자가 같은 입력으로 다시 시도할 수 있다. 저장 후 commit 직전에도 전체 예산을 재확인한다.

원문·이미지 변경 후에는 과거 근거를 그대로 보존하지만 tag 확정 여부·sourceVersion·파일 token이 현재 입력과 일치해야 `current_evidence`가 반환한다. 이는 TP2의 추가 승인 signature/풀·정책 검증 전 내부 읽기 경계이며 동점 정렬을 켠 것이 아니다. 같은 파일 경로의 수동 덮어쓰기는 허용하지 않고 재업로드/재인수한다. 공개 GET에 파일 재해싱이나 모델 호출은 추가하지 않는다.

인수 결과와 한계는 [TP1b 기록](../execution-plan/2026-11-07/records/taste-tie-implementation-results-2026-11-11/TP1b/README.md)에 누적한다. 일반 DB 역이관은 하지 않고 후속 배포에서도 additive 필드는 보존한다.
