# 공유 HTTPS 배포와 이전 이미지 복귀

배포는 `compose.yaml`과 `compose.deploy.yaml`을 사용한다. Django와 PostgreSQL에는 호스트 포트를 열지 않는다. 정적 Nginx만 호스트 루프백 포트를 열고, 같은 호스트의 HTTPS 프록시가 해당 포트로 연결한다. 프론트와 `/api/`는 하나의 HTTPS 출처를 사용한다. 팀이 관리형 TLS 진입점을 선택하면 전달 방식과 접근 범위를 그 환경에서 확정한다. [배포용 Compose](../../compose.deploy.yaml) · [HTTPS Nginx 설정](../../ops/nginx/arti-https.conf.template)

## 팀이 정할 값

| 질문 | 정할 값과 설정 | 담당 |
| --- | --- | --- |
| 어디에 열까요? | 고정 `https://<호스트>`, 사용할 서버, 접근 가능한 팀원과 사용 기간. `DJANGO_ALLOWED_HOSTS`에는 호스트명과 내부 헬스체크 이름을 넣고 스킴·포트는 뺀다. | 서비스 운영 담당과 준억 |
| 누가 DNS와 인증서를 관리할까요? | DNS 변경 권한, TLS 종료 지점, 인증서·키 파일 경로, 자동 갱신과 갱신 후 설정 재적용 담당. 호스트 Nginx를 쓰면 `ARTI_DEPLOY_HTTP_PORT`와 프록시의 로컬 목적지 포트를 맞춘다. | 인프라 담당 |
| 어떤 이미지를 배포하고 복귀할까요? | 배포 SHA와 `ARTI_API_IMAGE`, `ARTI_WEB_IMAGE`, `ARTI_DB_IMAGE`를 레지스트리 digest로 기록한다. 이전 정상 API·웹 digest 두 개와 저장소 접근 권한을 함께 남긴다. | 배포 담당 |
| 누가 데이터를 보호하고 복귀를 결정할까요? | Compose 프로젝트 이름, DB와 미디어 볼륨, 백업 저장 위치·보유 기간, 복구 시간과 허용할 데이터 손실 범위. `ARTI_DB_PASSWORD`는 해당 DB의 비밀번호, `DJANGO_SECRET_KEY`는 서버 전용 값을 같은 배포 환경에 유지한다. | 백업·복귀 담당 |
| 어떤 기능을 먼저 켤까요? | 사용할 전시·자료 권리, V2 사용 여부와 조사풀 승인 해시. 메일을 운영에 포함하면 `ARTI_PASSWORD_RESET_ORIGIN`, `ARTI_PASSWORD_RESET_FROM`, SMTP 발신 설정과 담당도 확정한다. | 준억, 자료 담당, 계정 운영 담당 |

실제 값은 서버의 Git 제외 환경 파일이나 비밀 저장소에 입력한다. 공유할 때는 변수 이름과 담당만 적는다. 카카오 초기값은 공란이며, 실제 연동과 실기기 확인은 후속으로 둔다. [메일 설정과 발송 검수](비밀번호재설정_로컬검수와배포준비.md) · [W06 자료 인수](2026-11-13_W06_팀검수통합인수표.md)

## 배포와 HTTPS 확인

1. 전용 운영 환경 파일에 위 값을 입력한다. `ARTI_DEPLOY_HTTP_PORT` 기본값은 `8080`이다. HTTPS 템플릿의 `@ARTI_HTTPS_HOST@`, `@ARTI_TLS_CERT@`, `@ARTI_TLS_KEY@`, `@ARTI_WEB_UPSTREAM@`을 채운다. 같은 호스트에서는 upstream이 `http://127.0.0.1:8080`이고 `@ARTI_EDGE_RESOLVER@`는 빈 문자열이다. 프록시의 실제 포트가 달라지면 upstream도 맞춘다. 예제의 `$host`, `$uri`, `$arti_web`은 Nginx 변수다.
2. 배포 전 이전 API·웹 digest, DB·미디어 백업 해시와 복구 시각을 기록한다. Compose 프로젝트 이름과 DB 볼륨을 확인한 뒤 PowerShell에서 검증하고, 승인된 배포 회차에 마이그레이션을 한 번 적용한다. `config --quiet`는 설정값을 출력하지 않는다.

```powershell
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $true
$deploy = @('--env-file', '.env.compose.deploy', '-p', 'arti-shared', '-f', 'compose.yaml', '-f', 'compose.deploy.yaml')
docker compose @deploy config --quiet
docker compose @deploy pull db api web
docker compose @deploy up -d --pull never --wait db
docker compose @deploy run --rm --pull never --no-deps -T migrate
docker compose @deploy up -d --pull never --wait api web
```

3. 호스트 Nginx의 `http` 설정에 포함되는 경로에 작성한 설정을 두고 `nginx -t`가 성공하면 다시 읽힌다. 팀 PC에서 인증서의 호스트명·유효기간, `/api/ready`의 PostgreSQL 응답 `200`, 영수증 직접 주소와 JS 번들을 확인한다. 별도 합성 계정의 본인·관리자 `200`, 다른 회원 `403`, 비로그인 `401`을 확인한다. 콜백과 재설정 경로는 `no-store`·`no-referrer`를 확인한다.
4. 메일·카카오를 꺼 둔 최초 환경에서는 `python scripts/probe_account_https.py <HTTPS주소> mail --expect-disabled`와 `python scripts/probe_account_https.py <HTTPS주소> kakao --expect-disabled`로 상태와 보호 헤더를 확인한다. 이 두 검사는 주소로 요청을 보내며, SMTP 발송이나 카카오 인가 교환을 실행하지 않는다.

## 이전 이미지 복귀

1. 운영 담당이 확보한 이전 정상 API·웹 digest를 운영 환경 파일에 설정한다. Compose 프로젝트, DB와 미디어, 서버 비밀 설정을 대조한다. 메일 워커를 같이 쓰는 운영 환경이면 담당이 해당 워커를 먼저 정지하고 같은 이미지 조합으로 재개한다.
2. 이전 Django 이미지의 마이그레이션 목록과 실제 DB에 적용된 이력을 비교한다. 성공이면 같은 DB·미디어에서 이전 이미지로 기동할 수 있는 다음 검수로 넘어간다. 이력이 다르거나 조회에 실패하면 이 절차에서 멈추고, 복원 기준 시점과 백업을 운영 담당이 판단한다. 일치하는 이력에서도 데이터 형식의 호환성과 응답을 확인한다.

```powershell
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $true
$deploy = @('--env-file', '.env.compose.deploy', '-p', 'arti-shared', '-f', 'compose.yaml', '-f', 'compose.deploy.yaml')
$schemaCheck = Get-Content -Raw -Encoding utf8 scripts/check_release_schema.py
docker compose @deploy config --quiet
docker compose @deploy pull api web
docker compose @deploy run --rm --pull never --no-deps -T api python manage.py shell -c $schemaCheck
docker compose @deploy up -d --pull never --no-deps --wait api
docker compose @deploy up -d --pull never --no-deps web
```

3. 같은 HTTPS 주소에서 정적 영수증 직접 주소·JS 번들, DB 준비, 원래 영수증 ID와 관람 한 건, 역할별 권한, 미디어를 재검수한다. 유지보수 중 생긴 장애는 일반 로그에 남고 콜백·재설정의 민감 값은 로그에 남기지 않는지 확인한다. 실제 트래픽 전환 여부를 담당이 기록한다. [기록과 DB·미디어 복원](2026-11-11_main_시연복구체크리스트.md#복원-후-영수증-접근-권한-확인)

## 합성 재현

```powershell
pwsh -NoProfile -File ./scripts/runDeployRollback.ps1 -Revision aea8f9a -PreviousRevision 99c36f5 -IncompatibleRevision 63aafe8
```

PowerShell 7.4 이상, Docker Desktop과 Compose, Git, Python, Windows curl이 필요하다. 테스트는 전용 Compose 프로젝트와 합성 PostgreSQL을 만들고 루프백에서 시험 인증서를 검증한다. 배포 후보 `aea8f9a`, DB 이력이 같은 이전 코드 `99c36f5`, 이력이 다른 대조군 `63aafe8`을 사용한다. 결과는 `data/private/arti-deploy-check-<ID>/result.json`에 남고 시험 자원을 정리한다.
