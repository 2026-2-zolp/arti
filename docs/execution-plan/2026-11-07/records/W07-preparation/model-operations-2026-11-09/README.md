# W07 모델 서비스 운영 안정성

2026-11-09 / 기준b8fac09 / 실제 팀 라벨 없이 진행 가능한 선행 기술 과업. [운영 안내](../../../../../operations/모델서비스_로컬운영.md),[실제 모델 결과](live-result.json),[실행문](executed-live-probe.py.txt),[첫 실행 결과](first-live-result.json),[최종 검사 요약](validation.json),[PostgreSQL 로그](postgres-tests.log).

## 문제와 보완

기존 로더는 CLIP을 먼저 필드에 게시한 뒤 processor/NLI를 준비했고, 요청 경로에서 로딩을 기다릴 수 있었다. FastAPI 직접 동시 추론을 제한하는 슬롯도 없었다. Django는 같은 관리자 요청의 첫 분석 실패 후 감정 필드에서 같은 upstream을 다시 호출할 수 있었고, 모델429를502로 바꿨다.

runtime.py의 단일 로딩/추론 슬롯으로 준비 중503·추론 중429를 대기 없이 알리고, health/ready를 구분했다. 분석 예외가 나도 슬롯을 해제하며 loader 실패는5초 후 다음 요청에서 재시도한다. analyzer.load는 모든 구성요소 성공 후 필드에 게시한다. 완료 직후 재로딩 경합과 스레드 시작 실패도 보완했다.

Django는 요청 내부 실패 캐시·429/Retry-After 보존·30초 timeout 상수·끊긴 HTTP 응답 정제를 추가했다. 기존 글로벌 PostgreSQL advisory lock, 원문 승인 제한, 부분 성공, suggested 저장, 버전 충돌 보호는 유지했다. 다른 요청끼리 실패를 공유하지 않으며 GPT로 태그/감정 성공을 대신하지 않는다.

실모델 최종 시험은 Windows CPU4스레드·고정 CLIP/mDeBERTa revision·오프라인 파일에서 실행했다. 최초 요청503 약12ms, 로딩 중 다음 요청503 약28ms, 모델 준비 약5.81초. 동시 성공은약4.93초/거절약4ms, timeout 후 재성공약3.32초. 재기동 준비약9.53초, 서버계열 peak RSS1261.04MiB(약1.23GiB)였다. 프로세스 실행·OS캐시·동시 시스템부하가 있는 단일 측정이며 SLA/운영 서버 크기나 일반 정확도로 해석하지 않는다. peak는0.1초 표본·launcher와 자식 RSS 합계이고 caller는 제외한다.

실제 중단은 이미 끝난 서비스만 내린 것이 아니라 health.analysisBusy=true 중 Django의 진행 요청을 중단했다. 이 테스트는 DB를 쓰지 않는 provider 호출이고, 저장 보호는 별도의 실제 PG+지연HTTP 검사가 담당했다. 두 근거를 합쳐 실제 모델+실제 저장을 한 번에 시험했다고 과장하지 않는다.

## 검증 루프

초기 pytest import가 tests 패키지 경로와 맞지 않아 상대 import로 수정했고, 전용 임시폴더 상위 경로 누락은 디렉터리 준비 후 재실행했다. 기존17개와 초기신규5개22개가 통과했다. 자체 검토에서 loader 완료 경합·스레드 시작 실패를 추가 보완해 Windows23개가 통과했다. 이후 Linux/작성 비활성 조건에서 기존 write2개가 활성 설정을 가정해 실패했다. 각 가짜 writer 시험이 활성 조건을 명시하도록 분리하고, 비활성일 때 generate를 호출하지 않는 검사를 추가했다. Torch 없는 Linux의 운영 권장 비활성 조건에서 최종24개가 통과했다. 느린 요청·busy·실패는 이벤트로 결정해 단순 시간맞추기 시험을 줄였다.

PG 전체96개가 먼저 통과했고, 추가 검토에서 chunked/부분 HTTP 응답의 IncompleteRead가 비정규화될 수 있어 HTTPTransportError를 안전한502로 처리하고 신규 검사 후97개를 재통과했다. 이 정규화 보완은 실모델 시험 이후이므로 live-result sourceHashes의 model_service.py와 최종파일 차이를 validation.json에 명시했다. 모델 runtime/추론 소스는 동일하다. 기록한 로컬 파일 bytes hash는 OS별 줄바꿈 정규화와 구분한다.

실모델은 초기4가지 시험→최종 로더 재확인→진행 중 프로세스 중단을 추가한5가지 시험으로 보강했다. 앞선 성공을 최종 새 코드 시험으로 가장하지 않으며 첫 기록도 보존했다. 유료 LLM·유영국 원본·일반 DB는 사용/수정하지 않았다. 프론트 변경이 없어 프론트/브라우저 검사를 이번에 재실행하지 않았다.

기술/시니어는 슬롯/경합/프로세스 범위와 늦은 응답을, 데이터는 suggested/확정·버전·실패 보존을, 운영은 상태 관측·timeout/재기동·로그/비밀값을, 방문자/콘텐츠는 무한 대기나 가짜 성공을 만들지 않는지, 팀/교수/평가위원은 실제 추론과 가상장애·정식 품질의 근거 구분을 자체 검토했다. 동일 작성자의 관점 검토이며 외부 승인과 다르다.

## 한계와 다음

단일 모델 프로세스의 로컬 운영 기준이다. native 추론은 caller timeout으로 강제 취소되지 않고 실제 완료까지 슬롯을 유지한다. 영구 정체는 운영자 재시작이 필요하며 watchdog/분산 queue/다중worker 전역제한은 추가하지 않았다. readiness는 모델 로딩 상태이지 유휴 용량·품질 보증이 아니다. 다운로드 영구 정체도503으로 드러나며 사전 파일 확보·운영자 확인이 필요하다.

[운영 안내](../../../../../operations/모델서비스_로컬운영.md)대로 새 Django 분석 서비스는 Kanana write를 비활성으로 제한한다. 레거시 write를 동시에 켜는 자원 보호는 이번 슬롯에 포함하지 않는다. 통합 배포 위치·프록시/연결 수 제한·예산은 W12/W08에서 결정한다. 팀 검수·유영국 품질·G5는 변경하지 않는다. 다음 독립 기술 과업은 W11 PR CI 마감, 병행할 W12 운영 결정안이다. 실제 팀 라벨이 오면 콘텐츠/정식 품질 과업을 이어간다.
