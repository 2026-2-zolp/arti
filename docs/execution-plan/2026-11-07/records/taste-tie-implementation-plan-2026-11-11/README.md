# R04 취향 동점 기능 — 구현 상세 작업 계획

2026-11-11 / 출발점 `9234371` / **계획만 작성,제품 적용 전**.

[동점 계약](../taste-tie-contract-2026-11-11/README.md)과 [프론트 전달본 검토](../taste-tie-contract-2026-11-11/frontend-intake.md)를 실제 소스에 대조했다. 이번 산출물은 다음 개발을 위한 과업 지시와 통과 기준이다. 새 스키마/API/화면/설정은 아직 없고,26개 후속 검증 시나리오는 모두 **미실행**이다. 기존 W/G/AC나 사람 검수 상태를 올리지 않는다.

## 목표·범위·착수 조건

빈도/최대8태그/3·5·7점 추천을 유지하면서 **같은 빈도일 때만 출처가 확인된 점수로 우선순위를 보조**한다. 결측/혼합 출처는 동점 그룹 전체를 고정 순서로 대체하고,현재풀 변경과 옛 저장 취향 재사용을 분리한다. 미확정 초안·저장실패 때문에 현재 관람/계정/영수증이 손상되지 않게 한다.

이 계획의 범위는 점수 provenance,서버 계산/호환,프론트 확인과 기존 UI hunk선별,격리 검증이다. 태그 어휘·보정값 최적화·재학습·새 LLM/챗봇 기능·토너먼트·대표3강제·전시 추가·조사 최종10점 선정·실자료 승인·공개 활성화·AWS/CD·원격 push는 포함하지 않는다. 유영국/인상주의/외부 후보의 사람 검수는 병렬로 진행 가능하며 이 기술 구현의 승인 자료로 자동 사용하지 않는다.

제품 착수는 **이 상세 범위와 추가 결정 검토 후 별도 지시**에서 시작한다. 단계 실패는 수정→실패 사례 재현→영향 회귀→같은 단계 재판정으로 반복한다. 통과한 단계만 로컬 커밋하고 다음 단계로 간다. 이미 통과한 앞단계가 바뀌면 그 단계 영향 검사도 다시 수행한다. 사람/환경 의존 항목은 대기로 표시하고 성공으로 대체하지 않는다.

향후 TP1~TP4를 승인하더라도 여기의 DB migration·enable·컨테이너 재기동은 **전용 격리 환경에서만 검증**한다. 일반 arti-dev 적용·환경 재생성·운영 배포는 이 순서의 자동 후속이 아니며,백업/호환/증거를 검토한 뒤 별도 범위로 정한다.

실제 소스와 계약에서 추가로 구체화한 [결정 D1~D7](decisions.md)을 먼저 확인한다. 특히 새 계정쓰기의 재시도,구형 클라이언트의 v2 덮어쓰기 방지,관람 중 풀교체와 영수증,disable 시 기존 v2 읽기는 이전 문서보다 구체화된 제안이다. 이전 계약 파일은 역사적 근거로 보존했다.

## TP1: 점수 출처부터 저장

주된 파일은 ai-service의 `config.py/analyzer.py/main.py/image_fetch.py/runtime.py`와 신규 `provenance.py`,Django의 `model_service.py/providers.py/models.py/editing.py/serializers.py`,신규 `0003_tag_score_evidence.py`다. 기존 루트 `.env.example`·`.env.compose.example`과 모델 로컬 운영 문서를 보완할 계획이다. **backend-django/ai-service의 .env.example은 현재 존재하지 않으므로 별도 파일이 있다고 가정하지 않는다.** Compose에는 모델 서비스가 없으므로 모델 Dockerfile/배포 서비스를 이번 범위에서 만들지 않는다.

1. 분석 요청에 실제 실린 파일 바이트와 모델이 읽은 파일 바이트의 SHA를 확인한다. 모델/processor의 실제 로딩 artifact와 프롬프트/전처리/보정 signature를 만들고,로컬 폴더의 출처를 모르면 unknown/null로 남긴다.
2. FastAPI의 추가 nullable tagEvidence를 Django에서 검사한다. 구형 응답의 필드 부재는 허용하되,존재하는 잘못된 필드는502로 분리한다. text fallback·감정 모델 정보를 이미지 태그 근거로 바꾸지 않는다.
3. tag_score_revision/evidence를 additive migration으로 추가한다. 기존점수/태그/승인/계정 snapshot을 수정하지 않는다. 새 분석 성공 시 세값을 같은 트랜잭션에 쓰고 suggested를 유지한다. 실패한 tag는 세값 모두 무변경,전체 예산초과는 전체 결과 저장0이다. 다른 종류의 기존 부분성공 정책까지 바꾸지 않는다.
4. fake 응답/부분로드/재기동·429/503/504·원본변경/낡은 version을 검사한다. 일반 API 요청 중 provenance가 부족하다고 재분석하지 않는다.

승인 signature가 없거나 근거가 없는 자료도 기존 v1 기능은 유지한다. v2 AI 동점 사용 가능 상태와 작품/콘텐츠 사람 승인은 별개다. 새 provenance를 붙였다고 기존 공개풀을 활성화하지 않는다.

## TP2: 서버 한곳에서 계산하고 저장 보호

신규 `taste_resolution.py/taste_evidence.py`,기존 `survey.py/recommendations.py/serializers.py/views.py/member.py/records.py/config/urls.py`,관리자 다중잠금 경계와 Account의 마지막 쓰기 receipt 구조를 대상으로 한다.

1. 서버 공통 helper에서 counts·6자리정수 합·동점 그룹 fallback·canonical 순서를 계산하고 기존 참조모델30반례와 대조한다. 프론트에 두 번째 알고리즘을 만들지 않는다. 기존 v1의 weighted score/태그 순서/후보/추천수는 동결한다.
2. 새 GET capability와 읽기 전용 resolve를 추가하되 생성 enable은 default false다. v1필드/기존 poolVersion 식·추천 배열·PUT204는 유지한다. 새 preview와 저장/추천은 동일 시점의 풀10점을 사용하고,사용자 확인 후 실제 실행 때 다시 버전을 검사한다.
3. Account→Pool ID순→Artwork ID순의 짧은 잠금 순서를 통일한다. 관리자 batch confirm의 요청순 잠금을 함께 보완한다. 모델/네트워크 호출은 잠금 밖이다. 실제 PG 두 연결+barrier로 혼합 근거와 교착을 확인한다.
4. 새 계정 쓰기는 expected version+mutation ID를 원자 확인한다. 성공 응답이 유실된 동일 요청은204 한 번의 저장 결과로 재사용하며,stale/다른 payload는409다. 구형 v1은 v2계정을 무버전으로 덮지 못한다. 옛 snapshot 읽기에는 현재풀을 요구하지 않는다.
5. `records.canonical`도 프로필을 검증하므로 관람 도중 풀교체를 별도 다룬다. 서버 인증된 actor/visit-bound 관람근거를 쓰되 신규 추천/계정 저장의 현재 버전 검증을 우회하지 않는다. 기존 visitId 동일 재시도 경로를 먼저 유지한다. 이 증거는 승인/인증 토큰이 아니다.

v2의 실제 인터페이스는 이전 계약+D1~D7을 함께 기준으로 한다. 이 계획의 참조/형식 검사 성공을 실제 PG 동시성 통과로 적지 않는다. DB 스키마 변경은 실제 착수 당시 migration 번호를 다시 확인한다.

## TP3: 화면은 확인 성공 뒤 한 번 반영

주된 파일은 `types.ts/api/client.ts`,신규 `lib/tasteDraft.ts`,`U05/U06/U08/U12`,`visitReducer/VisitContext/receiptPayload`다. 기존 `tasteFromPicks`는 v1 호환용으로 유지한다. 미확정 새관람 UUID·근거·초안은 로컬에 두고,확정되기 전 기존 visitId/추천/반응을 바꾸지 않는다.

1. 서버가 v2 형식과 enable을 함께 제공할 때만 새 flow를 쓴다. 미지원 상태나 실패를 AI 동점 적용으로 표시하지 않는다. saved v1/v2를 명시적으로 읽고 v2를 v1으로 위장하지 않는다.
2. 선택 태그 부분집합 편집과 새태그 추가/manual 전환을 구분한다. 빈선택 확정은 막되 상위3개를 강제하지 않는다. 배열순서만 달라졌거나 원래 의미로 돌아오면 no-op이다.
3. preview 후 실제 변경/새관람을 확인하고 계정 CAS저장·최신계정 확인 뒤 확정 dispatch 한 번을 보낸다. 취소/409/실패·PUT성공 후 api.me실패를 각각 표시하고 기존관람을 보존한다. ‘이번관람만’도 사용자 명시 선택이다.
4. actor·requestGeneration·editRevision으로 늦은응답을 막는다. 로그인/로그아웃·다른계정·새관람·새로고침·저장소복구·pending 영수증을 시험한다. 같은 mutation과 원래 body로만 저장 재시도한다.

UI 병합은 [기존 전달본 분류](../taste-tie-contract-2026-11-11/frontend-intake.md)를 보존한다. 오류/경고색·error-text·이유강조/헤더는 후보이며 동섭님 종합본 기준을 재확인한다. 회신이 없으면 해당 hunk는 보류하고 TP1/TP2 및 독립적인 확인 흐름은 진행 가능하다. **선별 UI 미병합을 완료라고 표시하지 않으며,선택 항목의 보류를 핵심 v2기능 전체의 완료로 혼동하지 않는다.**

전역 조사 API·U05 contain·U07 같은시간 복귀·U10 문단·닉네임100자·기존 회귀는 반드시 보존한다. 헤더는 중복 제목을 줄이면서 주제목 계층이 남는 경우에만 적용한다. 화면 크기를 줄이려고 작품을 cover로 자르는 변경·node_modules/lockfile 일괄교체·ZIP전체 덮기는 하지 않는다.

## TP4: 격리 환경에서만 기능 켜고 인수

시험 프로젝트 제안명은 `arti-tie-integration`,API/UI 제안 포트는14018/15178이다. 실제 사용 전 점유 여부를 확인한다. DB/미디어 볼륨도 전용으로 만들며,일반 `arti-dev`와 env·볼륨·컨테이너 이름을 공유하지 않는다. 비밀값은 ignored 시험 env에만 두고 출력하지 않는다. API의 GPT provider는 disabled로 하고 새 다운로드를 자동 실행하지 않는다.

- 합성10점/5쌍과 별도 추천 전시를 격리에만 준비한다. fixture의 approved/confirmed는 시험 표식이며 실제 자료 승인이 아니다. 유영국16점이나 외부 후보를 최종조사로 적재하지 않는다.
- v1 전후 출력(ID/순서/score/matchedTags) 보존과 v2 weights/태그 집합 보존을 검사한다. 선정 집합·방문 순서 변화는 따로 기록하며 만족도/동선 최적성으로 부르지 않는다.
- 추천→지도→작품해설/가이드→도슨트 맥락→회원/비회원 영수증을 fake 서비스로 완주한다.409·응답유실·다른계정·중복클릭·풀교체·disable/복구를 포함한다. GPT 품질을 다시 측정하지 않는다.
- 기존 cached 실제 이미지 모델1회로 실제 artifact/processor·입력 SHA·보정 signature를 대조한다. cache/출처 확인이 안 되면 해당 항목은 대기이며 TP4 전체 통과를 주장하지 않는다. CI는 계속 fake/offline이다.
- 기존 CI4job 상당 명령을 수행한다. 새 단위/PG/API 시험은 해당 job이 수집하는 경로에 둔다.실제 Actions 성공은 push 후 별도이며 이번 요청의 원격push는 없다.
- 일반환경의 전후 행/미디어/활성풀·원본 보존을 확인한다. 다른 작업으로 바뀐 것이 있으면 외부변경과 구분해 확인하고 복원/덮어쓰지 않는다. 정리도 본인 시험 자원만 대상으로 하며 일반환경 `down -v`는 금지한다.

실행 기록은 각 단계마다 **왜/변경 전후/파일/명령·환경/원수/실패와수정/남은제약/다음단계**를 누적한다. `plan.json`의 각 case가 요구하는 evidence 파일을 별도 실행 기록 아래 연결한다. 26개 미래 사례는 이번 계획에서 통과로 표시하지 않는다. 로컬 commit 제목은 기존 체계를 따르고 본문은 불릿 뒤 필요한 맥락/검증만 붙인다. 원격push는 별도다.

이번 계획 검증: `python docs/execution-plan/2026-11-07/records/taste-tie-implementation-plan-2026-11-11/verify.py --planning-worktree`. 이는 파일/출처/단계 DAG/검증 매핑/금지범위/계획오류 반례만 검사한다. 검증 결과는 [validation.json](validation.json)에 기록한다. 미래 구현 뒤에는 과거 소스를 Git 기준으로 확인하는 기본 모드만 사용하고,미적용 전용 worktree 검사를 CI에 계속 강제하지 않는다.
