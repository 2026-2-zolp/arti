# R04 동점 처리 계약 구체화

2026-11-11 / 기준 `ce5e487` / **제품 적용·최종 선정·공개 활성화·원격 푸시 없음**.

먼저 [프론트 전달본 대조](frontend-intake.md)를 수행했다. 이후 기존 [전역 조사 계약](../team-feedback-2026-11-10/survey-contract.md),[실제 점수 비교](../W07-preparation/survey-comparison-2026-11-10/README.md),[블라인드 검수 준비](../../../../review/taste-survey-2026-11-10/README.md)를 잇는 계약을 작성했다. 이 문서는 향후 구현의 기준이며 현재 API에 아래 v2 필드/경로가 이미 생겼다는 뜻이 아니다.

## 핵심 결정

1. **빈도·최대8태그·3/5/7점 추천 수는 유지**한다. 점수는 빈도가 같은 태그 사이에서만 우선순위를 보조하며 가중치를 바꾸거나 대표3개로 잘라내지 않는다.
2. 서버가 검증한 같은 이미지 태그 모델·revision·프롬프트/전처리·보정/점수 정의의 점수만 비교한다. 선택한5점의 해당 동점 태그 점수가 모두 있어야 한다. 하나라도 빠지거나 비교 불가능하면 **그 동점 그룹 전체**를 서버 `TAGS` 순서로 정렬한다. 누락을0으로 채우거나 일부 태그끼리만 유리하게 비교하지 않는다.
3. 점수는 소수6자리 반올림 후 정수로 합산한다. 합까지 같으면 `TAGS` 순서다. 이는 일관성을 위한 결정이며 공정하거나 최적임을 증명하지 않는다. 점수는 선호 확률이 아니다.
4. 새 선택은 기존 poolVersion에 더해 **별도 점수 근거 버전**도 확인한다. 오래된 입력은409로 거절하고 작성 중 선택은 보존한다. 저장된 취향은 당시 서버 snapshot을 사용하고 새풀·새모델로 소급 변경하지 않는다.
5. 사용자 선택 집합 수정과 배열 순서·대표 표시를 구분한다. 선택 근거 안에서 제외/복귀는 picks 부분집합,근거 없는 태그 추가를 확정하면 manual 균등 가중치다. 재계산은 명시적 확인 후에만 새 관람에 반영한다.

## 정렬·누락 규칙

서버가 검증한5개 쌍 선택에서 counts를 다시 센다. 선택 태그는 counts>0인 부분집합이어야 한다. 클라이언트 counts·점수·tagOrder는 신뢰하지 않는다. primary는 기존 `max(1,count)` 정수가 같을 때만 동점이다. picks에서는 count>=1이며,manual/오래된 counts 결측의1점 보정은 기존 호환을 유지한다.

동점 그룹마다 선택한 **5개 이미지 전체**의 해당 태그 점수를 합산한다. 해당 태그가 작품의 등록 태그에 들어간 경우만 합산하거나 횟수로 나누지 않는다. 동일5점·같은 분모이며 `scores`에 있는 유효한0도 포함한다. 비교 그룹 밖 태그 점수 결측은 이 그룹에 영향을 주지 않는다.

| 상황 | 처리 |
| --- | --- |
| 비교가능한 그룹 점수 모두 있음 | 각값 `Decimal(str(value))`로 소수6자리 ROUND_HALF_UP → 1,000,000배 정수 →5점 합,합이 큰 순 |
| 같은 합/6자리 이하 차이 | TAGS 순서.순환 epsilon 비교·입력 배열순서·Math.random 금지 |
| None/누락/문자열/bool/NaN/Infinity/범위밖 | 그룹 전체 fallback,0으로 대체하거나 잘라 쓰지 않음 |
| 모델 revision/보정/점수정의 불일치·text 태그 | 그룹 전체 fallback.같은 모델명만으로 비교 가능 판정 금지 |
| 점수 출처/입력 이미지해시/scoreRevision/서버 승인 signature 없음 | 그룹 전체 fallback.추정 메타데이터 생성 금지 |
| 중복/잘못된 쌍·선택 근거 없는 태그 |400 VALIDATION_ERROR,전체 무변경 |
| 새 picks의 풀·점수 근거 변경/준비해제 |409 VERSION_CONFLICT,전체 무변경 |

TAGS 순서는 `풍경→인물→추상→빛→강렬한 색감→차가운 색감→따뜻한 색감→부드러운 색감`이다. 이 마지막 대안에도 고정 편향은 남는다. 최종 동점은 UI에 동점임을 알릴 수 있지만 대표3개를 임의 활성화하거나 서버상한3개를 도입하지 않는다. 무작위는 추천 재현성/원인 설명을 떨어뜨려 이번 안에서 제외했다. 적은 모델 차이가 실제 선호 차이라는 주장은 하지 않는다.

## 근거·버전·서버 snapshot

비교 signature는 이미지 태그 생산 모델 ID/revision,프롬프트·전처리 해시,보정 해시,태그 정의 버전,`image-calibrated-tag-v1` 점수 정의를 묶는다. GPT 모델이나 감정 결합 mDeBERTa 버전을 그대로 이미지 태그 signature로 쓰지 않는다. 서버가 승인한 signature와5점 각각의 출처가 일치해야 한다. 공개/클라이언트 입력이 스스로 승인 출처임을 선언할 수 없다.

tieContextVersion은 policyVersion·태그정의·기존 poolVersion·서버 승인 signature와 **풀10점 전체**의 순서/ID/태그/태그상태/점수/scoreRevision/입력이미지해시·출처를 정규화한 hash다. 비선택 작품 변경도 추적해 화면에 받은10점 묶음을 고정한다. 모델 실행 환경만 바뀌어 실제 값/정의가 달라지면 새근거다. 정규화는 UTF-8 JSON,ensure_ascii=false,키 정렬,공백 없는 구분자로 고정한다.행의 고정 필드는 id/tagStatus/signature/tagSource/scoreRevision/imageSha256이며,tags는TAGS순서,scoresUnits는8개태그의6자리정수 또는 결측null이다.상단은policyVersion/tagDefinitionVersion/poolVersion/approvedSignature/orderedPoolRows다.유효0과null은다르다.원시점수의미세차이가양자화후같더라도정상재분석은scoreRevision을갱신한다.운영저장은NaN/Infinity를허용하지않으며,참조모델 fingerprint의합성invalidNumber표시는시험용일뿐저장스키마가아니다.

서버 저장 v2에는 기존 counts/selectedTags·originalPicks·조사 출처 외에 policyVersion·당시 tieContextVersion/signature 식별자·당시 동점 그룹의 가용성/판정이유·정수 합/순서·counts/selectedTags binding을 보존한다. 전체 이미지나 GPT대화는 넣지 않는다. 클라이언트가 돌려준 tieEvidence는 거절하고,새 picks는 서버 근거로 다시 생성한다. 현재풀 변경과 저장 snapshot 재사용을 분리한다.

구형 v1 snapshot은 counts/선택 집합 그대로 사용하고 서버의 기존 TAGS 대안을 쓴다. 프론트가 보존한 표시 배열은 소급 재정렬하지 않는다. 새로운 점수 필드를 배치로 채우거나 읽기만으로 계정 버전·관람기록을 갱신하지 않는다. counts 일부/전체 결측은 기존 max(1,count) 호환,범위밖/bool/알 수 없는 프로필 스키마 등 잘못된 서버 데이터는 복구 검토로 분리하고 자동 덮어쓰지 않는다. 저장된 v2의 tie정책/근거 binding을 확인 못하면 기존 가중치+TAGS fallback과 운영 진단을 남긴다. 현재풀로 옛 선택을 재해석하지 않는다.

## API·확인 흐름: 향후 구현 계약

현재API는 v1이며 아래는 **미구현 명세**다. 버전 지원이 확인되지 않은 클라이언트는 기존 v1로 동작하고 AI 동점 기능이 적용됐다고 표시하지 않는다.

- 향후 `GET /api/taste-pool`은 기존 응답에 `supportedTasteProfileVersions:[1,2]`와 `tieContext:{policyVersion,tieContextVersion}`을 추가한다. v1필드/poolVersion의 의미는 유지한다. 출처가 부족해도 유효한 조사 태그가 준비돼 있으면 tie는 fallback으로 해석 가능하며,기존 조사 자격 완화는 하지 않는다.
- 향후 `POST /api/taste-profiles/resolve`는 쓰기 없는 preview다. `tasteProfile.version=2`,source·selectedTags·picks/poolVersion/tieContextVersion 또는 저장버전을 받는다. 응답은 서버 counts/정규화 profile·전체 tagOrder·그룹별 method/reason·`userConfirmed:false`다. 점수 퍼센트·AI신뢰도·원본모델 입력은 공개하지 않는다. 이 한 경로를 둬 프론트·서버의 독립 재구현/숫자차이를 줄인다. 명칭/의미를 여기 기준으로 고정하되 이번에 URL을 추가하지 않았다.
- 새 picks 저장/추천은 v2 근거를 다시 검증한다. preview응답 자체를 승인 토큰처럼 신뢰하지 않는다. 낡으면409이며 자동 v1전환·manual전환은 하지 않는다. 같은 동점 원칙을 표시 순서와 서버 커버리지 배정에 공유한다.
- v1 입력은 기존 코드 경로/가중치/서버 TAGS 대안을 유지한다. v2실장 시에도 v1을 AI로 조용히 바꾸지 않는다. v1/v2 혼합 회귀가 통과해야 한다. 기존 반환형(추천 배열/계정 저장204)을 바꾸지 않고 preview의 새응답을 별도로 사용한다.
- source=saved는 인증된 본인의 account와 savedProfileVersion이 같아야 한다. 위조 counts/순서/picks는 무시하며 계정 집합과 다른 요청은400,비인증401,저장버전 불일치409다. 새 v2계정 저장에는 명시적 `expectedSavedProfileVersion`을 두고 lock 안에서 재확인해 stale 탭이 새취향을 덮어쓰지 않도록 한다. **현재 PUT tastes는 새저장에 이 낙관적 버전검사를 하지 않는다**. 구현 준비에서 별도 보완해야 한다.
- source=manual은 임의 유효8태그의 비어 있지 않은 집합과 균등 가중치다. 과거 picks/counts/동점 점수는 새증거로 섞지 않는다. 이 동작은 현재 manual 계약의 연장이다.

새 preview의 실패는400 VALIDATION_ERROR/401 AUTH_REQUIRED/409 VERSION_CONFLICT로 구분한다. 잘못된 저장 스키마는 사용자 입력400으로 몰지 않고 운영 복구 진단 `STORED_PROFILE_REVIEW_REQUIRED`로 구분하며,구현 시 사용자에게는 저장 취향 확인/명시적 재조사 경로를 제공한다. 점수 부족만으로 모델 호출·timeout·503을 만들지 않는다. 요청 처리 중 모델 재추론을 하지 않는다.

## 추천/동선 영향과 경계

동점 보조는 **같은 빈도 태그의 커버리지 시도 순서**만 바꾼다. 작품 점수의 빈도 가중치·strength·후보 자격·상위점수/작품ID 순·matchedTags의 작품강도순·관람수3/5/7은 그대로다. 기존 `[:count]` 시도 범위와 후속 채우기를 이번 정책으로 개선했다고 주장하지 않는다. 태그마다 한 작품을 반드시 보장하지 못하며 없는 취향 자동 대체도 하지 않는다.

동선 계산 알고리즘은 바꾸지 않는다. 다만 선정 작품/초기순서가 달라지면 결과 동선과 등거리 순서는 달라질 수 있다. 실제 보행시간/최단경로 개선을 주장하지 않는다. 작품별 weighted score·추천 집합·방문 순서의 변화는 구현 후 별도 측정해야 한다. 현 참조모델은 **태그 우선순위 계약**만 검증한다.
