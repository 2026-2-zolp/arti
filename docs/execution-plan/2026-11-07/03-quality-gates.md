# 검증단·단계별 인수 기준 v2.1

## 검증 역할과 증거

정합성(요구·맥락·범위), 기술(API·상태·전환), 데이터(출처·검수·저장·이전), AI(근거·관찰·실제호출·자원), 사용자(모바일·재진입·여정), 운영(Docker·AWS·CI/CD·복구) 관점으로 나눠 검토한다.

실제 팀 인원에 맞춰 역할을 겸할 수 있으나 구현자/검토자 동일 여부를 기록한다. 별도 AI 검토는 문서 정합성 보조이며 사람 작품검수·실제기기·모델·AWS 실행을 대신하지 않는다.

기존 검증단에 [팀·교수·초보관람객·콘텐츠 운영 페르소나](10-persona-review-and-improvements.md)를 추가한다. 실제당사자 의견이 아닌 근거기반 가상검토다. 단계와 위험에 맞는 1~2개 관점만 더하고 매변경 전원검토/회의를 추가하지 않는다.

각 AC에는 커밋·환경·입력·기대·실제·로그·검토자·날짜가 필요하다. pass에는 evidencePaths가 필요하며 gate pass에는 reviewEvidence가 필요하다. 링크 존재만으로 증거 내용의 진실성을 보증하지 않는다.

## 과업과 게이트의 규칙

- task dependsOn과 requiredGates는 in_progress/complete에 공통으로 필요한 착수 선행이다.
- completionDependsOn/completionGates는 complete에만 필요한 추가조건이다. W11은 W03 후 시작하지만 W04 완료 전 최종 CI완료를 표시하지 않는다.
- task complete: 선행·완료추가조건 + own AC 전부 pass.
- gate pass: own AC 전부 pass + 관련 task complete + 선행gate pass + 실제 검토증거.
- 자기 게이트를 과업 선행으로 넣지 않는다. G5와 G6는 여러 과업의 최종 집계이므로 W06/W08은 자기 AC를 충족하면 먼저 완료 가능하다.
- AC31은 필수 이슈 종결 후 최종집계다. 필수 이슈를 닫기 위해 AC31 자체를 먼저 요구하지 않는다.
- 불일치·실패·외부대기는 fail/blocked/not_run으로 남긴다. 평균점수·대다수결로 필수실패를 상쇄하지 않는다.
- 개발 gate G2는 로컬 회귀만, GCI는 실제 Actions다. GOPS는 운영결정이며 G1과 분리된다.
- RDS 미채택 자체는 실패가 아니다. 선택한 PostgreSQL 운영환경이 동일한 접근제어·암호화·migration·복구 기준을 충족해야 한다.

## 통과할 때까지의 루프

1. 변경 전에 관련 W/F/AC와 입력·판정·범위를 고정한다.
2. 작은 변경→해당 검사→인접 회귀→증거→검토를 수행한다.
3. 실패 원인을 환경/계약/구현/데이터/모델/범위로 분리하고 수정한다. 같은 실패가 두 번 반복되면 다른 관점에서 전제를 재검토한다.
4. 필수 AC를 통과할 때까지 같은 단계에서 반복한다. 외부입력 부족은 blocked로 두고 독립 과업만 진행한다.
5. 모델/DB/인증/배포 경계가 바뀌면 영향받는 pass를 재검증 상태로 되돌리고 과거 증거를 보존한다.
6. 범위변경은 결정과 영향검토를 남긴다. 기준을 사후에 낮추거나 기록만 하고 품질미달을 통과시키지 않는다.

고정 평가셋에서 오류0건이라는 기준은 그 시험 범위의 주장이다. 전체 모집단 무오류를 보장하지 않는다. 유효한 sourceId와 주요사실의 근거 일치, 관찰질문의 적절성을 별개로 판정한다.
