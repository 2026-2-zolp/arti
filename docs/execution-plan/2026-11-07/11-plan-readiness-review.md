## API 교체와 기능 수정의 실제 순서

1. **W03:** 기존 Express의 잘못된 동작과 정상 동작을 분리해 기록한다. 결함 재현 성공을 제품 통과로 처리하지 않는다.
2. **W04:** Django/Postgres를 별도 개발 DB와 포트에서 구성한다. Express/SQLite는 비교용으로 보존한다. 프론트의 API 주소를 환경별로 명시하고 한 실행에서 우연히 두 API를 섞지 않는다.
3. **W04의 첫 작은 흐름:** 새 DB migration → 테스트 전시/작품 → 공개 목록/상세/추천 → React에서 같은 fixture 표시. 계약상 의도적 공개 제한은 차이표에 쓴다. 운영 seed나 자동 승인으로 연결 성공을 만들지 않는다.
4. **W05:** 콘텐츠/검수 → 추천 → 인증/도슨트 맥락 → 기록 → 실제 데이터 이전 순으로 넓힌다. 각 단위에서 API 검사와 관련 화면을 함께 확인한다. W04의 부분 연결은 전체 서비스 전환 완료가 아니다.
5. **전체 개발 전환:** 회원/관리자 로그인, 업로드/조회, 검수, 추천, 대화, 기록, 실패 안내가 대상 API에서 동작하고 데이터 이전 정책이 확인되면 기본 개발 실행을 Django로 바꾼다. 이 시점에도 AWS 공개 릴리스는 별도 게이트다.
6. **기존 코드 정리:** 대응 기능·검사·문서가 새 API로 옮겨졌음을 확인한 뒤 Express 실행 경로와 중복 의존성을 제거한다. 이전 Git 기준점과 필요한 데이터 원본을 보존한다. 두 API에 같은 기능을 각각 완성하지 않는다.

전환 실패 시 환경별 API 설정과 코드 diff를 되돌리고 개발 DB를 분리해 원인을 확인한다. 코드 복귀가 DB 복구라는 뜻은 아니다. 실제 자료에 대한 파괴적 migration은 AC17 보존 판단과 복원 증거 전에는 수행하지 않는다.

## 공수·범위와 검증 루프의 운영

- 현재는 1인 통합 개발을 기본으로 한다. 팀 자료 준비는 실제 회신 전까지 가용 공수로 계산하지 않는다.
- W02는 계약 목록/개발 결정/예시·회귀 매핑의 세 묶음으로, W04는 모델·migration/첫 흐름/Compose의 세 묶음으로 나눠 진행한다. W05는 기존 다섯 단위를 유지한다.
- 각 묶음 착수 시 예상 집중 작업 회차와 가장 큰 불확실성 하나를 기록하고, 끝나면 실제 작업 시간과 대기 시간을 분리한다. 회차는 통상 2~4시간 분량으로 나누되 이는 전체 공수 약속이나 자동 중단 기준이 아니다. 첫 두 묶음 실측 후 남은 범위를 다시 추정한다.
- 같은 실패가 두 번이면 기존 루프대로 전제를 재검토한다. 환경 문제에는 환경만, 계약 문제에는 관련 계약/fixture만 고친다. 통과 기준을 낮추거나 관계없는 재설계를 늘리지 않는다.
- 시연 일정이 부족하면 F21 고급 알고리즘·추가 UX 등 선택 범위부터 제외 검토한다. 승인 근거, 기록 정확성, 대화 격리, 핵심 여정, 필수 검증을 임의로 면제하지 않는다. 시험 시연과 공개 서비스는 구분한다.

영향받는 AC/gate의 과거 pass를 그대로 승계하지 않는다. execution.json 상태를 재검증 전 not_run으로 조정하고, 선행 조건 때문에 함께 무효화되는 완료 과업/후속 게이트도 정합하게 조정한다. 이전 증거는 삭제하지 않고 새 변경과 유효 범위를 설명한다. 단순 문구 수정만으로 실제 서비스 시험을 반복하지 않는다.
