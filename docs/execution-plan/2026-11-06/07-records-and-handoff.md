## 실행 기록 양식

파일은 records/ 아래에 작업별로 추가한다. 아래는 양식이며 실제 실행 결과가 아니다.

- 기록ID / 날짜(KST) / W-ID / F-ID / AC-ID
- 구현자 / 검토자 / 동일인 여부
- 기준 커밋 / 변경 커밋 / 프론트ZIP 기준 / 환경·버전
- 입력 데이터·fixture·모델·프롬프트/보정 버전
- 사전에 정한 기대 결과와 통과 기준
- 실행 명령·실제 결과·종료코드·상태코드
- 증거 파일/Actions run/민감정보 제거 여부
- 판정: pass/fail/not_run/blocked
- 실패 원인 / 수정 내용 / 영향받는 재검증 범위
- 다음 작업 / 외부 의존 / 남은 위험

## 결정 기록 양식

- D-ID / 상태(제안·결정·변경·폐기) / 일자 / 결정 주체
- 해결할 문제와 관련 W/F-ID
- 검토 대안과 현재 선택
- 선택 이유·일정/비용/복잡도·자료 근거
- API/데이터/프론트/운영 영향
- 기존 결정의 대체 범위
- 검증 방법 / 되돌릴 조건 / 미결 항목

## 상태 갱신 규칙

실행상태의 단일 기준은 execution.json이다. 사람이 보는 문서와 함께 갱신한다. task: planned/in_progress/blocked/complete, issue: open/in_progress/blocked/accepted_deferred/closed, AC/gate: not_run/pass/fail/blocked.

task complete에는 연결된 필수 AC pass가 필요하다. gate pass에는 모든 AC pass·증거·검토기록이 필요하다. issue closed에는 해결 커밋/증거와 연결 AC pass가 필요하다. 중요한 구현 변경 후 관련 AC는 재검증 상태로 돌리고 이전 pass 로그는 삭제하지 않는다.

문서 구조 검사 스크립트는 ID·연결·파일·상태의 형식적 조건을 검사한다. 실제 서비스 동작과 증거 내용의 진실성은 검증단이 확인한다.

## 매 작업 회차 시작/종료

시작: 최신사용자지시→현재결정→작업상태→선행게이트→관련이슈/AC→변경공간 확인 순으로 읽는다.

종료: 변경커밋·실행증거·실패·이슈상태·미결결정·다음명령을 기록한다. 서비스 비밀·사용자 전체 채팅·모델가중치를 기록에 복제하지 않는다.

다음 작업자가 답할 수 있어야 할 질문: “현재 어디까지 실제로 통과했는가?”, “어떤 결함/결정이 열려 있는가?”, “어떤 환경에서 무엇을 실행하면 재현되는가?”, “다음 한 작업은 무엇인가?”
