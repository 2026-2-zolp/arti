# 자체 검증단과 단계별 통과 기준

## 검증단 구성

검증은 작성자의 “잘 된 것 같다”는 판단만으로 닫지 않는다. 아래 역할로 분리해 증거를 검토한다. 팀 인력에 맞게 한 사람이 여러 역할을 맡을 수 있으나 구현자와 검토자 동일 여부를 기록한다. AI 검토는 보조이며 실제 환경·사람 검수를 대체하지 않는다.

| 역할 | 점검 관점 |
| --- | --- |
| 정합성 | ARTI 목적·회의 합의·사용자 지시·설계와 구현의 일치, 범위 과잉 |
| 기술 | API·상태·타입·인증·회귀·전환 호환성, 이중 구현 |
| 데이터 | 출처·검수·식별자·관계·저장·이전·복구 |
| AI | 실제 호출 여부, 근거·유보·대화·평가 분리·자원 |
| 사용자 | 모바일 관람 완주·오류·재진입·이미지 저장·관리자 사용 |
| 운영 | Docker·AWS·CI/CD·환경·비밀·로그·지연·비용 |

이번 문서 제작에는 작성자와 별도로 **범위/정합성 검토, 기술/운영 검토**를 수행하는 보조 검토자를 둔다. 검토 결과는 [문서 검토 기록](08-document-review.md)에 기록한다. 실제 팀원의 승인이나 서비스 게이트 통과로 표현하지 않는다.

## 판정 규칙

- AC 판정은 not_run(미실행), pass(통과), fail(실패), blocked(외부 입력 대기)로 관리한다.
- 각 게이트의 **필수 AC 전부가 pass**이고 증거가 있어야 게이트 pass다. 평균 점수·다수결로 필수 실패를 상쇄하지 않는다.
- 코드 존재·테스트 fake·저장된 노트북 출력·문서 검사 통과로 실제 모델/브라우저/AWS 검증을 대신하지 않는다.
- N/A는 조용히 사용하지 않는다. 예: 운영 DB 부재는 AC17의 부재 확인 경로로 검증한다. 기능 범위 변경은 결정 기록·영향 검토·해당 기준의 새 버전을 남긴다.
- 판정에는 커밋/환경/입력/기대/실제/로그/검토자/날짜가 있어야 한다. 비밀·개인정보는 제거한다.
- 기존 코드의 알려진 실패를 조사 단계에서 재현한 것은 AC06 통과 근거가 될 수 있다. 그 결함의 해결을 요구하는 AC11~AC16은 여전히 통과할 수 없다.

## 게이트별 필수 기준

### AC01 · G0 · W01

**기준:** 정식 소스·ZIP·SHA·변경 목록과 실행 버전이 기록되고 원본이 보존됨。

**필수 증거:** baseline.md 및 소스 diff / 검토 역할: 정합성 / 현재: 미실행.

### AC02 · G0 · W01

**기준:** 빌드/타입/기존테스트 및 결함 재현을 새 작업 공간에서 실행하고 데이터 존재 여부 확인。

**필수 증거:** 명령·종료코드·로그/재현표 / 검토 역할: 기술 / 현재: 미실행.

### AC03 · G1 · W02

**기준:** 8태그·10점5쌍·빈도·수정 취향·4종 콘텐츠·검수·ID·좌표의 정상/실패 예시가 일치。

**필수 증거:** 계약 예시·대조표 / 검토 역할: 정합성 / 현재: 미실행.

### AC04 · G1 · W02

**기준:** 스택·인증·모델위치·AWS범위/예산·지원모바일·지연예산을 결정하고 미결의 영향 격리。

**필수 증거:** 결정기록·담당·수치/조건 / 검토 역할: 운영 / 현재: 미실행.

### AC05 · G1 · W02

**기준:** 모든 이슈에 수정 위치·담당·검사 연결, 이중 구현 방지 경계 명시。

**필수 증거:** 이슈 추적표·작업계획 / 검토 역할: 기술 / 현재: 미실행.

### AC06 · G2 · W03

**기준:** 알려진 결함의 재현 입력/기대/실제 결과가 있고 조사 내부 구현에 과결합되지 않음。

**필수 증거:** 회귀 검사·실패 로그 / 검토 역할: 기술 / 현재: 미실행.

### AC07 · G2 · W03

**기준:** PR CI 실행 성공/실패 증거와 required/탐지 검사 구분, 비밀/유료AI 없이 기본 검사。

**필수 증거:** Actions run·job 정의 / 검토 역할: 운영 / 현재: 미실행.

### AC08 · G3 · W04

**기준:** 합의한 API fixture를 대상 API에서 검증, 기존 결함 수정은 의도적 차이로 명시。

**필수 증거:** 계약 검사·차이표 / 검토 역할: 기술 / 현재: 미실행.

### AC09 · G3 · W04

**기준:** Postgres 빈DB migration·동일fixture 재적재·ID/JSON/null/날짜/관계 제약 확인。

**필수 증거:** DB 검사 로그·모델/migration / 검토 역할: 데이터 / 현재: 미실행.

### AC10 · G3 · W04

**기준:** Compose 새 환경 기동·DB준비·재시작 후 DB/파일 보존, 키 없는 설정 예시 재현. 운영모드에서 데모 자동시드·고정 관리자 자격이 생성되지 않음。

**필수 증거:** 시작/재시작 로그 / 검토 역할: 운영 / 현재: 미실행.

### AC11 · G4 · W05

**기준:** 생성→별도항목수정→저장→재조회 후 guide/summary/tag/emotion의 값·검수 상태 보존. 승인 원문/출처 버전 변경 시 기존 summary/guide를 stale 또는 확정해제로 처리하고 공개/AI근거에서 제외, 재검수 후에만 재노출。

**필수 증거:** API round-trip와 화면 증거 / 검토 역할: 데이터 / 현재: 미실행.

### AC12 · G4 · W05

**기준:** pending/source_check 작품 및 suggested AI필드가 공개 목록·상세·질문·해설에서 차단되고 관리자만 미리보기。

**필수 증거:** 상태 조합 API 검사 / 검토 역할: 데이터 / 현재: 미실행.

### AC13 · G4 · W05

**기준:** 취향/시간/전시 변경시 추천·진행 상태 정책 적용, 늦은 응답이 최신 결과를 덮지 않음. 고정 선택·반대 빈도·사용자수정 예시의 기대 프로필/점수/추천근거가 계약과 일치하고 선택 원본 저장·재조회 일치. 추천 목록이 반드시 달라야 한다는 조건은 사용하지 않음。

**필수 증거:** 경합 검사·화면 기록 / 검토 역할: 사용자 / 현재: 미실행.

### AC14 · G4 · W05

**기준:** 같은 visit 중복POST/재시도로 1건 저장, AI실패와 무관하게 기록 저장·재조회, 합의필드 보존。

**필수 증거:** DB건수·재시도/오류 검사 / 검토 역할: 데이터 / 현재: 미실행.

### AC32 · G7 · W10

**기준:** 작성자 외 검토자가 문서만으로 실행·등록검수·배포/복구 절차를 따라 확인。

**필수 증거:** 독립 재현·인수 기록 / 검토 역할: 정합성 / 현재: 미실행.


AC31은 릴리스 종결의 최종 집계 기준이다. releaseRequired=true 이슈의 종결 선행 AC에 AC31 자체를 넣지 않는다. 먼저 개별 해결 기준을 통과하고 이슈를 종결한 다음 AC31에서 최종 집계한다.

## 통과할 때까지의 루프

1. 착수 전에 AC와 입력·판정 방법을 고정한다.
2. 구현/문서 변경 → 필요한 검사 실행 → 증거 수집 → 담당 검토.
3. 실패하면 원인을 환경/계약/구현/데이터/모델/범위로 나누고 가장 작은 수정으로 해결한다.
4. 해당 AC와 영향받는 인접 AC를 재실행한다. 모델·DB·인증·배포 경계 변경 시 관련 전체 흐름도 재검증한다.
5. 필수 AC가 모두 통과할 때만 다음 의존 단계의 완료를 허용한다.
6. 같은 실패가 두 차례 수정 후에도 반복되면 독립 검토자가 전제와 접근을 다시 본다. 기준을 낮추지 않고 수정 방식을 바꾸거나 명시적 결정으로 범위를 재설계한다.
7. 키/입력/권한 부족은 blocked로 남기고 독립 과업만 진행한다. 시간 경과는 통과 증거가 아니다.

W08처럼 조기에 준비 가능한 작업은 “일부 준비” 상태로 진행할 수 있다. G6 최종 통과는 W09의 CI/CD·복귀까지 확인해야 한다. 전체 납품 완료는 G0~G7 전부 통과한 뒤다.

AI 품질의 정성 문항은 W02/W06에서 합격·불합격 예시를 고정하고 AC19에 보존한다. AC21의 잘못된 작품/가짜 출처/미검수 근거 0건은 해당 고정 질문셋 범위의 필수 기준이다. 모집단 무오류를 보장한다는 표현은 사용하지 않는다. 지연·태그 품질 목표는 측정 후 유리하게 바꾸지 않도록 첫 평가 전에 정한다.
