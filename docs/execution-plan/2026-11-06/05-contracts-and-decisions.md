# 계약과 기술 결정

## 사실·권장·미결의 구분

현재 사용자가 확정한 것은 구현 착수 전 상태, 최신 ZIP·광권 코드 기준, AWS 고려, CI/CD 포함, 독립된 실행 문서 및 검증 루프다. Django는 원설계와 프로젝트 특성을 고려한 **권장안**이다. RDS·S3·EC2·FastAPI 운영 방식·인증 방식은 최종 채택 완료로 기록하지 않는다.

기존 아카이브의 “목표 스택 원설계 복귀”라는 계획 문구는 역사 기록으로 남긴다. 현재 실행에서는 D01의 채택 결정을 먼저 기록한다. 미정 상태에서 서로 다른 구현을 병행하지 않는다.

## 핵심 계약 초안

아래 새 필드는 **제안이며 현재 API에 존재한다고 뜻하지 않는다**. 실제 타입 이름/필수 여부/호환 방식은 W02에서 확정한다. 전체 기존 호출은 [조사 대조표](../../project-baseline/2026-11-06/07-contract-baseline.md) 참조.

| 영역 | 현재 | 필요한 명세 |
| --- | --- | --- |
| 취향 | 최대6태그만 반환, 서버 최대8 수신 | 선택풀ID·버전·선택작품ID·빈도·사용자수정 결과. 태그강도0~1과 빈도는 별개 |
| 추천 | exhibitionId/tastes/duration → 목록 | 입력 프로필/버전에 결과 연결, 변경/빈결과/동률/시간별수량·후보부족 정책 |
| 작품 | description/source/referenceUrl + 검수상태 | 작품 승인과 AI필드 confirmed 별도. sourceID/버전·공개 DTO/관리자 DTO 구분 |
| 가이드 | front guidedLooking만, backend guideIntro/guidedHints/guideStatus 추가 | 생성응답 병합·저장필드·version충돌 검사. 원문 수정시 기존 AI산출물 stale 처리 |
| 대화 | artworkId/question → answer | visit별 history 제한, mode/model/sourceIds/유보·오류, 승인자료만 사용 |
| 영수증 | 회원POST 저장, 이유/dwell/선택원본 누락 | 필요한 필드·visitId 중복방지·서버저장상태·AI해석 별도 재시도 |
| 인증 | user/admin 토큰 별도, scrypt | 선택된 새 방식·401·logout·callback·타인 접근·해시/세션 전환정책 |
| 파일 | 서버로컬 filename | 저장객체키와 제공URL 분리, S3제한열람·만료·모델접근·삭제 |
| 장시간분석 | HTTP 요청 안에서 대기 | 동기유지/작업ID 선택, 상태 pending/running/succeeded/failed와 재시도/중복방지 |
| 지도 | xy0~100 / 도면픽셀 width,height | 서로 바꾸지 않음. 경로·이동시간 의미·실제축척 유무 |

태그8: landscape/people/abstract/light/vivid/cool/warm/soft. 감정6: calm/joy/sadness/tension/awe/nostalgia. light는 평균 밝기만을 뜻하지 않는다. 기존 평가의 의미를 바꾸려면 새 라벨·평가가 필요하다.

## 스택 전환의 안전한 경계

1. 현재 API와 실패를 먼저 이해한다. 계약을 깨면서 새 API와 프론트를 따로 만들지 않는다.
2. W02에서 채택한 스택에 공개 목록·상세·추천부터 작은 흐름을 만든다.
3. 인증·관리자·기록을 옮기며 필수 결함을 해결한다. Express에서 OAuth/Postgres/전체RAG를 먼저 완성하지 않는다.
4. 외부ID·좌표·태그 의미는 보존한다. 버그로 확인된 미검수 노출·저장 손실은 호환 대상에서 제외한다.
5. 데이터가 있으면 원본·파일을 보관하고 변환/복구를 검증한다. 새 해시 방식으로 비밀번호가 자동 호환된다고 가정하지 않는다.
6. API/DB 경계별로 회귀 증거를 남기고 프론트를 전환한다. 코드복귀와 DB복구가 다른 점을 문서화한다.
