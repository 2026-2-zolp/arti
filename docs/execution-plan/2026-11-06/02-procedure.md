# 단계별 실행 절차

새 작업은 W-ID를 사용한다. 기존 아카이브 T-ID는 당시 계획 식별자이며 현재 완료 상태로 승계하지 않는다. 모든 작업은 아직 미착수다. W02에서 스택 채택을 기록한 후 실제 구현 경로를 고정한다.

## 전체 순서

W01 기준선 → W02 계약·결정 → W03 회귀·기본CI → W04 선택 스택 기반 → W05 핵심 흐름.

W02 이후 W06 자료 준비를 병행할 수 있다. W04 이후 W08 AWS 첫 배포를 시작한다. W05·W06·W07 실제AI·W08을 완료한 후 W09 CD, W10 실환경 인수로 진행한다.

**의존성의 정확한 기준은 execution.json의 dependsOn이다.** 자료 준비·모델 실험·인프라 조사는 병행 가능하나 필수 게이트는 건너뛰지 않는다.

## W01 기준선과 재현 공간

- 목적: 조사 사본과 실제 개발 소스를 분리하고 재현 기준을 확보한다.
- 선행: 이 문서와 사용자 제공 자료 읽기.
- 절차:
  1. 정식 저장소를 격리된 경로에 확보하고 현재 브랜치·SHA·변경 여부를 기록한다. 기존 작업을 덮어쓰지 않는다.
  2. dev/김광권의 최신 변경과 고정 SHA를 비교한다. 프론트 ZIP과 저장소 프론트의 차이를 목록으로 만든다.
  3. ZIP 기반 프론트와 API를 연결할 통합 브랜치 기준을 만든다. Git에 node_modules·모델 가중치·키·실제 업로드 파일을 넣지 않는다.
  4. 문서화된 Node/Python 버전으로 빌드·타입·테스트와 조사 audit의 주요 사례를 재현한다.
  5. 실제 DB·업로드·계정이 있는지 확인한다. 있으면 이전/복구용 원본을 보관하고, 없으면 “없음”을 확인한 사람·시점을 기록한다.
- 산출물: 기준선 기록, 변경 파일 목록, 실행 명령·로그, 기존 데이터 존재 여부.
- 통과: G0의 AC01~AC02.
- 실패: 버전·환경 오류와 제품 오류를 구분한다. 해결 전 새 구현의 성공 증거로 쓰지 않는다.

## W02 계약과 최소 기술 결정

- 목적: 구현 전에 서로 다른 가정과 중복 작업을 줄인다.
- 선행: W01.
- 절차:
  1. [계약표](05-contracts-and-decisions.md)의 결정 항목을 요청/응답 예시로 구체화한다.
  2. 취향풀·빈도·사용자 수정, 콘텐츠4종·검수, 외부ID·좌표, visitId·저장·AI 모드를 정한다.
  3. Django 채택 여부·인증 방식·모델 실행 위치·AWS 최소 서비스/예산을 결정한다. 사용자/팀의 미확정 사항을 확정 사실로 쓰지 않는다.
  4. Express의 결함을 지금 수정할지, 새 구현에서 수정할지 F별 위치를 정한다. 재현 사례 확보를 우선하며 Express 전체 완주를 전환 선행조건으로 강제하지 않는다.
  5. CI 검사와 실제 모델 평가의 범위, 최소 지원 모바일 환경, 응답 지연 예산을 수치/사례로 미리 정한다.
- 산출물: 결정 기록, API 예시, 필드/상태표, 이슈별 수정 위치·담당 제안, 새 공수.
- 통과: G1의 AC03~AC05. 구현을 좌우하는 미결이 남으면 해당 작업 착수 불가.
- 실패: 자료 충돌의 결정 주체와 필요한 질문을 기록한다. 독립적인 자료 준비를 진행할 수 있다.

## W03 회귀 사례와 기본 CI

- 목적: 현재 실패를 놓치지 않고 이후 전환을 같은 기준으로 검사한다.
- 선행: W02.
- 절차:
  1. F02·F03·F04·F10의 재현 입력/기대 결과를 고정하고 F11~F13의 실제 화면 재현을 추가한다.
  2. private reducer와 폴더 경로에 결합된 조사 harness를 그대로 제품 테스트로 복사하지 말고 공개 기능·API 수준으로 옮긴다.
  3. GitHub Actions에서 프론트 빌드/타입, 현 API 테스트, 모델 계약 테스트를 실행한다. 목표 API가 생기면 Postgres 테스트를 추가한다.
  4. 알려진 결함은 실패 증거로 추적한다. required CI에서 숨기거나 전체 green으로 표현하지 않는다. 결함 전용 탐지 job을 별도로 두면 후속 수정 후 required 검사로 승격한다.
  5. 실제 LLM 키·모델 대용량 다운로드 없이 기본 CI가 동작하는지 확인한다.
- 산출물: 회귀 시나리오, Actions run 링크, 필수/탐지 job 구분.
- 통과: G2의 AC06~AC07. G2는 회귀 체계 마련을 의미하며 제품 결함 해결을 뜻하지 않는다.

## W04 선택 스택과 PostgreSQL·Docker 기반

- 목적: 확정된 구현 경로에서 계약을 유지하는 작은 API를 만든다.
- 선행: W03. W02에서 Django를 채택했다면 다음 절차 적용.
- 절차:
  1. Django/DRF 서비스 골격과 Postgres 모델/마이그레이션을 구성한다. 최소 전시·작품·출처·검수 구조부터 시작한다.
  2. 기존 외부 문자열ID와 좌표0~100, 태그8/감정6의 의미를 유지한다.
  3. 공개 목록·상세·추천을 고정 fixture로 검증한다. 계약과 같아야 하지만 기존 미검수 노출 등의 결함은 재현하지 않는다.
  4. API+Postgres Compose, DB 준비 확인, 업로드/캐시 저장 경로, 환경변수 예시를 구성한다. 실제 비밀값은 넣지 않는다.
  5. 빈 DB 시작→마이그레이션→fixture→조회→재시작을 반복해 영속성을 확인한다.
- Express 유지 결정 시: 같은 계약·Postgres·마이그레이션·검사를 충족하는 대체 작업으로 결정 기록과 계획을 갱신한다. 이 선택을 이미 승인된 사실로 취급하지 않는다.
- 산출물: 골격·모델·migration·Compose·동등성/의도적 차이 결과.
- 통과: G3의 AC08~AC10.

## W05 핵심 관람·관리자·인증·기록

- 선행: W04.
- 절차:
  1. 가이드 생성 응답과 저장을 일치시키고, 미검수 작품/AI 산출물의 공개 노출을 차단한다.
  2. 추천 입력 변경·stale 응답·빈 후보·선택풀 부족·API 오류 화면을 처리한다.
  3. 선택한 인증을 구현하고 401 복구·로그아웃·관람/대화 격리·타인 기록 접근을 검증한다.
  4. visitId로 중복 저장을 막고 AI 해석과 기록 저장을 분리한다. 반응 이유·시간·선택 원본 중 합의한 항목을 저장/재조회한다.
  5. 관리자와 회원 권한을 구분하고 이미지 업로드·검수 상태·미리보기 경로를 확인한다.
  6. 기존 DB가 있다면 원본 보관→변환→개수/ID/관계/상태 검증→복구 연습. scrypt 계정은 검증된 이관/재인증 정책을 따른다.
- 산출물: 통합 코드, 필요 시 데이터 변환/복구 절차, API·화면 증거.
- 통과: G4의 AC11~AC17. 실제 모델 없이 통제된 fixture로 통과 가능하나 G5를 대신하지 않는다.

## W06 공식 자료·선택풀·지도 준비

- 선행: W02. W03~W05와 병행 가능.
- 절차:
  1. 공식 작품ID·연도·치수 등 식별 정보를 수집하고 동명/상충 자료를 분리한다.
  2. 원문·URL·버전/수집일·사람 검수 상태를 기록한다. 자료 사용 가능 범위와 이미지 노출 범위를 확인한다.
  3. 취향풀10점·독립5쌍과 실제 전시 코퍼스를 구분한다. 파일럿3~5점은 최종 코퍼스/선택풀을 대체하지 않는다.
  4. 그림·공식 해설·확정 태그·좌표를 검토한다. 실제 도면 없이는 이동시간/보행최적화를 확정하지 않는다.
  5. 기존40장 평가 입력·라벨·모델/보정 파일을 인계받고 재현 범위를 기록한다. 별도의 전시 표본·질문셋을 고정한다.
- 산출물: 출처·검수 manifest, 선택풀, 전시 fixture, 평가 입력 목록.
- 통과: G5의 AC18~AC19에 필요한 데이터. G5 최종 판정은 W07 후.

## W07 실제 AI 연결·평가

- 선행: W05,W06.
- 절차:
  1. 1개 승인 작품으로 모델 성공/자료 부족/키 없음/오류/timeout을 분리해 검증한다.
  2. 승인 sourceIds만 조회하고 모델이 돌려준 출처ID를 서버에서 검증한다. 사용자·자료 속 지시가 권한/정책을 바꾸지 못하게 한다.
  3. 짧은 최근 대화·visit 단위 격리, 근거 밖 유보, 관찰 유도 질문을 확인한다.
  4. 로컬 태그/감정 모델의 메모리·준비시간·추론시간을 측정한다. Kanana는 유지 실익·자원·외부 LLM 대안을 비교하고 숨은 fallback으로 사용하지 않는다.
  5. 고정 질문셋/전시 표본으로 결과·실패·지연을 기록하고 사람 검토한다. 모델명/버전/보정/프롬프트를 함께 남긴다.
- 산출물: 실제 호출 증거(키 제거), 평가표, 실패 사례, 자원 측정.
- 통과: G5의 AC18~AC22. 입력·키가 없으면 미실행, 다른 독립 작업만 진행.

## W08 AWS 첫 배포와 운영 기반

- 선행: W04. 초기에는 fixture로 검증하며 W05/W07 완료를 기다리지 않는다.
- 절차·산출물: [운영 문서](06-operations.md)의 계정/예산→API·RDS→미디어→모델→공개주소→상태·복구 순서.
- 통과: G6 중 AC23~AC26. 실제 AWS 자원 연결 결과가 필요하며 Compose 성공으로 대체하지 않는다.
- 주의: 실제 리소스 생성은 비용·계정 범위가 정해진 뒤 수행한다. 현재는 미생성. W05 이전 환경은 접근을 제한하고 실제 사용자자료·알려진 데모/관리자 계정을 노출하지 않는다. 운영 빈DB의 자동시드를 차단하고 초기관리자는 별도 안전한 절차로 생성한다.

## W09 CD와 배포 검증

- 선행: W05,W07,W08.
- 절차: OIDC→검증된 이미지→마이그레이션 직렬화→배포→상태/핵심API→복귀 검증. [운영 절차](06-operations.md) 참조.
- 산출물: Actions 배포 run, 이미지 digest/커밋, migration 결과, smoke·복구 증거.
- 통과: G6 전체 AC23~AC28. 첫 배포를 전부 자동화하기 전에 동일 절차를 한 번 확인한다.

## W10 실환경 최종 인수·기술 설명

- 선행: W06,W09 및 G0~G6 통과.
- 절차: 두 계정/비회원·새 관람·실패·재진입·모바일·실제 모델·영수증 이미지 저장을 포함해 전체 흐름을 확인한다. 다른 기기 평가가 관리자 서버 조회에 모이는지도 확인한다.
- 산출물: 지원 환경별 인수표, 시연 동선, 실제 스택·DB·AI·알고리즘 설명, 설계 변경·남은 제한.
- 통과: G7의 AC29~AC32. 한 전시 완주·필수 신뢰성·저장 기준에 열린 결함이 없어야 완료다.
