# R04 TP1b — 점수·출처·revision 원자 저장

2026-11-11 / `dev/임준억` / 착수 `41f8fb8`. [TP1a 모델 점수 출처 전달](2026-11-11_R04_TP1a_모델점수출처전달.md)에 이어 사용자가 격리 PostgreSQL의 구조/저장 보호 구현을 승인했다. 일반 개발 DB 변경·공개 활성화·원격 푸시는 하지 않는다. 동섭님 프론트 종합본 재확인은 별도다.

## 맥락과 변경 결과

TP1a는 모델 근거를 전달·검증해도 저장하지 않았다. 동점 보조 점수를 앞으로 사용할 때 점수와 근거의 시점이 엇갈리거나, 재분석 실패가 확정값을 훼손하면 안 되므로 이번에는 저장 경계를 만들었다. 동점 정렬/preview/v2 계정 저장을 구현한 단계는 아니다.

| 변경 대상 | 이전 | 이후 |
| --- | --- | --- |
| Artwork/migration | tag_scores만 존재 | nullable tag_score_evidence, 기본0 tag_score_revision 추가. 기존 모든 열·행/승인/계정/관람/풀은 그대로 |
| 태그 제공자 | 근거를 제외 | 유효한 근거만 태그에 전달. 감정 JSON에는 계속 제외, 구형 응답의 scores 형식은 유지 |
| 분석 저장 | 점수만 변경 | 같은 행 잠금/version 확인/transaction에서 세값 저장. 새 분석은 suggested, 동일 점수 재분석도 revision+1 |
| 구형 서비스 | 근거 구분 없음 | 새 분석에 근거가 없으면 null로 저장. 예전 근거를 새 점수에 붙이지 않음 |
| 과거 입력 근거 | 현재 입력과 구분 불가 | 서버 sourceVersion·파일 token 결합. 원문/이미지 변경 후 과거 근거는 보존하되 현재 근거로 반환하지 않음 |
| 저장 실패/경합 | 기존 version 보호 | 점수/근거/revision도 함께 보호. 잠금2초초과503·낡은 version409·commit 직전 예산 소진 rollback 추가 |

주 변경 파일은 Django `models.py`, 신규 `0003_tag_score_evidence.py`, `providers.py`, 신규 `tag_scores.py`, `editing.py`다. `test_tag_persistence.py`를 추가하고 TP1a 전달 시험의 태그 반환 기대값을 새 계약에 맞췄다. 운영 문서에는 저장 형식·이관·일반환경 미반영·rollback 경계를 추가했다. 공개/관리자 DTO에는 내부 근거를 추가하지 않았고 모델 서비스·프론트·설정·추천 로직은 변경하지 않았다.

저장 근거는 원래 모델 envelope 8필드와 서버의 sourceVersion/inputImageFile이다. 원래 모델 checksum은 envelope만 대상으로 한다. 사람 confirm·승인 signature 허용은 별개이며, 클라이언트는 점수·근거·revision을 쓸 수 없다. 같은 파일 token을 수동 덮어쓰지 않고 기존 새 파일명 업로드 구조를 따른다.

## 검증과 보완 루프

1. 별도 `arti-tp1b-20261111-db`와 전용 loopback 포트·tmpfs를 만들었다. 일반 `arti-dev`의 DB/API 컨테이너·볼륨은 공유하지 않는다. 모델 URL/키를 비우고 LLM은 disabled로 실행했다.
2. 신규15건이 실제 PostgreSQL에서 통과했다. 서로 다른 연결의 중간값 관측, save 뒤 예외 rollback, 같은 version의 두 완료 분석200/409, 모델 실행 중 원문 수정/confirm409, 기존 확정값·구형 null·클라이언트 주입 차단을 확인했다.
3. 기술/시니어와 운영/데이터 관점에서 전체8점수 없는 근거를 거절하고, 분석 저장 transaction 한정 lock_timeout2초와 commit 직전 예산 확인을 추가했다. 실제 HTTP timeout/늦은 응답과 기존 활성/비활성 풀 이관 사례도 보강했다.
4. 전체 회귀1회차137건 중 기존 이미지2건이 Windows 파일 핸들 정리에서 실패했다. 처음에는 response.close를 cleanup에 등록했으나 Django TestCase의 DB 연결까지 닫아 다음 시험12건에 영향을 줬다. 설치된 Django 클라이언트의 closing_iterator_wrapper를 확인하고 다운로드 스트림을 정상 소비/내용 검증하도록 수정했다. 해당2건 통과 후 전체를 다시 검증했다. 제품 파일 반환 코드는 수정하지 않았다.
5. 비공개 시험 실행기의 출력 인코딩도 UTF-8로 수정했다. 이는 제품/공개 코드 변경이 아니다. 최종 건수와 결과는 아래 실행 기록의 tests/validation에 남긴다.

범위 보완으로 기존 이미지 시험2파일에 스트림 소비를 추가했다. 앞선 파일 정리 오류를 무시하거나 테스트를 제외하지 않았다. 기존 부분 성공 정책은 유지해 tag 실패에도 독립적인 요약 성공은 저장하되 태그 묶음은 유지한다. 전체 예산 초과는 모든 결과를 저장하지 않는다.

검증단은 기술/시니어·방문자·운영/데이터·팀·교수/제3자 평가위원의 **같은 작성자 역할별 자체 검토**다. 독립 인적 검수는 아니다. 사용자가 보는 상태와 내부 확정/출처를 분리하고, 모델 품질·최종 조사 선정·공개·실제 가중치 인수를 기술 시험 통과로 오인하지 않도록 확인했다.

[TP1b 실행 기록](../execution-plan/2026-11-07/records/taste-tie-implementation-results-2026-11-11/TP1b/README.md)에 B1~B6·실제 시험 원수·이전 기록/소스 보존·일반환경 경계를 연결했다. 원래 계획/TP1a 아카이브를 수정하지 않고 현재 진척은 실행 기록과 R04 계획에 누적한다. 공식 W/G/AC 상태는 승격하지 않는다.

최종 판정: **B1~B6 통과**, 전체 Django **138건(신규18)**·기존 스크립트 **53건** 통과. 시스템 검사/미작성 migration 차이는 없다. timeout/늦은 응답 합성 HTTP 서버의 예상 ConnectionAbortedError 진단은 남지만 시험 실패는 아니다. 일반 개발 환경과 모델/프론트의 변경은 없고 로컬 커밋만 남긴다.
