# 관리자 이미지 분석 선택 전달

- 기준은 `3cc3018`이다. 관리자 단일 작품 화면의 **이미지도 분석**을 끄면 브라우저는 `useImage: false`를 보냈지만 Django는 이미지 파일을 읽고 내부 분석 서비스에 함께 전달했다. 루프백 모의 HTTP에서 이미지 포함 요청과 `usedImage: true`를 재현했다.
- Django가 생략된 `useImage`를 기존 기본값인 `true`로 처리하고, 명시 값은 JSON 불리언만 허용하도록 수정했다. `false`에서는 작품 제목과 승인된 해설 원문만 내부 태그·감정 분석에 보낸다. 작품에 등록한 파일이나 외부 이미지 주소는 조회하지 않는다. `true`와 생략은 기존 로컬 이미지 분석 경로를 사용한다.
- 같은 요청에서 태그와 감정이 공유하던 응답 캐시는 그대로 요청 단위다. 이미지 선택을 바꿔 새 요청을 보내면 새 입력으로 분석한다. 요약·가이드 생성은 기존 승인 원문을 사용한다. 텍스트 전용 요청에 이미지 사용을 주장한 태그·감정 응답은 `PROVIDER_ERROR`로 거절한다.
- 합성 검수는 `useImage` 생략 → `false` → `true` 순으로 실행한다. 분석 제공자에 도착한 이미지 바이트와 요청 수, 요약·가이드 요청이 일치하는지, 새 분석 저장 시 원문 버전과 등록 이미지가 보존되는지 비교한다. 누락된 이미지, 외부 주소, 잘못된 플래그와 모의 응답의 이미지 사용 주장도 검사한다.
- 전용 PostgreSQL에서 새 이미지 선택 회귀와 기존 모델 장애·버전 충돌·태그 저장 회귀를 합쳐 34개가 통과했다.

## 관리자 Chrome 전송 대조

`9111fb1` 기반 수정본의 프로덕션 프론트와 별도 합성 PostgreSQL을 사용했다. 기존 관리자 두 탭 시험에서 구버전 분석의 409, 미저장 입력 보존, 최신 원문으로 다시 분석한 200을 확인한 뒤 같은 작품의 체크박스를 전환했다. 모의 제공자는 수신한 제목·원문·디코딩한 이미지의 SHA-256을 기록한다.

| Chrome 조작 | 모의 제공자가 받은 항목 | 관리자 화면 |
| --- | --- | --- |
| 켜기 | 제목·해설·`imageBase64`. 디코딩한 이미지가 업로드한 PNG와 일치 | 이미지 + 해설 |
| 끄기 | 같은 제목·해설. 이미지 바이트와 URL 필드 없음 | 해설 |
| 다시 켜기 | 같은 제목·해설과 첫 실행과 같은 이미지 바이트 | 이미지 + 해설 |

각 선택은 모의 분석 요청 한 번과 Django 응답 200을 확인했다. 확정 요약·원문 버전·등록된 도판은 유지됐다. 반환 결과의 `usedImage`와 `tagSource`도 각 선택과 일치했다. 프로덕션 빌드와 같은 Chrome 시나리오의 연속 두 회가 통과했다. 기존 [관리자 Chrome CI](../../.github/workflows/ci.yml)의 충돌 회귀에서 이 전환을 다시 실행한다. 실제 모델 호출과 실기기 검증은 보류했다.

