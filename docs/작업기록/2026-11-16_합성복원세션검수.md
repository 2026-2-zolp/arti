# 11/16 합성 백업 복원과 세션 범위 검수

회원 영수증 한 건이 든 합성 PostgreSQL을 복원할 때 원본 세션도 함께 복제되는지 확인했다. ARTI는 요청 토큰의 SHA-256 해시를 `arti_session`에서 조회하고 만료 시각, 활성 계정 상태와 회원·관리자 역할을 대조한다. 복원 전에 발급된 토큰은 원본 DB와 함께 복사된 세션 행으로 복원 후보에서도 인증될 수 있다. [인증 코드](../../backend-django/arti/authentication.py) · [복원 운영 결정안](../operations/W12_운영구성과예산결정안.md)

## 재현 순서

1. `f18bc0a`의 이미지와 [합성 배포 전 검사](2026-11-16_운영형배포전검사.md)를 사용한다. 원본과 후보에 각각 새 Compose 프로젝트, PostgreSQL·미디어 볼륨, 루프백 Nginx를 사용한다. 원본과 후보의 `pg_control_system().system_identifier`가 다른지 확인한다. 운영용 DB 연결 정보와 실제 계정은 쓰지 않는다.
2. 원본에 합성 회원의 영수증 1건·반응 1건을 저장한다. 회원 토큰은 회원 영수증 `GET /api/visits/{id}`의 Bearer 인증에, 관리자 토큰은 관리자의 `GET /api/admin/visits/{id}`에 `X-Admin-Token`을 사용한다. 두 토큰을 덤프 생성 전에 발급하고 영수증 본문을 비교한다. 인증 값은 셸 메모리에 보관한다.
3. 원본 웹을 잠시 닫고 `pg_dump`와 미디어 사본을 만든다. 원본 웹을 다시 기동한 뒤 후보의 빈 DB로 `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`을 실행한다. 후보에서 신규 로그인 전에 원본 토큰 두 개로 같은 회원·관리자 경로를 읽는다. 후보에서 새 로그인으로 두 역할의 토큰을 발급해 같은 영수증을 읽고, 후보에서 발급된 토큰은 원본에서 각각 401인지 확인한다.
4. 현재 후보가 위 합성 DB이며 클러스터 식별자가 원본과 다름을 다시 확인한다. `CANDIDATE_SYSTEM_ID` 자리에 확인한 후보의 숫자 식별자를 넣고 SQL을 `$deleteSql`로 준비한다. 후보 인수인 `@restore`로 `docker compose @restore exec -T db psql -U arti -d arti -v ON_ERROR_STOP=1 -tAc $deleteSql`을 실행해 합성 세션 수를 대조한다.

   ```sql
   with cleared as (
     delete from arti_session
     where (select system_identifier::text from pg_control_system()) = 'CANDIDATE_SYSTEM_ID'
     returning 1
   ) select count(*) from cleared;
   ```

5. 후보에서 원본 발급 및 후보 발급 토큰이 모두 401인지 확인한다. `docker compose @restore restart api`로 후보 API만 재시작하고 같은 토큰을 다시 검사한다. 후보에서 재로그인한 회원·관리자의 영수증과 원본 토큰으로 읽은 영수증을 비교한다. 두 프로젝트의 계정·영수증·반응과 합성 미디어 해시도 대조한다.

## 확인 결과

`f18bc0a`를 아카이브한 실행 `arti-preflight-15f6861ee087`은 Docker 28.1.1, Compose 2.35.1, PostgreSQL 17에서 통과했다. 배포 전 검사기의 임시 복제본으로 원본 웹을 백업 뒤 다시 열었고, 별도 후보 API만 재시작해 아래를 확인했다.

| 시점 | 복원 후보 | 원본 |
| --- | --- | --- |
| 복원 직후 | 덤프에서 돌아온 세션 2건. 원본에서 발급한 회원·관리자 토큰이 각각 200과 같은 영수증 본문을 반환했다. | 원본 회원·관리자 토큰 모두 200이었다. |
| 새 로그인 뒤 | 후보에서 새로 발급한 회원·관리자 토큰도 각각 200과 같은 본문을 반환했다. | 후보에서만 발급한 회원·관리자 토큰은 각각 401이었다. |
| 후보 세션 폐기·후보 API 재시작 | 합성 세션 5건을 폐기했다. 폐기 직후와 재시작 뒤 원본 발급·후보 발급 토큰은 모두 401이었고, 재시작 뒤 세션은 0건이었다. | 원본 발급 회원·관리자 토큰은 200으로 같은 영수증을 열었다. 계정 2개·영수증 1건·반응 1건·세션 2건과 미디어 해시가 일치했다. |
| 후보에서 재로그인 | 새 회원·관리자 토큰으로 같은 영수증 ID·본문을 200으로 확인했다. 계정 3개·영수증 1건·반응 1건과 미디어 해시는 유지됐고 신규 세션 2건이 생성됐다. | 이때 후보에서 발급한 토큰도 각각 401이었다. |

시험 전용 Compose 컨테이너·네트워크·볼륨·이미지 태그와 임시 검사본이 정리됐음을 확인했다.

## 운영 검토

- 대상 공개 전에 세션 유지 또는 재로그인을 운영 담당이 결정한다. 복원본의 기존 세션을 폐기하는 방식을 택하면 승인된 대상 DB 확인, 세션 폐기, 재시작 뒤 401, 새 로그인 뒤 200, 원본 조회 유지까지 확인 항목에 넣는다.
- 이번 시험은 합성 Compose와 API 헤더 인증을 사용했다. 브라우저의 주소별 로그인 정보가 자동으로 옮겨지는지, 실제 계정·운영 DB의 세션 정책, 백업 파일 보존·공개 범위는 시험 범위 밖이다. 토큰과 영수증 원문은 결과 파일에 남기지 않았다.
