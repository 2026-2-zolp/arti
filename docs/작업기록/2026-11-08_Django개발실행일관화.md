Compose는 Django를 명시했으나 단독 Vite의 기본은 Express4000이었고 관리자 경로도 별도 설정에 의존했다. 같은 소스를 다른 API로 실행할 수 있어 공통 apiTarget, Vite 환경 로딩, client 관리자 경로를 맞췄다. 이제 추가 설정 없는 호스트 실행도 Django4018을 사용하며 Express는 명시적으로 선택한다.

주요 파일은 frontend/src/lib/apiTarget.ts, vite.config.ts, src/api/client.ts, tests/apiTarget.test.mts, .env.example이다. dev/preview 프록시와 브라우저 target이 같은 규칙을 사용하고, 오타·빈 target·부적절한 origin은 거부한다. preview의 빌드 target/API_BASE가 현재 설정과 다르면 재빌드를 요구한다. 서버 환경 전체를 주입하거나 자동 fallback을 추가하지 않았다.

현재 진입점으로 docs/개발실행-Django.md를 추가하고 루트·프론트·API·처음 시작·Windows 안내를 연결했다. 검증단이 발견한 API README의 옛 Express 기본 설명과 프론트 README의 기존 실행 절차를 현재 기준과 legacy로 구분했다. Python 초기화 도구 조건도 명시했으며 과거 자료와 기존 백엔드는 삭제하지 않았다.

검증: 프론트17건·타입·Django/Express 빌드 통과. Linux Node22에서도 깨끗한 설치 후17건·타입·빌드를 통과했다. 실제 호스트에서 회원 로그인→추천/지도/작품→3점 영수증 저장 후 Compose 회원 화면에서 같은 기록을 재조회했다. 양쪽 관리자 로그인, Compose 미검수 작품/보호 이미지, preview, 설정 불일치 거부, Django 중단 시 오류→복구 후 재시도를 확인했다. AI503과 입력 보존을 확인했으며 실제 GPT 키는 사용하지 않았다.
