## 배경과 변경 전후

새 도구는 전시·작품ID/recordId/assetId·SHA256·근거/초안 manifest를 받아 사전검사→명시 신규 생성만 수행한다. 파일 변조/탈출/중복·기존ID/미디어·승인/좌표 필드 주입은 거절한다. 전시는 draft, 작품은 source_check·이미지 노출false·태그/감정 미생성·좌표null이며 요약/가이드는 suggested로 둔다. 여러 전시와 같은 제목의 다른 작품을 분리해 보존한다. 파일 회수는 이번 호출이 만든 파일에 한정하고 기존 자료는 덮어쓰지 않는다. [계약](../operations/전시자료_비공개인수_v1.md)에 제한과 실패 복구 경계를 기록했다.

## 검증·보완 루프

초기 PostgreSQL77회귀 통과 후 자체 기술/SENIOR 시각에서 DB commit 후 stdout 실패가 이미지 정리로 이어질 위험을 발견했다. 출력은 실패 정리 범위 밖으로 옮겼고 재현 회귀를 추가해 최종78/78 통과했다. Django check 정상·makemigrations --check --dry-run 변경 없음. CI는 기존 arti.tests discovery에 새 회귀가 포함되는 구조이며 원격 실행/푸시는 하지 않았다.

일반 앱 API 정지→실제 arti-dev DB/미디어 사전 보존→dry-run 무변경→명시 적재→API 재기동 순으로 진행했다. 전시1·작품3, 계정/세션/관람/반응0. 공개목록0·작품/이미지404·관리자 API/이미지200·제안상태 유지·재적재 차단·재시작 후 행/파일 해시 동일을 확인했다. 관리자 읽기는 내부 메모리 principal 검사이며 실제 관리자 계정/로그인은 생성/검증하지 않았다. private의 사전 dump/media 세트는 보존하고 새 실백업 자체의 재복원은 하지 않았다. 이전 합성 복원 시험과 구분한다.

팀 시각에서는 안정ID/과거표 보존, 교수/평가위원 시각에서는 시연 재구성/미확정 표시와 과장 방지, 방문자 시각에서는 구체 관찰/열린 질문/도슨트 맥락, 기술/SENIOR 시각에서는 예외·출력 실패·충돌/공개 격리를 자체 점검했다. 동일 작업자의 페르소나별 자체 검토이지 독립 팀원/교수 승인으로 표시하지 않는다. [단계별 자체 검토·집계/해시/API 실행 증거](../execution-plan/2026-11-07/records/W06/core3-intake/README.md).
