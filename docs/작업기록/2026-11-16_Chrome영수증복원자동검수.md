# 운영형 복원에서 Chrome 영수증 검수

`runOpsPreflight.ps1`에 `-ChromeReceipt`를 추가했다. `source-receipt`에서 실제 Chrome으로 합성 전시의 회원가입, 취향 V2 비교 5쌍, 30분 추천, 지도, 작품 3점 감상을 진행한다. 첫 작품의 반응 사유를 선택하고 관람을 마치면 Chrome의 `POST /api/visits` 한 번이 201을 반환한다. 영수증 안에 추천 순서대로 작품 3점이 표시되는지 확인한다. [기존 운영형 검사](2026-11-16_운영형배포전검사.md) · [Chrome 검사](../../frontend/tests/receiptRestore.browser.cjs)

`restored-web-access`에서 기존 API·권한·미디어 검사를 먼저 실행한다. 이어 복원 주소의 새 Chrome 컨텍스트에서 다음을 확인한다.

- 본인은 로그인 후 마이페이지의 영수증 카드 한 건을 연다. 원본과 같은 영수증 ID·관람 ID와 작품 순서·반응 사유를 확인한다. 영수증 직접 주소에서 새로고침해도 상세 API가 200을 반환하고 같은 순서로 표시된다.
- 관리자는 회원 조회에서 해당 회원의 관람 기록 한 건을 선택해 목록과 상세 API의 200 응답 및 동일 ID를 확인한다.
- 다른 회원은 영수증 직접 주소에 로그인해 상세 API 403과 오류 안내를 확인한다. 비로그인 상태에서는 화면이 로그인으로 이동하고 상세 API 직접 조회는 401을 반환한다. 두 경우 모두 영수증 본문을 표시하지 않는다.
- 복원 주소에 보낸 `POST /api/visits`는 0건이다. 원본 및 복원 단계의 `chrome` 보고에는 합성 영수증 ID, 요청·기록 수와 상태 코드가 남는다. Chrome 실패는 검사 단계만 기록하며 비밀번호와 세션, 요청 본문은 저장하지 않는다.

## 실행

기존 검사와 같은 PowerShell 7.3 이상, Docker Desktop/Compose, Node 22, PC Chrome 및 잠금 프론트 의존성을 사용한다. 저장소 루트의 명령에 `-ChromeReceipt`를 붙인다. 해당 플래그를 생략하면 종전 API 영수증 경로를 실행한다. HTTPS 포트가 사용 중이면 빈 루프백 포트를 지정한다.

```powershell
npm --prefix frontend ci --ignore-scripts --no-audit --no-fund
pwsh -NoProfile -File ./scripts/runOpsPreflight.ps1 -Revision fe72c92 -HttpsPort 5627 -ChromeReceipt
```

선택한 `-Revision`은 배포 후보 이미지의 Git 커밋이다. Chrome은 그 커밋에서 빌드한 원본·복원 이미지에 접속한다. 브라우저 검수 코드는 검사기를 실행한 작업본의 파일을 사용한다. 실제 모델 호출과 실기기 검증은 보류했다.

## `fe72c92` 검수 결과

- `arti-preflight-71300a8bf382`의 전체 검사와 정리가 통과했다. 원본 Chrome 저장은 201 한 번이었고 복원 후 동일 ID 한 건을 발견했다. Chrome에서 본인·관리자 `200/200`, 다른 회원 `403`, 비로그인 `401`, 새로고침 `200`과 추가 저장 요청 0건을 확인했다.
- 기존 복원 검사에서 PostgreSQL DB·미디어 복원, 후보 마이그레이션 실패, 동일 Nginx의 API 복구, 모의 HTTPS 카카오 콜백 `302/502`도 통과했다.
- 공유한 취향 비교·추천 헬퍼로 기존 `receipt-session` 회귀를 별도 합성 PostgreSQL에서 실행했다. 세션 만료 후 본인으로 재로그인하면 1건이 저장됐고 다른 계정으로 로그인하면 요청이 0건이었다.
