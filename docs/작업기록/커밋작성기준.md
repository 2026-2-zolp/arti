## 참고한 HALIL 사례

로컬 HALIL 저장소의 실제 Git 이력을 읽기 전용으로 확인했다. `5fde3ddb`는 저장소/파이프라인/워커/API/DB와 검사의 변경을 위치·역할별로 설명했고, `aebc186a`는 업로드와 색인 형식 불일치의 원인, 파서 선택 이유, 변경 후 처리, 실측·회귀·배포 조건을 서술했다. 발표자료 커밋들도 실제 교체/이동/유지 대상을 구체적으로 구분했다.

ARTI에는 **왜 바꿨는지 → 무엇을 어디서 바꿨는지 → 이후 동작 → 검증과 한계**의 연결을 적용한다. HALIL의 제목 scope나 다른 프로젝트 규칙을 그대로 옮기지 않는다. 항상 긴 본문을 쓰는 것이 목표는 아니다.

## 제목은 유지

`유형: 한글 작업 요약`을 사용한다. 기존처럼 해당하면 W 번호를 넣는다.

```text
feat: W05 관람 기록 저장과 만료 복구 구현
fix: 관리자 확정 충돌 후 재검토 안내 보완
ci: W11 PostgreSQL·프론트 회귀 검사 자동화
docs: 다음 과업 확인과 커밋 본문 작성 기준 정리
```

## 본문에 담을 내용

1. **배경/목적:** 어떤 문제·요청·선행 작업 때문에 변경했는가.
2. **실제 변경:** 주요 파일/모듈의 역할과 변경 전후 동작을 연결한다. 단순 파일명 목록이나 “개선/정리 완료”만 쓰지 않는다.
3. **검증:** 실제 실행한 검사와 결과·환경을 적는다. 로컬/원격, 가상 응답/실모델, 부분검사/전체 검사를 구분한다. 이전 커밋의 검사 결과를 이번에 재실행한 것처럼 쓰지 않는다.
4. **영향/잔여:** 계약·데이터·설정·재시작 영향이나 남은 검증을 필요한 만큼 적는다. 자세한 맥락은 관련 작업기록 경로로 연결한다.

작은 문서 수정은 2~3문장으로도 충분하다. 기능/DB/통합 변경은 문단과 항목을 써서 변경 범위를 구체화한다. 이번 커밋에 없는 구현, 미래 작업, 다른 커밋의 성과를 포함하지 않는다. 사용하지 않은 검사·승인·협업자도 만들어 적지 않는다.

## 커밋 전 확인

- staged diff와 파일 목록이 제목·본문의 범위와 일치하는지 확인한다.
- 주요 변경을 누락하거나 작업기록 파일 경로만으로 본문을 대체하지 않는다.
- 필요한 검증을 수행하고, 미실행/실패/대기는 구분해 적는다.
- 키·개인정보·로컬 고유 데이터·민감한 경로를 메시지와 첨부 로그에 넣지 않는다.
- 여러 줄 메시지는 UTF-8 파일과 `git commit -F`를 사용해 실제 개행을 보존한다.
- 커밋과 원격 push/PR/main 병합 승인은 구분한다. 과업별 승인 범위를 따른다.

누적 작업기록은 상세 맥락과 실패/수정 루프를 보존하며, 커밋 본문은 해당 diff를 검토하는 사람이 변경을 이해할 수 있도록 요약한다.

## 2026-11-09 본문 형식 보완

제목 체계는 유지한다. 본문은 변경 내용을 짧은 불릿으로 먼저 제시하고, 필요한 경우 아래 문단에 배경·검증 한계·후속 맥락을 덧붙인다. 각 불릿은 실제 변경이나 수행한 검사 한 가지를 구체적으로 설명한다. 긴 절차와 상세 로그는 작업기록으로 연결한다. 검증 결과는 해당 커밋에서 확인한 사실만 적는다. 기존 커밋은 재작성하지 않는다.
