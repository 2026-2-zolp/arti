# 11/15 AI 도슨트 모의 Chrome 회귀 CI

- **실행** · `ARTI CI`의 PR 및 수동 실행에 `Docent Chrome` 작업 세 개를 연결했다. 장애 재시도(502·429·타임아웃), 자료 갱신·다음 작품 이동, 관람가이드·AI 힌트·쉬운 요약을 각각 실행한다. 작업마다 새 PostgreSQL과 합성 전시·관리자를 준비해 자료 수정이나 요청 제한이 서로 영향을 주지 않게 했다. [GitHub Actions 매트릭스](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations)
- **연결** · Playwright를 프론트 잠금 파일에 고정했고, Ubuntu 러너에 설치된 Chrome에서 프론트 프로덕션 빌드를 연다. 프리뷰와 실제 Django API는 루프백 주소에 바인딩한다. 테스트용 Django는 루프백 모의 제공자를 사용하며, 프리뷰 준비 확인에서 모의 응답 헤더를 검사한다. Chrome은 프리뷰 외 주소로 보내는 요청을 차단한다. [Ubuntu 러너 이미지의 브라우저](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md#browsers-and-drivers)
- **실패 진단** · 실패한 시나리오의 도슨트 요청을 줄 단위 JSON으로 출력한다. 필드는 `requestId`, HTTP 응답 코드 `status`, 근거 버전 `evidenceVersion`이다. 근거에는 확인 가능한 자료 버전·원문 버전·리비전만 포함한다. 도슨트 요청 전에 실패한 경우 세 필드는 `null`이다. 질문·답변·요청 본문·인증값·스택은 CI 출력에 포함하지 않으며 서버 출력과 브라우저 추적 파일도 수집하지 않는다.
- **로컬 재현** · [기존 브라우저 하네스](2026-11-15_AI도슨트브라우저복구.md#재현)의 환경에서 프론트 잠금 의존성을 설치하고 `node frontend/tests/docentRetry.browser.cjs`를 실행한다. 자료 갱신과 이동은 `ARTI_DOCENT_RACE_TESTS=1`, 가이드와 요약은 `ARTI_DOCENT_ENTRY_TESTS=1`을 서버와 실행 셸에 각각 적용한다. 합성 관리자는 [자료 변경 검수의 재현 절차](2026-11-15_AI도슨트응답대기중작품변경.md#재현)를 따른다.
- **자체 검수** · actionlint와 ShellCheck, 프론트 단위 테스트 43건 및 프로덕션 빌드가 통과했다. Windows Chrome에서 8개 시나리오를 확인했다. Ubuntu 24.04 컨테이너에서는 Playwright Chromium과 Node 22·Python 3.12를 사용해 워크플로의 설치·빌드·합성 DB 구성·실행 명령을 재생했고, 세 합성 DB에서 8개 시나리오가 통과했다. 브라우저 응답 직후와 시작 전 실패를 각각 유도해 지정한 세 필드만 반환되는 것도 확인했다. 로컬 커밋 범위이므로 GitHub 호스팅 러너 실행은 아직 확인 대상이다. 실제 모델 호출과 실기기는 계속 보류했다.
