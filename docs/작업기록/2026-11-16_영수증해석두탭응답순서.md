# 영수증 AI 해석 두 탭 응답 순서 검수

- **환경** · `7d3fb10`의 제품 트리를 기준으로 별도 PostgreSQL 17, Django, PC Chrome과 루프백 모의 제공자를 사용했다. 같은 합성 회원의 두 탭이 동일한 관람 ID와 요청 본문으로 해석했다. 첫 요청의 제공자 응답을 보류한 동안 두 번째 요청이 실제 Django를 거쳐 처리되도록 했다.
- **재현** · 수정 전 두 번째 해석이 먼저 표시되고 저장된 뒤, 먼저 요청한 해석이 늦게 도착하자 같은 영수증의 문안을 덮었다. 두 탭은 각각의 세션 저장소를 사용하므로 새로고침할 때도 기존 탭의 문안을 먼저 읽었다.
- **서버 수정** · `0007_visit_interpretation_versions`는 기존 해석 문안을 유지하고 요청 순서와 저장된 성공 순서의 DB 기본값을 0으로 둔다. 회원 영수증 행은 요청 순서 부여 동안만 잠근다. 제공자 응답 뒤에는 저장된 성공 순서보다 큰 번호만 반영한다. 이미 더 나중에 요청한 해석이 성공했다면 늦게 도착한 탭에도 저장된 해석을 반환한다. 더 나중 요청이 실패했다면 먼저 요청한 성공 결과를 저장할 수 있다.
- **화면 수정** · 회원 영수증이 같은 관람을 다시 저장할 때 응답의 해석을 현재 화면과 탭 저장소에 반영한다. 새로고침 뒤 탭에 남았던 이전 문안도 서버의 최신 해석으로 맞춘다. 비회원 해석은 현재 탭에서 보존한다.
- **통과 확인** · 먼저 요청한 해석이 늦게 200으로 도착해도 두 탭의 응답·새로고침·회원 조회는 최신 성공 해석이었다. 반대로 두 번째 요청을 502로 실패시키면 기존 문안이 유지되다가 첫 요청의 성공 결과로 바뀌었다. 영수증 ID와 관람 순서·반응이 같고 회원 기록은 한 건이었다. 기존 회원·비회원의 502 재시도와 계정 전환 경로도 통과했다. [Chrome 회귀](../../frontend/tests/receiptInterpretation.browser.cjs)
- **인접 검수** · Django 영수증·제공자 20건, 프론트 단위 44건과 타입 검사·빌드, Chrome 관람 15건·PNG 복구 6건·저장 응답 유실을 통과했다. 별도 PostgreSQL에서 이전 스키마의 영수증을 마이그레이션해 문안이 유지되고, 같은 DB에 이전 모델로 저장한 새 영수증에도 두 순서 기본값이 들어가는지 확인했다.

## 재현

새 합성 환경에서 [영수증 모의 제공자 기동 절차](2026-11-16_영수증해석502통합회귀.md#powershell-재현)를 실행한다. 현 작업에서는 다른 검수와 겹치지 않도록 PostgreSQL 5693, Django 5694, 프리뷰 5695를 사용했다. 포트를 바꿀 때는 그 절차의 `PGPORT`, `serve(포트)`, `VITE_API_PROXY`, 프리뷰 포트와 `ARTI_REVIEW_BASE`를 함께 맞춘다. 검사는 `X-Arti-Receipt-Mock: 1` 헤더를 확인하고 해당 루프백 밖의 브라우저 요청을 차단한다. 실제 모델과 실기기는 사용하지 않았다.
