# A-04 관리자 감정 분석 분리

2026-11-22 · 기준 `c5170c0`

서울의 기존 분석판은 FP16·2스레드·배치 6으로 체칠리아 49.36~51.06초, 탕자 44.93~45.74초, 왕비 24.03~24.28초를 기록했다. 모델 계산 시간만으로도 일부 작품이 내부 HTTP 한도 45초를 넘었다. 입력을 자르거나 배치를 축소하는 대신 감정 결과만 별도 작업으로 처리한다.

## 관리자 흐름

1. A-04의 분석 요청은 Luna 쉬운 요약과 관람가이드, CLIP 도판 태그 제안을 저장한다. 관리자가 세 제안을 확인하고 확정할 수 있다. 도판 분석을 끈 경우 태그는 기존 mDeBERTa 텍스트 방식으로 계산한다.
2. Django가 같은 저장 트랜잭션 안에서 감정 작업을 등록한다. 별도 워커가 가져가서 기존 이미지·텍스트 감정 산식으로 제안을 작성한다. 감정 작업이 대기하거나 실행 중이어도 화면에서 다른 제안을 다룰 수 있다.
3. 감정 결과가 오면 A-04는 현재 편집 버전과 맞는지 확인하고 감정만 적용한다. 작품 해설이나 요약 등 작성 중인 내용은 보존한다. 다른 편집으로 버전이 달라졌으면 최신 감정 제안을 불러올 수 있다.

같은 작품·승인 원문·도판 바이트·도판 사용 여부·모델 설정 버전에 대한 대기, 실행 중, 완료 작업은 재사용한다. 모델 서버도 끝난 점수만 최대 32건, 완료 후 5분 동안 보관하므로 응답이 끊긴 뒤 동일 입력을 다시 보냈을 때 활용할 수 있다. DB 작업에는 해시와 상태를 보관한다. 실패한 작업은 다시 요청할 수 있으며 완료 전 모델 혼잡은 제한된 횟수 안에서 지연 재시도한다.

실행 전과 저장 직전에 승인 상태, 원문 버전, 입력 해시, 감정 편집 상태를 검사한다. 원문이나 도판이 바뀌면 옛 결과를 저장하지 않는다. 워커가 중단되어 재처리하더라도 만료되거나 교체된 작업 토큰으로는 결과를 저장할 수 없다. 감정 결과는 다른 항목과 마찬가지로 관리자가 확정해야 한다.

## 스페인 작품 검수

팀 PC 검수 키트 `31eca16`의 원문과 도판을 해시 확인 후 격리 PostgreSQL 17에 불러왔다. 실제 로컬 CLIP·mDeBERTa FP16, CPU 2스레드·배치 6을 사용했다. Luna 텍스트 결과는 모의 응답이다. 체칠리아는 키트 원문 222자이며 이전 서울 실측의 승인본은 240자다.

| 작품 | 원문 | 태그·요약·가이드 저장 | 감정 워커 처리 |
| --- | ---: | ---: | ---: |
| 성녀 체칠리아 | 222자 | 1.83초 | 5.45초 |
| 돼지들 사이의 탕자 | 201자 | 0.64초 | 3.35초 |
| 빈소에 안치된 마리아 루이사 왕비 | 84자 | 0.77초 | 2.65초 |

세 작품에서 감정 등록 후 다른 제안을 먼저 확정했다. 같은 입력으로 등록을 반복해도 같은 작업 ID가 돌아왔고, 완료 후 추가 감정 작업이 생기지 않았다. 기존 통합 분석과 태그 8개·감정 6개의 점수가 일치했다. 체칠리아 원문과 탕자 도판을 각각 추론 응답 직전에 교체했을 때 두 옛 감정 결과 모두 저장되지 않았다. 표는 Windows 로컬 시간이며 운영 Luna 응답 시간은 포함하지 않는다.

- PostgreSQL Django 회귀 32건과 마이그레이션 변경 검사 통과. 감정 선저장 방지, 재시도, 기한이 지난 워커, 원문·도판 교체, 태그 출처, 관리자 요청 예산 포함.
- FastAPI 회귀 41건 통과. 감정 계산 중 CLIP 태그 조회, 배치와 스레드 설정, 점수 일치, 캐시 재사용·만료 포함.
- 프런트 빌드와 단위 80건 통과. 배포용 Compose와 감정 워커 프로필 구성 검사 통과.
- 기존 관리자 Chrome 회귀에 감정 검수를 추가했다. 감정 대기 중 요약 확정, 감정 도착 시 편집 중인 입력 유지, 새로고침 후 감정 제안 표시가 통과했다. 기존 분석 충돌, 도판 선택, 공개본 보호, 확정 철회 흐름도 통과했다.
- 별도 `analyze_artwork_emotions --watch` 프로세스가 등록된 작업을 가져가 저장했다. 46초 뒤 오는 모의 응답으로 전경의 45초와 분리된 워커 대기 한도도 확인했다.
- Django 전체 313건 중 312건을 첫 실행에서 통과했다. 음성 테스트 한 건의 하위 확인 두 개는 로컬 가상환경에 `websockets`가 없어서 실패했다. 잠금 파일의 버전 `17.4`를 격리 검수 경로에 추가하고 해당 테스트 클래스 두 건을 재실행해 통과했다.
- `0024`에서 만든 작품이 `0025` 적용 뒤 남았고, 교체 전 ORM으로도 새 작품을 저장할 수 있었다. 새 점수 출처 필드는 DB에 빈 문자열 기본값을 둔다.

## 반영 순서

1. 현재 모델 서비스의 고정 가중치·보정 설정을 유지하고, `/analyze-tags`와 `/analyze-emotion`을 지원하는 이미지로 교체 후보를 만든다. FastAPI의 `ARTI_NLI_DTYPE=float16`을 명시한다. 모델 프로세스는 하나를 사용하고 두 경로가 준비됐는지 확인한다.
2. API·워커를 새 릴리스로 올리기 전에 `0025_artwork_emotion_job`을 적용한다. API와 워커에 같은 `ARTI_MODEL_SERVICE_URL`과 `ARTI_ANALYSIS_REVISION`을 설정한다. 모델이나 보정값을 변경하면 분석 리비전도 바꾼다.
3. API 환경에 `ARTI_BACKGROUND_EMOTION=true`를 적용하고 Compose 프로필 `background-analysis`의 `emotion-worker`를 실행한다. 워커는 API와 동일한 Django 이미지·DB·미디어를 사용한다. 현재 배포 스크립트는 웹과 API만 교체하므로 워커를 켠 뒤에는 API 릴리스 또는 분석 설정 변경 시 워커도 함께 재생성한다. 모델의 두 경로와 워커를 준비하기 전 기본값은 `false`다.
4. 전경 분석 전체 60초, 모델 태그 요청 최대 45초를 유지한다. 감정 워커 요청만 최대 90초이며 작업 소유권은 120초다. 공개 반영 전 서울 환경에서 긴 원문과 실제 Luna가 섞인 요청으로 세 제안이 먼저 오는지, 감정이 90초 내 완료되는지 확인한다.

이 기록과 코드는 로컬 작업 범위다.
