# ARTI 개발 협업 규칙

> 팀원 초대 전에 마련한 기본 운영안입니다. **main을 통합본으로 유지하고 각자의 브랜치에서 작업한 뒤 PR로 합칩니다.** 필요하면 팀 회의 후 수정합니다.

## 1. 기록 위치
- 회의·결정·전체 일정·조사: [Notion](https://app.notion.com/p/26-2-ARTI-a3534713f16782789905811787871032)
- 기능·버그·개발 이력: GitHub Issues / Pull Requests
- 빠른 대화: 카카오톡·디스코드 (중요한 결정은 Notion 또는 관련 PR에도 기록)

## 2. 브랜치 운영

| 브랜치 | 역할 | 예시 |
| --- | --- | --- |
| `main` | 팀 전체 통합 기준. 직접 작업·직접 push 지양 | `main` |
| `dev/<GitHub아이디>` | 팀원별 작업 브랜치. 최초 한 번 만들고 지속 사용 | `dev/your-id` |
| `feat/<아이디>-<작업명>` | 한 사람이 여러 작업을 나눠 PR해야 할 때 선택적으로 생성 | `feat/your-id-artwork-list` |

**기본은 개인 브랜치 → PR → main**입니다. 브랜치 이름과 별개로 본문/설명은 한국어로 작성해도 됩니다.

### 개인 브랜치 최초 생성
```bash
git clone https://github.com/2026-2-zolp/arti.git
cd arti
git switch -c dev/<본인-GitHub아이디>
git push -u origin dev/<본인-GitHub아이디>
```
위 `<본인-GitHub아이디>`는 실제 계정명으로 바꿉니다.

### 평소 작업
```bash
git switch dev/<본인-GitHub아이디>
git fetch origin
git merge origin/main
# 코드 작성·테스트 후
git add <수정한-파일>
git commit -m "feat: 작품 취향 선택 화면 구현"
git push
```

1. GitHub Issue로 작업 목적과 완료 기준을 정합니다.
2. 작업하기 전에 **항상 최신 main을 반영**합니다.
3. 자신의 개인 브랜치에서 개발하고 직접 실행·검토합니다. AI 생성 코드도 예외가 아닙니다.
4. GitHub에서 **base: main ← compare: dev/본인아이디**로 PR을 만듭니다.
5. PR 설명(한국어)에 변경 내용, 관련 Issue, 테스트, 화면 캡처(해당 시)를 적습니다.
6. 다른 팀원 1명 이상의 검토를 권장하고, 통합 후 다시 최신 main을 반영합니다.

**주의 — 장기 개인 브랜치와 병합 방식:** `dev/<아이디>`처럼 같은 브랜치를 여러 번 재사용할 경우, 처음에는 `Create a merge commit` 방식을 권장합니다. `Squash and merge`로 합친 뒤 이전 커밋이 개인 브랜치에 그대로 남으면 다음 PR에 과거 변경이 중복 표시될 수 있습니다. Squash 방식이 필요하면 **병합 후 개인 브랜치를 최신 main으로 재정렬**하거나 새 기능 브랜치를 만드는 방향을 합의하세요. 작업 중인 커밋을 확인하지 않고 `reset --hard`나 강제 푸시를 사용하지 마세요.

> 서버에서 `main` 직접 push 차단이 적용되었는지는 별도 관리자 설정으로 확인해야 합니다. 규칙 문서를 작성했다고 자동 보호되는 것은 아닙니다.

## 3. 커밋 제목·PR 작성 언어

**커밋은 영어 유형 + 한국어 작업 설명**으로 통일합니다.

```text
feat: 작품 취향 선택 화면 구현
fix: 전시 지도 마커 위치 오류 수정
docs: 프로젝트 협업 규칙 정리
refactor: 추천 API 응답 처리 구조 개선
chore: 프론트엔드 개발 환경 설정
test: 작품 추천 로직 테스트 추가
```

- 유형: `feat` 새 기능, `fix` 오류 수정, `docs` 문서, `refactor` 동작 변경 없는 구조 개선, `chore` 설정·유지보수, `test` 테스트
- 유형 다음에 `: `를 입력하고, 제목은 **어떤 작업을 했는지 간단히 한국어로** 적습니다.
- 필요한 경우 커밋 본문에 이유·영향·주의사항을 **한국어로** 기록합니다.
- PR 제목도 같은 형태를 권장하며, PR 설명/코드 리뷰도 한국어로 작성합니다.
- 기술적인 고유 명칭, 변수·API 경로, 라이브러리 이름은 원문 표기를 유지합니다.
- 이전 영문 커밋의 기록은 굳이 재작성하지 않습니다.

## 4. 최소 안전 규칙
- `.env`, 비밀 키·토큰·개인정보, DB 덤프를 커밋하지 않습니다.
- 실제 전시 출품 여부·작품 이미지 사용권·해설 출처·위치 데이터가 **실제인지 모의인지**를 명확히 기록합니다.
- 검증되지 않은 작품 설명을 공식 사실처럼 보여주지 않습니다.
- 프론트·백엔드 공통 ID, API 요청·응답 방식이 바뀌면 상대 파트와 먼저 조율합니다.
- 영향 범위가 큰 의존성/구조 변경은 먼저 Issue에서 논의합니다.
- 리뷰에서는 정상 동작, 예외 처리, 변경 범위, 테스트 여부를 확인합니다.
