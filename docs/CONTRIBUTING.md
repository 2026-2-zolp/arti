# 협업 및 코드 관리 가이드 (초기 운영안)

> 팀원 초대 전에 준비한 **권장 운영안**입니다. 팀 합의로 수정할 수 있습니다.

## 어디에 남기나요?
- 회의·결정·조사·일정: [Notion](https://app.notion.com/p/26-2-ARTI-a3534713f16782789905811787871032)
- 개발 작업·버그·코드 리뷰: GitHub Issue / Pull Request
- 긴급한 소통: 카카오톡·디스코드 → 합의한 결론은 Notion/PR에 기록

## 기본 작업 흐름
1. Issue 작성(목표·담당·완료 기준). Notion 일정/WBS는 기존대로 유지합니다.
2. `main` 최신화 후 별도 브랜치 생성(`feat/`, `fix/`, `docs/`, `chore/`).
3. 변경 크기는 검토 가능한 수준으로 나눕니다. AI 생성 코드도 본인이 읽고 실행·검증합니다.
4. PR에서 관련 Issue와 변경점·검증·스크린샷(화면 작업)을 남깁니다.
5. 가능하면 다른 팀원 1명이 확인한 후 `main`에 Squash merge합니다.

## 꼭 지켜주세요
- `main`에 직접 push하지 않는 것을 **팀 규칙**으로 권장합니다. (서버 차단 설정 여부는 별도 확인)
- `.env`, API 키, 개인 데이터, 저작권 확인 전 원본 이미지, DB 덤프는 커밋하지 않습니다.
- 데이터가 실제 전시 소속인지, 이미지 권리와 출처가 무엇인지 표시합니다. 불확실하면 `unverified`.
- API 계약·ID 체계가 달라질 때는 관련 작업자에게 먼저 공유합니다.
- 모델 기반 작품 설명은 **공식 해설과 생성된 해석을 분리**하고 미검증 사실을 추가하지 않습니다.
- 큰 의존성 도입이나 프로젝트 구조 변경은 먼저 Issue에서 논의합니다.

## 권장 커밋 형식
`feat: add exhibition entry page`
`fix: correct artwork position mapping`
`docs: clarify artwork data provenance`

## 리뷰에서 확인할 점
- 기존 흐름 파손 여부·예외 처리·비회원 경험
- 작품 ID·전시 ID·추천 ID의 일관성
- 출처·권리·가상 정보 표시
- 실제로 실행·테스트했는지 (하지 못했다면 이유 명시)
