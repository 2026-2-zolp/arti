# 🤝 ARTI 개발 협업 규칙

[← 메인 안내로](../README.md) · [팀원 시작 가이드](TEAM_ONBOARDING.md)

## 한 줄로 이해하기

**`main`은 팀의 공통 완성본, `dev/이름`은 개인 작업 공간, PR은 합치기 전에 서로 확인하는 과정**입니다.

```text
main에서 최신 코드 받기
       ↓
내 dev/이름 브랜치에서 개발
       ↓
테스트 → 커밋 → push
       ↓
PR 생성 (dev/이름 → main)
       ↓
팀원 리뷰·확인 → main 병합
       ↓
다음 작업 전 내 브랜치에 최신 main 반영
```

## 1. 브랜치 관리
- `main`: 공통 통합 브랜치. **직접 push하지 않고 PR로만 변경**하는 팀 규칙
- `dev/임준억`, `dev/김광권`, `dev/지성현`, `dev/김동섭`: 개인 작업 브랜치
- 복잡한 작업을 동시에 여러 개 진행한다면 `feat/작업명` 같은 단기 브랜치를 추가해도 됩니다.

팀원의 이름은 Notion의 **팀원 정보**를 기준으로 확인했습니다. 이는 코드 소유권이 아니라 각자의 독립 개발 공간을 의미합니다. 브랜치 이름을 GitHub 아이디로 변경하기로 합의하면 추후 조정할 수 있습니다.

## 2. 개인 브랜치에서 작업하는 법
최초 1회: [팀원 시작 가이드](TEAM_ONBOARDING.md)의 방법으로 **이미 생성된 원격 브랜치를 연결**합니다.

매 작업 시작 시:
```bash
git switch dev/본인이름
git fetch origin
git merge origin/main
```

변경 후:
```bash
git status
git add -A
git commit -m "feat: 작품 추천 결과 화면 구현"
git push
```

**`git add -A` 하기 전에는 반드시 포함 파일을 확인**합니다. 개인 데이터, API 키·비밀번호, 불필요한 대용량 파일은 올리지 않습니다.

## 3. 커밋·PR 작성 규칙

커밋 제목은 **영어 유형 + 한국어 설명**으로 작성하고, 필요한 커밋 본문과 PR 설명도 한국어를 기본으로 합니다.

| 유형 | 예시 |
| --- | --- |
| `feat` | `feat: 전시 QR 진입 화면 구현` |
| `fix` | `fix: 지도 마커 표시 오류 수정` |
| `docs` | `docs: 프론트엔드 실행 방법 추가` |
| `refactor` | `refactor: 추천 로직 함수 분리` |
| `chore` | `chore: 환경변수 예시 정리` |
| `test` | `test: 작품 조회 API 테스트 추가` |

PR에는 무엇을 바꿨는지, 어떻게 테스트했는지, 다른 사람이 확인할 부분을 적습니다. 구현하지 못한 부분도 명시합니다.

## 4. 병합 원칙과 주의사항
- PR의 **base는 `main`**, compare는 내 `dev/이름` 브랜치
- 다른 팀원 **1명 이상 리뷰** 권장
- 개발 초기의 **장기 개인 브랜치 재사용**에는 `Create a merge commit` 방식 권장
- `Squash and merge`로 기존 변경을 합친 뒤 개인 브랜치를 계속 사용하면 다음 PR에 이전 커밋이 다시 표시될 수 있으므로, 이를 정리할 줄 알 때 사용하거나 기능별 새 브랜치를 만듭니다.
- 병합 후 개인 브랜치를 다시 최신 `main`과 동기화합니다.
- 충돌·리베이스·강제 푸시가 필요하면 먼저 팀에 공유합니다.

> **문서상의 규칙**과 GitHub의 기술적인 강제 설정은 별개입니다. 현재 `main` 브랜치 보호는 별도 설정이 필요합니다.

## 5. 개발 시 지킬 사항
- 작품 데이터는 **공식 출처**, 실제 전시 출품 여부, 이미지 사용권, 검수 상태를 구분합니다.
- AI가 만든 해설과 공식 해설을 혼동하지 않습니다.
- 프론트·백엔드 API/타입/ID 변경은 담당자와 먼저 합의합니다.
- 규모가 큰 구조·의존성 변경은 Issue에서 공유합니다.
- 다른 사람이 실행·리뷰할 수 있도록 폴더별 README도 함께 갱신합니다.
