정리: 2026-11-08 KST / 담당: 임준억, AI 개발·검증 보조 / 대상 브랜치: `dev/임준억`.

이 문서는 흩어져 있던 조사·회의·인수·설계·실행 계획을 연결하는 입구다. 실제 개발 변경은 [작업기록](작업기록/README.md), 상세 절차·판정은 [실행계획](execution-plan/2026-11-07/README.md)에서 확인한다. 과거 조사 아카이브는 당시 판단을 보존하며 최신 결정으로 소급 수정하지 않는다.

## 1. 왜 통합을 다시 준비했는가

프론트는 동섭님·성현님 작업, 백엔드와 모델은 광권님 구현이 병행됐다. 각 구현이 독립적으로 진행되면서 태그 개수·취향 선택·가이드 구성·검수 상태·API 필드에 차이가 생겼다. 제안/설계의 Django·PostgreSQL과 실제 Express·SQLite도 달랐다. 단순 파일 합치기만으로 사용자 흐름·데이터 신뢰성·실제 AI가 함께 성립하지 않는 상황이었다.

준억은 최초 GitHub 개설 이후 별도 기능 구현이 없었다고 명확히 했으며, 통합본을 받아 계약을 정리하고 리팩토링하는 역할로 진행했다. 과거 카톡의 “API 연동/하네스 진행” 문구를 실제 구현 완료 증거로 쓰지 않았다. 이후 실제 작업은 W01부터 단계별 로그와 코드로 기록했다.

준억 원격 기준은 동섭 통합본의 조상이다. 이력 삭제·강제 reset·기존 타인 커밋 재작성 없이 병합했다. W01~W04는 먼저 수행·검증한 작업을 **2026-11-08에 회고 정리해 커밋**하는 것이다. 커밋 날짜/작성자를 과거로 꾸미지 않고, 실제 수행 기록과 커밋 정리 시점을 구별한다.

동섭님 인수 원문은 [작업기록 폴더의 원문](작업기록/1107_김동섭_(리팩토링전)프론트_백_통합.md)에 내용 그대로 옮겼다. 다른 팀원의 과거 작업을 준억의 새 구현으로 표시하지 않는다.

## 3. 서비스에서 지켜야 할 흐름

초보 관람객이 전시 QR/주소로 들어와 취향·시간을 고르고, 추천과 지도에 따라 작품을 보며, 해설·관찰 질문·AI 도슨트를 통해 감상을 이어가고 영수증을 받는다. 로그인은 기록 저장을 위한 선택 기능이다.

- U10은 **작품 해설 / 관람가이드 두 탭**을 유지한다. 공식 원문이 기본이고 검수된 쉬운 요약은 선택해서 본다.
- 가이드는 검수된 짧은 도입·관찰 질문, 필요할 때 펼치는 힌트를 중심으로 한다. 일반 감상 팁은 작품별 가이드와 구분한다.
- 도슨트로 이동했을 때 **대화를 처음부터 다시 시작하지 않는다.** 현재 작품·보고 있던 해설/질문·실제 사용자 관찰·최근 대화를 이어받고 돌아오면 보던 탭/위치를 복원한다. 입력하지 않은 감상은 지어내지 않는다.
- source 확인과 AI 초안 검수는 다르다. 공식 근거→AI 초안→관리자 검수→공개 순서를 지킨다.
- 취향 8태그와 감정 6태그는 서로 다르다. 취향은 추천, 감정은 설명/영수증 보조다. 이해 수준을 취향에서 추정하지 않는다.

새 다중전시 플랫폼·실내 실시간 측위·모델 학습·벡터DB·복잡한 작업큐를 통합의 기본 요구로 추가하지 않는다. 교수 관점의 입력→처리→출력 추적과 작은 비교 평가를 현재 핵심 흐름에 연결한다.

## 4. 채택한 방향과 미결 사항

| 영역 | 채택한 개발 방향 | 아직 확인할 부분 |
| --- | --- | --- |
| 프론트 | 기존 React·화면/URL 유지 | U05/06 최종 UX 합의, profile/맥락/저장 연결 |
| 서비스 API | Django/DRF로 전환, `/api`·기존 DTO 의미 재사용 | W05의 전체 쓰기·회원·기록·도슨트 기능 |
| DB | PostgreSQL·명시 migration, 원본 SQLite 비파괴 보존 | 팀원 고유 데이터/검수값/이미지/도면 export와 실제 이전 |
| 모델 | CLIP/mDeBERTa FastAPI 경계 유지, 생성형은 외부 API 방향 | 실제 provider/근거·품질·지연·자원 측정 |
| Kanana | 실험 자산으로 구분. 현재 코드의 관리자 요약/가이드 생성 역할도 확인 | 기본 외부 API 경로로 대체·실제 실패/유보 검증 |
| 운영 | Docker 개발 기반, GitHub Actions CI/CD 계획 | AWS 예산/권한/리전/저장소/배포 결정. RDS/S3/EC2는 후보 |

Django 전환은 이번 개발의 채택 결정이며 과거 팀 전체가 이미 확정했다고 주장하지 않는다. 새 API를 위해 Express에 같은 기능을 먼저 완성하는 이중 작업은 하지 않는다. AWS·키·Actions 대기가 무관한 로컬 작업 전체를 막지 않도록 선행 조건을 분리했다.

전체 37개 이슈의 담당·상태·검증 연결은 실행계획의 `04-issues.md`와 `execution.json`이 기준이다. 아래는 맥락 요약이다.

| 묶음 | 변경 전 문제/오해 | 적용할 기준과 주의 |

| 기록/인증 | 같은 관람 중복 저장·이유 누락·AI 대기와 저장 결합 | visit 중복 방지·DB 저장 여부 명시·해석 분리·원본 보존 |

| 대화 | 화면 기록만 있고 모델 history 없음, 작품ID만으로 캐시 | actor/visit/전시/작품/콘텐츠 버전 격리, 승인 자료를 서버에서 재구성 |

| 운영 | 알려진 기본 계정·수동 schema·실행 환경 차이 | 자동 시드/계정 차단, 명시 bootstrap·migration·영속/복구·CI/CD를 각각 검증 |

캡처40장과 WikiArt79장은 Git에 있었다. 초기 “이미지 없음” 판단은 부분 조사 사본의 누락이었으므로 정정했다. 유영국 작품을 위한 전시/작품 구조는 이미 존재하며 새 DB를 따로 만들 필요는 없다. 실제 출품 여부·동명작품·연도/치수·출처·권한·좌표·태그 준비는 따로 검수한다.

## 7. 앞으로의 누적 규칙

변경 전에 관련 W/F/AC를 확인하고 작은 구현→해당 검사→인접 회귀→별도 검토→증거→상태 갱신 순으로 진행한다. 같은 실패가 두 번이면 전제를 재검토한다. 필수 기준을 낮추거나 가상 검토를 실제 사람/모델/클라우드 검증으로 대체하지 않는다.

W별 검증 통과 시 코드와 작업기록을 함께 커밋한다. 기록은 과업별로 나누되 날짜가 바뀌거나 변경 방향이 달라지면 새 문서에서 이전 기록을 연결한다. 원격 푸시·PR·배포는 로컬 커밋과 별개다.
