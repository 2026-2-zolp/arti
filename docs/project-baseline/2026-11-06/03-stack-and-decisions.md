# 스택 전환과 결정 기록

## 근거와 결론

자료실의 제안발표 PDF 9·13쪽 및 백엔드 설계서 1.2는 **React·TypeScript·Vite / Python·Django·DRF / PostgreSQL / Docker**를 명시한다. 10/18 중간발표 제작 기록 18장은 Express·SQLite 초기 프로토타입과 Django·PostgreSQL 설계의 차이를 그대로 남겨 두고 공통 스택·연동 규격은 후속 정리 대상으로 설명한다.

따라서 “현재 API가 있으니 언어 변경 근거가 없다”는 이전 판단은 수정한다. **계획의 목표 스택은 원설계로 복귀**다. 다만 자료실 PDF가 실제 최종 제출 파일과 동일한지, 최종 제출 설계서가 무엇인지는 별도 확인되지 않았다. 후속 문서가 Express 영구 채택을 확정한 근거도 발견되지 않았다.

Python 모델 서비스를 FastAPI로 분리해 두는 것은 Django API와 공존할 수 있다. 이를 전부 Django 내부로 다시 작성할 이유는 아직 없다. 프론트도 현재 React 기반을 유지한다.

## “먼저 맞추고 전환”의 경계

현 Express에서 할 일은 공통 응답·상태·검수 계약, 프론트의 데이터 손실 방지, 최소 관람 흐름, 계약 테스트다. Express에서 OAuth·정교한 새 DB·전체 RAG·배포까지 완성하고 다시 이식하지 않는다. 실제 AI의 작은 연결 증명은 Python 경계에서 재사용 가능하게 만든다.

전환 시작 조건은 **G1: 통제된 자료로 핵심 흐름과 오류를 확인**하는 것. 이것이 통과하면 T05로 이동한다. G1에서 문제가 오래 걸려도 Express 기능 확장을 계속하지 않고 남은 문제를 계약 테스트로 옮겨 Django에서 해결한다. 최초 통합 작업 한 회차가 끝날 때 목표 전환 착수 범위를 다시 점검한다.

## 전환 범위

| 층 | 유지/재사용 | 바꾸거나 검증할 부분 |
| --- | --- | --- |
| 프론트 | React 화면·모바일 흐름·좌표0~100 | 공통 타입·오류·추천 무효화·저장·인증 상태 |
| API | 기존 프론트가 사용하는 JSON 계약을 우선 유지 | Django/DRF 구현. 과거 /api/v1 초안과 현재 /api를 동시에 뒤섞지 않음 |
| 추천 | 8태그 점수·검증된 결정적 기준선 | 선택 원본/빈도 계약. 임베딩 고도화는 비교 근거 후 |
| 모델 | Python 모델·임계값·평가 스크립트 | 호출 인터페이스·timeout·모드/근거·승인 데이터 범위 |
| DB | 전시/작품/계정/기록의 의미와 외부 식별자 | PostgreSQL 모델·마이그레이션·관계·제약·검수 이력 |
| 인증 | 로그인 선택이라는 제품 흐름 | 목표 환경 인증·OAuth 선택. 현 Bearer를 무조건 JWT라고 부르지 않음 |
| 실행 | 분리된 웹/API/모델 구조 | Docker 재시작·DB/미디어 영속성·헬스체크 |

현 ID는 ex-mvp/aw-01 등의 문자열이다. 옛 ERD의 int/UUID로 무조건 바꾸면 라우트·localStorage·기록 참조가 깨진다. 내부 PK와 외부 ID 매핑 또는 문자열 외부 ID 보존을 우선 검토한다. SQLite JSON 문자열을 Postgres JSON/관계로 옮길 때 숫자·null·누락 상태를 테스트한다.

계정 비밀번호는 현재 scrypt 해시다. Django 기본 해시와 자동 호환된다고 가정하지 않는다. 실제 운영 DB·계정 유무를 먼저 확인하고, 테스트 계정 재생성/명시적 재인증/검증된 호환 처리 중 하나를 선택한다. 원본 DB 백업 없이 파괴적 변환을 하지 않는다. 현재 전달된 자료에는 운영 DB가 없다.

언어/DB의 목표와 추천·동선 알고리즘의 세부안은 다르게 취급한다. 후자는 후속 회의에서 방향이 바뀌었으므로 설계 변경 기록으로 해결할 수 있다. 원설계 전체를 무조건 구현하거나, 원설계를 통째로 무시하는 두 선택을 강요하지 않는다.
