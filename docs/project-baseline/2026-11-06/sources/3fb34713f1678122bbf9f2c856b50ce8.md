## 3. 주요 논의 내용

### 3-1. 개발 대상: <b>유영국 작가전부터 시작</b>

- 기존 후보는 <b>화풍/사조 중심 신인상주의 전시</b>와 <b>유영국 개인전</b> 두 가지로 재확인(03:05, 08:54).
- 첫 구현 대상은 <b>유영국 전시</b>로 의견이 모였음(09:39\~11:08). 한국어로 된 공식 자료를 쓰면 해외 전시보다 번역 부담이 덜하다는 의견이 나왔고, 다른 팀원도 유영국 작품 포함에 동의.
- <b>신인상주의 전시를 취소한 것이 아니라</b> 첫 구현 후 추가할 수 있는 확장 후보로 남긴 취지.
- <b>구체적인 대상 전시 확정(회의 후 사용자 확인): 서울시립미술관 〈유영국: 산은 내 안에 있다〉.</b> 회의 당시에는 작가명만 호칭했지만 실제 개발 대상은 이 전시가 맞음을 확인.

### 3-2. 데이터 규모: <b>많이 모으기와 완성도 높여 테스트하기를 분리</b>

- 동선과 추천을 고려하면 실제 전시 데이터가 필요하다는 점에 공감(12:01\~13:42).
- 전체 작품 데이터를 하루 이내에 취합할 수 있을 만큼 수집이 쉽다면 <b>미리 DB에 충분한 분량을 적재</b>해도 좋다는 의견.
- 다만 이번 주 기능 테스트와 설명·위치 정보의 정밀 검증은 <b>약 5\~6작품</b>부터 진행하는 방식이 언급됨. 30\~40작품 사전 수집도 조건부 예시로만 제시됨.
- <b>최종 목표 작품 수·데이터 담당·수집 완료 기준은 회의에서 확정되지 않음.</b> 중간의 “90” 등 작품 총수 발언도 전사 불명확으로 확정 수치에 포함하지 않음.

### 3-3. 개발 범위: <b>26쪽 UI 전부가 아니라 세로 흐름 하나부터</b>

- 기존 26쪽 화면설계는 <b>최종 구현 목표</b>이며 중간발표까지 전 화면을 만들어야 하는 것은 아님(13:42\~17:11).
- 사용자 입력부터 결과 확인까지 처음부터 끝까지 한 번 동작시키고 이후 고도화하는 <b>최소 파이프라인 개발</b>을 지향.
- <b>당시 권장 구현 흐름</b>(준비안 참고): 전시 QR/URL → 취향 입력 → 작품 추천 → 2D 작품 위치·순서 → 작품 감상. 다만 <b>이 각각이 이번 주 필수 완료로 최종 확정된 것은 아니며</b>, 파트별로 가능한 범위를 조정하기로 함.
- AI 기능이 어느 정도 구현됐다면 중간발표 PPT에서 보이도록 포함하는 쪽으로 의견을 모음. 단순 UI 완성보다 실제 연동을 구분해 보여줄 필요.

### 3-4. AI 코딩 사용과 협업 진도 차이

- 김동섭님은 <b>Codex 중심 바이브코딩</b>을 계획하고 있고, 광권님은 Cursor 및 Claude 등 AI 도구 활용 의사를 이야기함(17:27\~23:39).
- AI 활용 여부·도구의 차이를 제한하기보다 <b>결과 코드를 이해하고, 팀원과 공유하기 전에 검수하며, 본인 작업 범위 밖 코드를 의도치 않게 변경하지 않는 것</b>을 중요하게 봄.
- 생성 속도가 다른 팀원 사이에서 <b>어떻게 작업을 나누고 진도를 맞출지</b> 우려 제기. 독립 작업 뒤 연결·수정하는 접근도 의견으로 나왔지만, 구체적인 공통 개발 규칙과 분담표는 아직 없음.
- <b>기록상 합의된 원칙</b>은 코드 이해·수정 범위 주의·상호 공유이며, 특정 AI 코딩 툴 통일이나 전체 개발을 한 사람이 맡는 결정은 없음.

### 3-5. 프론트·백엔드 분리 및 화면 제작 방식

- <b>프론트:</b> 김동섭님·지성현님이 화면설계 자료를 기준으로 상의하며 개발. <b>React</b>를 우선 고려(38:46\~39:00).
- <b>백엔드·AI:</b> 임준억님·김광권님이 별도 협의해 범위·기능을 맞춘 뒤 프론트와 연동(29:51\~31:49).
- <b>초기 구현 패턴:</b> 프론트는 화면을 먼저 구현하면서 API 응답에 해당하는 곳을 임시 Mock 데이터로 채우고, 백엔드 API가 준비되면 실제 데이터로 교체·연동하는 방식이 설명됨(25:26\~26:05).
- 화면설계 이미지→Figma→React 등 변환, Google Stitch 활용, Figma 관련 AI 기능·MCP 등 도구가 논의됨. <b>Figma·Stitch는 검토/선택 사항</b>이지 사용 확정이나 특정 유료 기능의 작동을 보장하는 내용은 아님.
- <b>지성현님 채팅 확인:</b> 기존 화면 목업은 <b>원하는 구도와 조건을 정한 뒤 ChatGPT로 이미지를 생성</b>한 것. 과거 프로젝트에서도 프론트가 먼저 나온 경험이 있다고 함. 다만 이번에는 <b>이미지를 바로 코드로 구현할지, Figma로 옮겨 작업할지 아직 확신이 서지 않는다</b>고 명시했으며, 이는 구현 방식에 대한 고민이지 개발 불가나 화면설계 반대 의사가 아님.
- 진행자는 코드로 바로 구현하는 방식과 Figma/Stitch 사용 모두 가능하다고 설명하고, 동섭님과 상의한 뒤 결정하도록 함. <b>기존 화면설계 이미지는 출발점</b>, 실제 개발된 화면에 변경이 생기면 <b>최종 제출 전 설계서에 반영</b>할 수 있다는 의견.
- 초기 레퍼런스는 김동섭님이 간단히 찾아 공유하기로 요청을 수락함. 프론트 세부 화면별 업무 분배는 추후 두 사람이 별도 확정.

### 3-6. 지도·QR 관련 기존 범위 재확인

- 전시 입구 QR/URL을 기준으로 추천 흐름을 시작함(35:45\~37:24). <b>작품마다 QR을 찍어 그 지점에서 추천을 새로 시작하는 방식은 추가 기능</b>으로 미룸.
- <b>2D 지도에 미리 매핑된 작품 위치를 기준</b>으로 안내할 계획이며 GPS/실내 실시간 측위 기능을 구현하려는 것이 아니라는 점을 재확인.
- '현재 위치' 문구는 실제 기기 좌표 측정이 아니라 <b>입구/직전 감상 작품 등 진행 상태에서 지정되는 기준 위치</b>라는 준비안의 해석과 정합.
