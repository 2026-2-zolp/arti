- 10/27 이후 광권님 프로토타입은 기존의 <b>6개 감정 범주</b>와 구분되는 <b>8개 시각/주제 태그</b>를 추천 기준으로 정리했습니다. 단순히 지표가 6개에서 8개로 늘었다는 뜻이 아닙니다.
- 11/3 회의에서 광권님이 시연한 <b>8개 태그, 7회 토너먼트</b>와 성현님이 시연한 <b>10개 작품, 최대 5회의 독립 비교</b>를 놓고 논의했습니다.
- 후반부에는 1위 작품을 뽑는 승자 진출형 토너먼트보다, <b>각 비교에서 이긴 5점의 공통 태그</b>를 활용하는 성현님 방식으로 정리했습니다.
- 이 방향은 당시 프론트·추천 API에 모두 구현되었다는 의미가 아닙니다. 회의 당시 코드 버전이 나뉘어 있습니다.

🎨 A. 5회 작품 비교·태그 집계·프론트 버전 조율 (01:02\~01:10 / 01:36\~01:40)

<b>발단</b> · 광권님 시연은 풍경/인물 등의 8개 취향 태그를 대진으로 연결해 8강→4강→결승 총 7회 비교하는 방식이었습니다. 성현님 시연은 작품 10점을 2점씩 짝지어 5회 각각 선택하는 방식이었습니다.

<b>왜 문제가 됐나</b> · 정식 토너먼트에서는 '인물'과 '풍경'을 모두 선호해도 같은 대진에서 한쪽이 탈락할 수 있습니다. 성현님 방식은 5번의 독립 선택으로 여러 관심사를 함께 포착하려는 취지였습니다.

<b>\[합의된 방향\]</b> · 작품 5점을 선택한 후 각 작품이 가진 복수 태그를 살피고, 겹치는 태그를 중심으로 취향을 도출하며, 사용자가 결과를 확인·수정한 뒤 관람 시간과 추천 단계로 진행합니다.

<b>\[미결\]</b> · 작품당 태그 수 제한(회의의 3\~4개는 예시), 출현 횟수의 가중치, 동률 처리, 태그가 안 나올 때, 수정한 태그의 우선도, 추천 요청 데이터의 구체적인 형태. '선택 작품 5점의 순위까지 확정'으로 기록하지 않습니다.

<b>\[코드 확인\]</b> · 성현님 ZIP에서는 <code>api.listArtworks(exhibitionId)</code>의 앞부분 최대 10점을 짝지으므로 실제 작품 수가 10점 미만이면 비교도 5회보다 적습니다. 선택 ID를 최종 저장하지 않아 취향 도출까지 이어지지 않습니다. 첫 10점이 전시별 후보가 아니라 독립적인 대표 작품이어야 하는지는 디자인 검토가 필요합니다.

🧮 B. 추천 점수·8개 태그·6개 감정 지표 (01:23\~01:30)

<b>8개 추천 취향 태그</b> · 풍경·인물·추상·빛·강렬·차가운·따뜻한·부드러운. 사용자 선호와 작품의 시각적/주제적 특징을 맞추는 용도입니다.

<b>6개 감정 지표</b> · 평온·기쁨·슬픔·긴장·경외·그리움. 광권님 브랜치에서는 작품 분위기 설명이나 영수증 등에 보조적으로 활용하며, <b>추천 점수 계산 자체에는 직접 사용하지 않습니다.</b>

<b>\[영상 확인\]</b> · 관리자 화면에서 취향 태그 수치와 감정 지표가 따로 표시됐습니다. 점수 계산과 토너먼트 순위의 관계를 놓고 질의가 있었습니다.

<b>\[기존 브랜치 코드\]</b> · <code>backend/src/lib/recommend.ts</code>는 사용자가 고른 태그마다 해당 작품의 태그 강도(0\~1)를 평가한 뒤 <b>평균</b>합니다. 입력 태그의 순서와 중복은 무시하며, 검수 완료·위치 등록 작품을 후보로 삼습니다.

<b>\[미결\]</b> · 새로운 5회 작품 선택에서 태그 출현 횟수(예: 따뜻함 3회, 풍경 2회)를 새 추천 점수에 어떻게 반영할지. 기존 평균식을 새 설계의 최종 합의식으로 단정할 수 없습니다.

<b>설명 예시(권고, 미합의)</b> · '선택한 작품 5개에서 따뜻함이 3번 나왔다'는 취향 신호와, '추천 후보 A의 따뜻함 강도가 0.8이다'는 작품 신호는 다른 데이터입니다. 두 신호를 잇는 규칙을 프론트·백엔드가 먼저 합의해야 합니다.

<b>논의</b> · 초보 관람객이 작품의 어디를 관찰하면 좋을지 이끄는 질문, 공식 원문 해설, 쉬운 설명, 취향 맞춤 답변을 중복 없이 나누려 했습니다. 광권님은 초보자 가이드와 관찰 질문을 결합하는 방안을 제시했습니다.

<b>\[회의 말미 방향\]</b> · 임준억이 '관람 가이드' 명칭을 제안했고 광권님이 받아들이는 흐름이 확인됐습니다. <b>원문 '작품 해설'과 '관람 가이드' 중심으로 정리</b>하되, AI Q&A·요약의 최종 탭 개수나 위치는 구현 검증이 더 필요합니다.

<b>\[미결\]</b> · 관리자 초안 생성과 Q&A의 호출 경로, 실제 API 사용 증빙, 출처 및 검수 상태, 응답 실패 시 안내, 로컬 모델의 계속 사용 여부.

<b>실제 전시 특성 문제</b> · 유영국 작품군에서는 인물 태그가 거의 나오지 않을 수 있으므로, 사용자의 1순위가 '인물'이라도 그 전시에 추천 가능한 작품이 없을 수 있다고 광권님이 지적했습니다. 성현님은 후순위 취향을 활용할 수 있게 생각하고 있었다고 설명했습니다.

<b>대체 추천</b> · 1순위가 없으면 다른 취향으로 추천하고 이유를 알리는 방향. 광권님 기존 브랜치에는 전시별 태그 커버리지와 대체 후보를 다루는 구현이 있습니다. 다만 실제 유영국 등록 데이터에 대한 정상 동작까지 입증한 것은 아닙니다.

<b>QR 진입</b> · 사용자 입장에서는 입구 QR을 스캔하면 <b>이미 해당 전시가 선택된 주소</b>로 들어오는 기존 방향을 유지합니다. 여러 전시를 고르는 화면은 시연/관리상 편의를 위한 것이며 사용자 필수 첫 화면으로 확정하지 않았습니다.

<b>\[미결\]</b> · 실제 전시 식별 URL, 태그가 아예 없는 경우의 메시지, QR과 관리자 등록/검수 사이 엔드투엔드 테스트.
