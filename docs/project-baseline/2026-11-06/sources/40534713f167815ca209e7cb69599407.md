## 1. 취향 조사 방식 · 합의 수준의 정확한 해석

### 김동섭 · 선행연구 공유 (녹음 10:18\~19:41)

- 영화 추천에서 5·10·20개 평가를 비교한 연구를 제시했다. 10개 조건의 체감 추천 적합도가 높았지만, <b>미술관에서 작품 10개가 최적이라는 직접 증거는 아니다.</b>
- 두 이미지 중 하나를 선택하는 2AFC 방식은 점수 평가보다 미세한 미적 선호 차이 탐지에 유리했던 연구 결과를 소개했다. 다만 이것이 <b>동일한 횟수의 질문에서 작품 추천 정확도가 더 높다</b>는 뜻은 아니다.
- 미술 작품의 평가 점수와 태그를 함께 활용하는 연구를 제시했다. 자유 입력 태그와 ARTI의 고정 태그 선택 방식은 구별해야 한다.
- 자세한 방법·한계: <mention url="https://app.notion.com/p/40534713f16780e789dbe719c1d88a62" />.

### 지성현 · 사용자 선택 부담 연구 (녹음 43:20\~45:16)

- 선택지 6개 대 24개 비교, 긴 설문과 응답 부담 등에 관한 연구를 공유했다.
- 선택지가 많다고 좋은 것은 아니므로 사용자가 완주할 수 있는 간단한 구성의 필요성을 설명했다.
- 이 연구들이 ARTI의 최적 작품 수나 추천 정확도를 입증하는 것은 아니다. 자료: <mention url="https://app.notion.com/p/40534713f16780869879da7d4b71fe73" />.

### 6\~10개 및 토너먼트식 (녹음 45:16\~47:21)

- 기존 태그 직접 선택 시연과 별개로, <b>대표 작품 이미지를 보여주고 두 점씩 비교하여 사용자의 선호 작품과 공통 태그를 추출</b>하는 방식을 다시 검토했다.
- 약 <b>6\~10개 작품</b>을 활용하는 구성과 밸런스 게임·토너먼트형 UX에 의견을 모았고, 이를 <b>프론트 수정 대상으로 진행</b>하기로 했다. 회의 직후 10/26 14:49 김광권이 카톡 작업 메모에 <b>“06\~10 토너먼트식”</b>을 명시했다.
- <b>미확정:</b> 작품이 정확히 6점인지 8점인지 10점인지, 총 비교 횟수가 몇 번인지, 승자가 다음 라운드로 진출하는 정식 토너먼트인지, 태그/점수를 어떻게 추출하는지는 확정되지 않았다.
- 특히 10개 작품을 두 개씩 비교하면 5회 선택을 할 수 있다는 <b>예시</b>가 나왔을 뿐, 모든 사용자가 5라운드를 수행한다는 결정은 아니었다.

<b>합의 수준을 반영한 기록:</b> “초기 취향 조사는 약 6\~10개의 대표 작품 이미지를 활용하고, 두 작품 중 더 선호하는 대상을 고르는 비교형·토너먼트형 UX로 수정하는 방향에 의견을 모았다. 공통 특징·태그를 분석해 추천에 활용하는 방안을 검토하며, 세부 작품 수·비교 횟수·라운드 규칙·분석 방법은 추후 구체화한다.”

## 2. 김광권 프로토타입 시연과 AI 쟁점 (녹음 02:41\~08:04, 19:41\~43:20, 47:19\~1:00:07)

- <b>관리자 화면:</b> 전시·작품 관리, 평면도 이미지 업로드, 작품 마커 이동, 작품별 감성 분석 실행 UI를 시연했다. 위치 변경의 저장·갱신, 여러 전시 관리와 선택 연동은 추가 확인 필요.
- <b>사용자 추천 시연:</b> 당시 구현에서는 미리 정해둔 <b>6개 태그</b> 중 사용자가 태그를 선택하고, 등록 작품의 감성 점수와 비교해 추천하는 방식이라고 설명했다. <b>사용자가 작품 이미지를 비교하여 취향을 파악하는 기존 기획과는 다른 시연 구현</b>이다.
- <b>태그·점수 의문:</b> 관리자 지정 태그, AI가 추정한 감성값, 사용자 취향 태그가 어떻게 대응되고 어떤 점수로 결합되는지 시연자도 정확한 내부 규칙을 재확인해야 한다고 설명했다. AI 도움으로 개발한 부분이 있어 코드와 모델 적용 방식의 상세 이해가 후속 과제가 됐다.
- <b>감성 AI 검증:</b> 화면에 나타난 이미지와 등록 작품 정보가 일치하는지 불명확한 사례가 있었고, 정확도 개선 수치도 평가 조건을 확인하지 못했다. <b>실제 해당 작품을 넣어 재현하고 검증하기 전에는 성능 개선 결과로 기록하지 않는다.</b>
- <b>챗봇:</b> Claude API를 연결했다고 소개한 화면이 있었지만, 질의 시 응답 형태를 보고 하드코딩·대체 응답 가능성을 지적했다. <b>실제 외부 API 호출 성공 여부는 미확인</b>이다. 이후 LLM API 교체·연결 확인, 대화 맥락 유지, 작품에 맞는 표현, 가드레일·인젝션 대응 등을 검토하기로 했다.
- <b>서비스 실행 구조:</b> 프론트·백엔드·Python AI 서버로 구분된 프로토타입을 설명했다. React, TypeScript 등 사용 언어 조율과 GitHub 코드 공유·실행 재현이 필요하다.
- <b>평면도:</b> 이미지 확대 시 화질 저하, 작품 위치 번호와 실제 추천 순서 매핑 보완을 논의했다. 평면도를 더 깔끔하게 단순화하거나 AI로 구조를 재표현하는 안은 <b>아이디어</b>이지 구현 확정 사항이 아니다.
- <b>음성:</b> TTS(텍스트를 음성으로 읽기), STT(사용자 음성 인식) 확장 가능성을 논의했다. 시연 UI 존재만으로 정상 구현·작동을 인증하지 않는다.

## 3. 다른 주요 논의

### 전시별 진입·지도·QR (녹음 38:34\~42:37)

- 사용자에게는 <b>전시 입구 QR/URL을 통해 이미 선택된 해당 전시</b>의 정보를 제공한다는 방향을 재확인했다. 처음부터 여러 전시를 고르는 화면이 필수인 것은 아니다.
- 여러 전시가 있을 경우 <b>관리자에서 각 전시를 관리하고 해당 전시의 데이터·화면이 사용자에게 올바르게 제공되는지</b> 점검한다. 이는 10/26 15:13 임준억이 카톡에서 “타전시 관리” 의미로 재설명한 내용과 일치한다.
- 실제 서비스 배포 URL을 QR로 만드는 방안을 제안했으며, 관리자에 QR 생성기를 반드시 구현한다고 확정하지 않았다.

### 감상 개인화 (녹음 48:19\~50:37)

- 설명 난이도를 입구에서 직접 선택시키는 방식과 <b>대화 중 사용자 반응을 분석하여 자연스럽게 조절하는 방식</b>을 비교했다.
- 후자에 긍정적인 의견이 많았으나 기술 난이도 우려도 제기됐다. 따라서 <b>방향성은 대화 중 반응 파악, 구체적 구현과 대안은 미결</b>로 기록한다.

### 좋아요·싫어요 및 관람 피드백 (녹음 1:01:36\~1:07:59)

- 작품 좋아요·싫어요를 단순 기록할지, 회원의 선호·비선호 태그를 누적하여 다음 추천에 쓸지 논의했다.
- 비선호 이유를 간단한 항목으로 수집하거나, 아트 영수증 직전 관람·동선 피드백을 모으는 안도 나왔다.
- 비선호 작품을 완전히 배제해서는 안 될 수 있다는 반론이 있었다. <b>구현 확정이 아닌 검토 아이디어</b>로 남긴다.

### OAuth 및 현장 방문 (녹음 1:08:00\~1:13:24)

- 임준억이 카카오 등 OAuth 로그인 도입 난이도·적용성을 조사해 공유하기로 했다. <b>OAuth 도입 확정은 아님</b>. 비회원 핵심 흐름은 기존 기획대로 유지한다.

## 4. 오늘의 핵심 논의 · 질문과 판단 방향

### A. 작품 감성 분석 AI — '실제로 무엇이 달라지나?'

<b>이미 코드에서 확인한 흐름:</b> 관리자 작품 이미지·해설 → <b>CLIP(이미지) / mDeBERTa(해설)</b> → 6종 감성 점수 → 관리자 검수·확정 → 사용자 취향 카드의 감성 점수와 비교 → 작품 추천. Claude API는 해설·Q&A 등 <b>글 생성</b>용으로 별도 사용.<br /><b>회의에서 확인할 것</b>

- 광권님이 <b>작품 1점의 등록 → 분석 → 관리자 확인 → 추천 반영</b>을 실제 실행 또는 로그로 보여줄 수 있는가? 안 되면 정확히 어디까지 동작하는가?
- 현재 <b>이미지 60% / 해설 40%</b>, \*\*감성 유사도 70% / 태그 일치 30%\*\*는 임의 가중치다. 임시로 유지할지, 비교 실험 후 조정할지?
- 6종 감성값은 <b>그림이 주는 분위기에 대한 모델 점수</b>이며, 사용자의 실제 감정이나 미술관의 공식 해석은 아니다. 관리자 검수를 어떻게 표시·반영할까?
- 추천 결과가 <b>감성값을 추가했을 때 기존 태그 추천보다 나아졌는지</b> 어떤 기준으로 확인할까? 실제 전시 작품·다수 평가자 라벨 확보가 가능한가?<br /><b>권장 판단:</b> 새 모델을 더 붙이기 전에 현재 감성 AI의 <b>실행 재현 + 추천 연결 + 작은 평가</b>를 1차 완료 조건으로 검토.<br /><b>회의 결론:</b> 채택 / 조건부 채택 / 보류: \_\_\_ · 시연 증빙: \_\_\_ · 평가 담당: \_\_\_

### B. 취향 조사 · 초보자/일반 사용자 구분은 별개의 문제

<b>먼저 분리해서 보자</b>

1. <b>무엇을 좋아하는가?</b> — 초기에 대표 그림·취향 카드를 고르고 작품 추천에 활용.
2. <b>어느 정도 설명이 필요한가?</b> — 감상 중 쉬운 설명·심화 설명의 깊이를 조절.<br /><b>질문</b>

- 초기 취향 이미지/카드는 <b>고정 세트</b>로 할까? 화면에 몇 개를 보여주고 몇 개를 선택하게 할까? 동섭님이 조사한 근거·개발 부담을 함께 비교.
- 사용자 취향 카드 → 6종 감성값 변환표는 <b>개발자 가정</b>이다. 이 표를 어떻게 검토·보정할까? '사용자 이미지 자체를 AI로 분석한다'고 잘못 설명하지 않기.
- 사용자 이해 수준은 <b>(a) 진입 전 선택</b>, <b>(b) 감상 대화 중 반응을 보고 조절</b>, <b>(c) 간단한 사전 선택 + 언제든 변경/대화 중 보정</b> 중 어느 방식이 필요할까?
- 초기 설문이 길어지는 비용과 실제 설명 차별화 효과를 비교. 초보자를 영구 라벨로 분류하지 않고, 사용자가 언제든 쉬운/깊은 설명을 요청하도록 할까?<br /><b>권장 방향:</b> <b>취향 추천 입력</b>과 <b>감상 설명 난이도</b>를 혼동하지 않는다. 사용자 수준을 사전에 묻는다면 그 정보를 어느 기능에서 실제 사용하는지부터 합의.<br /><b>회의 결론:</b> 취향 이미지 수/선택 수: \_\_\_ · 설명 수준 방식: \_\_\_ · 근거/실험: \_\_\_

### C. AI 감상·Guided Looking은 교수님 피드백에 어떻게 답할까?

<b>교수님이 강조한 것:</b> AI가 어떤 데이터로 어떤 판단을 하고 답을 만드는지, 사용자 수준에 따라 어떻게 설명이 달라지는지, 이를 어떻게 객관적으로 검증할지 보여주기. <b>직접 파인튜닝이나 멀티에이전트가 필수라는 뜻은 아님.</b><br /><b>최소 시연 후보(제안)</b>

1. 같은 작품 1점과 동일한 질문을 기준으로 '일반 고정형 해설'과 '수준·관심·직전 대화 반영' 응답을 비교한다.
2. 작품 ID로 <b>검수된 설명·출처</b>를 불러오고, Guided Looking 1질문 → 사용자 답변 → 다음 질문/설명 변화까지 재현한다.
3. 근거가 없는 연도·작가 의도 질문에는 모른다고 알리고, 공식 설명과 AI의 해석을 구별한다.<br /><b>평가 예시(작게 시작):</b> 사실 근거 일치 / 난이도 적절성 / 이전 대화 반영 여부 / 근거 부족시 안내. 비교 조건과 평가자·문항 수는 팀에서 정한다.<br /><b>주의:</b> <code>AI가 설명을 바꿉니다</code>라는 소개만으로 완료가 아니다. <b>구체적인 입력, 분기 근거, 실제 출력 2종, 평가 결과</b>가 남아야 한다.<br /><b>회의 결론:</b> 최소 AI 감상 시연: \_\_\_ · 기준 응답: \_\_\_ · 확인 지표: \_\_\_

### D. 현재 개발 결과를 어떻게 한 서비스로 연결할까?

<b>10/12 합의의 핵심:</b> 기능 전체를 한 번에 완성하기보다는 <b>실제 사용자가 들어와 취향을 고르고 추천을 확인하는 흐름부터 연결</b>하자는 것. 10/23에는 동섭·성현이 <b>전시 ID를 중심으로 첫 화면→관람 시작→취향·감상 화면</b>을 이어 가는 방향에 공감했지만, 상세 구현 계약을 완전히 확정한 것은 아니다.
