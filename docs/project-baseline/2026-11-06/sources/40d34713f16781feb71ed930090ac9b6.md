## 0. 회의에서 1분 안에 전달할 내용

지난 10/26 회의 이후 제 쪽에서는 <b>OAuth 로그인 도입, AI 감상 기능 구조, 그리고 기존 개발물의 연결 방식</b>을 조사했습니다. 두 기능 모두 제 담당으로 새롭게 실제 연동을 완료한 상태는 아니어서, 오늘은 구현 결과 대신 <b>채택할 방향과 이번 주 개발 범위</b>를 공유하려고 합니다.

로그인은 국내 모바일 전시 관람 환경을 고려해 <b>카카오 로그인 하나</b>를 먼저 적용해보겠습니다. 다만 개발자 앱 설정이나 인증·모바일 복귀 문제가 예상보다 오래 걸린다면 <b>Google 로그인을 대안</b>으로 검토하겠습니다. 로그인 자체가 비회원 관람 구현을 지연시키지 않게 하겠습니다.

마이페이지는 기존 관람기록을 활용해 <b>아트 영수증과 좋아요 작품</b>을 누적해서 보는 정도로 구성하고, 비회원도 이번 영수증을 이미지로 저장하거나 공유할 수 있도록 제안합니다. 여러 관람 기록을 계속 보관하고 싶은 사용자가 로그인하도록 하는 방식입니다.

AI는 작품 해설·초보자 해설·Guided Looking·자유 질문의 역할을 분리하고, <b>작품별 검수 자료와 대화 맥락을 활용해 실제 답변을 생성</b>하는 경량 하네스를 우선 구현해보겠습니다. <b>수요일까지 최소 기능을 시도해 실제 성공·막힌 부분을 업데이트</b>하고, 이후 기존 프론트와 연결해 11/9 컨설팅 전 검증 가능한 결과를 준비하겠습니다.

연동의 기준은 새로 전부 만들기보다 <b>광권님 최신 개발물의 진행 상태와 재현 가능성을 확인</b>하고, 충분히 구현되어 있다면 그 백엔드의 기능·데이터 모델을 최대한 재사용하자는 의견입니다.

## 2. OAuth · 조사 결과와 개발 계획

### 2-1. 카카오 우선, Google은 일정 리스크 대안

- <b>카카오를 우선하는 이유:</b> ARTI는 국내 미술관 방문자가 전시 입구 QR에서 모바일 웹으로 진입하는 서비스이므로 카카오 계정 접근성이 유리할 것으로 판단한다. 카카오의 웹 REST API는 인가 코드 요청→코드 콜백→서버 토큰 교환→사용자 식별을 지원한다.
- <b>Google 대안:</b> 공식 Google Identity Services 로그인 버튼·ID 토큰 서버 검증 방식이 잘 문서화되어 있어 웹 개발의 대체 후보가 될 수 있다. 그러나 Google용 콘솔 설정·클라이언트 ID·UI 수정도 별도 필요하며, 모바일 인앱 브라우저나 웹뷰의 제약을 테스트해야 한다. <b>카카오 실패 시 Google이 자동으로 더 빨리 끝난다고 단정하지 않는다.</b>
- <b>판단 시점:</b> 11/4 수요일 1차 점검에서 카카오 앱 활성화·등록된 리다이렉트 URI·실제 인증 콜백 확보 여부를 확인한다. 인증 문제가 해소되지 않고 일정 위험이 커진다면 Google로 전환하는 데 걸리는 추가 작업을 비교해 결론을 공유한다.
- <b>지연 방지:</b> 어느 제공자든 당장 연결되지 않으면 비회원 관람은 유지하고, 인증 도입은 따로 진행한다.

| 항목 | 우선 개발안 |
| --- | --- |
| 로그인 | 카카오 로그인 1개 / 최초 로그인 시 자동 계정 생성 |
| 사용자 키 | 이메일이 아닌 <code>provider + providerUserId</code>로 식별 |
| 개인정보 | 닉네임 등 최소 정보, 이메일 필수 수집하지 않기 |
| 상태 관리 | 인증 결과를 서버에서 확인한 뒤 <b>ARTI 자체 세션</b> 발급 |
| 보안 | 인가 코드·토큰은 서버 처리, <code>state</code> 검증·세션 쿠키 보안 설정 |
| 관리자 | 관리자 인증과 별개 / 소셜 로그인 대상 아님 |
| 비회원 | 전시 입장과 감상 가능, 로그인 강요 없음 |

<b>출처:</b> [카카오 로그인 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api) · [카카오 로그인 개요](https://developers.kakao.com/docs/ko/kakaologin/common) · [Google 로그인 버튼](https://developers.google.com/identity/gsi/web/guides/display-button) · [Google ID 토큰 검증](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

### 2-2. 프론트 협업 요청

- 로그인(U-03)은 카카오 로그인 버튼, 인증 취소·실패 안내, 로그인 후 기존 화면 복귀 중심으로 수정.
- 별도 회원가입(U-04)과 비밀번호 찾기·변경(U-14\~15)은 일반 사용자 기본 흐름에서 제외.
- 비회원 관람(U-02)은 유지. 로그인된 계정으로 계속할지, 게스트 관람할지 상태가 섞이지 않도록 분리.
- 제공자 교체에 대비해 프론트가 의존하는 최종 사용자·세션 응답 구조는 공통으로 유지.
- 백엔드 OAuth 개발·사용자 계정 연결은 임준억이 담당하는 안으로 제안.

## 3. 마이페이지와 비회원 영수증

<b>핵심 가치:</b> 계정 관리보다 <b>관람 경험의 누적</b>. 이미 존재하는 U-12 아트 영수증·U-13 관람기록을 우선 재사용한다.

| 기능 | 비회원 | 로그인 사용자 |
| --- | --- | --- |
| 추천·감상·영수증 확인 | 가능 | 가능 |
| 이번 영수증 이미지 저장 | 가능하도록 제안 | 가능하도록 제안 |
| 모바일 공유 / 링크 복사 | 여력에 따라 | 여력에 따라 |
| 과거 영수증 목록 | 영구 보관 미지원 | 계정별 누적 조회 |
| 좋아요 작품 | 이번 관람 안에서 확인 | 지난 관람까지 모아보기 |
| 다음 관람의 취향 불러오기 | 미지원 | 추후 확장 |

<b>마이페이지 최소 구성:</b> 프로필 표시 이름, 관람기록·아트 영수증 목록, 좋아요한 작품, 로그아웃. 비밀번호 변경·프로필 상세 편집·SNS 계정 연동은 제외.

<b>사용자 흐름 제안:</b> 비회원도 관람 종료 후 '이미지로 저장' 가능 → '내 기록에 계속 보관하기'를 선택하면 카카오 로그인 → 인증 성공 후 해당 관람 기록을 계정에 저장. 로그인 이전의 임시 관람 데이터가 리다이렉트 후에도 유지되는지 검증하고, 성공 확인 전 임시 기록을 지우지 않는다.

<b>범위 조절:</b> 이번 주에는 로그인한 사용자의 영수증 저장·재조회가 먼저다. 비회원 PNG 저장·SNS 공유와 로그인 후 게스트 기록 이관은 핵심 흐름 안정화 후 구현 우선순위를 결정한다. 이미지 저장 시 미술 작품 원본의 재배포 권리·캔버스 CORS 이슈를 확인한다.

## 4. AI · 조사한 방향과 최소 구현

### 4-1. 기능의 역할 정리 (광권님 논의 연결)

<mention url="https://app.notion.com/p/40634713f16780a5a3bbd2a620ea6731" />에서는 Guided Looking·초보자 설명·AI 맞춤 설명·AI 질문의 역할 중복과 API 미연결 문제가 제기되었다. 이를 모두 AI 생성 버튼으로 두기보다 다음처럼 구분해 제안한다.

| 사용자 기능 | 역할 / 우선 구현 |
| --- | --- |
| 작품 해설 | 관리자가 검수한 원문 정보 표시 |
| 초보자용 해설 | 쉬운 말로 재구성한 정보, 가능하면 사전 생성 후 검수 |
| Guided Looking | 색·형태·구도 등 <b>작품을 직접 관찰하게 만드는 질문</b> |
| AI에게 질문하기 | 실제 LLM 기반 자유 질문·답변 |
| 반응형 맞춤 설명 | 최근 반응을 보고 '어려워요/더 알고 싶어요' 등에 대응하는 후속 단계 |

<b>의견:</b> Guided Looking을 초보자 해설로 완전히 대체하면 초기 ARTI의 관람 참여형 차별점이 약해질 수 있다. 따라서 서로 다른 역할로 유지하되 <b>화면 복잡도를 줄이는 UI 통합</b>은 검토한다. 유영국의 추상 작품에 인물 감상 질문을 일괄 적용하지 않고, 해당 작품에 실제 확인되는 색·선·형태 질문을 사용한다.

### 4-2. 최소 AI 하네스 구조

1. <b>입력:</b> 전시 ID · 작품 ID · 사용자 질문 · 최근 대화 · 요청한 설명 방식
2. <b>근거 조회:</b> 작품 ID로 등록된 설명·관찰 요소·출처·관리자 검수 상태 확인
3. <b>응답 방식:</b> 쉬운 설명 / 관찰 질문 / 자유 질문 등 명시적인 모드 결정
4. <b>LLM 호출:</b> 승인된 작품 맥락과 최근 대화를 전달해 한국어 답변 생성
5. <b>응답 점검:</b> 빈 답변·작품 불일치·근거 부족·외부 호출 실패·출력 형식 확인
6. <b>반환:</b> 답변 + 사용된 자료 ID/출처 + 실제 LLM 여부/대체 응답 여부 + 오류 상태
7. <b>로그·평가:</b> 작품/요청 ID, 모델·지연·오류 및 고정 질문 테스트 결과 기록. 불필요한 개인정보는 저장하지 않음

<b>설계 원칙:</b> 새 에이전트 프레임워크나 대규모 벡터 DB 없이 <b>단일 LLM + 작품 ID 기반 검수 데이터 조회 + 코드로 제어하는 워크플로</b>부터 만든다. 근거를 프롬프트에 넣는 것만으로 정확성을 보장하지 않으므로 별도의 테스트가 필요하다.

### 4-3. 1차 개발 범위

- <b>수요일 목표:</b> 작품 1점의 검수 자료로 실제 LLM 답변 1회 호출하고, 실패/대체 응답을 구분해 공유하는 것을 우선 시도.
- <b>추가 가능하면:</b> 직전 2\~4개 메시지를 보내 후속 질문에 맥락이 반영되는지 실험.
- <b>11/9 전 목표:</b> 기본 Q&A / 쉬운 설명 / 근거 부족 답변 등의 사례를 5개 안팎의 고정 질문으로 검증하고 프론트 UI와 통합.
- <b>현재 아님:</b> AI 성능 향상 수치·API 호출 성공·Guided Looking 자동 개인화 구현 완료 등을 주장하지 않는다.

## 5. 프론트·백엔드 개발 연동 기준

<b>기본 제안:</b> 이미 구현이 많이 진행된 코드를 우선 살린다. 광권님 <b>최신 백엔드 실제 실행본</b>이 가장 완성도가 높고 재현 가능하다면, 해당 코드의 전시·작품·관람기록 데이터 모델과 API 동작을 우선 기준으로 삼고 프론트와 최소 계약을 확정한다.

<b>그러나 구현량만으로 결정하지 않는다:</b> 과거 개인 공개 저장소가 곧 현재 최신 팀 실행본은 아니다. 광권님 코드와 성현님 공유 프론트의 버전, 취향 태그 목록, 추천 알고리즘, 데이터 모델이 달라졌는지 확인하고, <b>실행 가능성·실제 유영국 데이터 적용·기능 일치·수정 비용</b>을 비교하여 채택한다. 서로 다른 부분은 API 어댑터로 조정할 수 있다.

### 통합을 위해 먼저 확인할 5가지

| 항목 | 합의할 최소 계약 |
| --- | --- |
| 전시·작품 | <code>exhibitionId</code>·<code>artworkId</code>가 전 화면과 DB에서 동일 |
| 취향 비교 | 2개 작품 중 선택 기록 → 8개 특징 태그 등 공통 정의로 변환 |
| 추천·지도 | 추천 작품 ID, 순서, 이유, 위치 좌표와 좌표 단위 |
| AI 질문 | 작품 ID·질문·최근 대화 입력 / 답변·출처·호출 상태·오류 출력 |
| 로그인·기록 | ARTI 사용자 ID, 로그인 세션, 방문 ID, 영수증 저장·조회 |

<b>프론트 코드 정적 검토에서 확인한 우선 문제:</b> U-05의 비교형 취향 선택이 선택 작품 ID나 태그를 남기지 않고 다음 화면으로 이동한다. U-08은 취향 태그가 비면 추천 요청을 하지 않는다. 따라서 <b>취향 선택→태그 산출→추천 API</b>의 연결을 먼저 확인·수정해야 한다. 지도 작품 ID·추천 순서, 비회원/회원 기록 분리도 통합 테스트 대상이다.

<b>현재 자료:</b> 10/31 공유된 성현님 <code>frontend.zip</code> 정적 검토(실행 검증과 구분) · <mention url="https://app.notion.com/p/40534713f167815ca209e7cb69599407" /> · [공용 ARTI GitHub](https://github.com/2026-2-zolp/arti) · [광권님 개인 초기 프로토타입](https://github.com/kgg0711/dataprocessing). 현재 공유본이 어느 브랜치·커밋과 대응하는지 팀 확인 필요.
