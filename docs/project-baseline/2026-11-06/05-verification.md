## 루프

1. 변경 전에 관련 F-ID와 기대 동작·비교 입력을 기록한다.
2. 한 계약 또는 한 실패를 작은 변경으로 해결한다.
3. 영향받는 단위/계약 검사 → 관련 화면 → 관람 연결 흐름을 검사한다.
4. 결과에는 커밋/환경/입력/기대/실제/로그를 남긴다. 실패가 남으면 원인을 수정하거나 범위를 줄이고 다시 검사한다.
5. 모델·DB·인증 같은 경계 변경 뒤에는 전체 핵심 흐름을 다시 검사한다.
6. 게이트 통과 후 계획/설계 변경표를 갱신한다. 새 근거 없이 같은 검사를 반복하거나 범위를 넓히지 않는다.

실제 AI 평가는 먼저 소수 작품과 질문으로 시작한다. factual 질문은 자료의 사실·출처 일치, 관찰 유도는 작품을 보게 하는 질문인지, 근거 밖 질문은 유보 여부, 후속 질문은 문맥 유지, 운영은 지연·실패율을 확인한다. 같은 질문셋의 전후 비교와 사람이 찾은 실패 사례를 함께 남긴다. 답변 길이나 응답 성공률 하나로 품질을 판단하지 않는다.

새 작업 결과의 기록 양식: 날짜 / 작업 T-ID / 문제 F-ID / 기준 커밋 / 환경 / 입력 / 기대 / 실제 / 증거 경로 / 판정(통과·실패·미실행) / 다음 조치.

## 아카이브 자체 검증

[검증 스크립트](verify_archive.py)는 문서 링크 대상, 고유 task ID, 작업 의존성 순환, 문제 ID의 작업계획 연결, 출처 스냅샷 존재를 검사한다. 문장 내용의 진실성이나 서비스 품질을 자동 보증하지는 않는다. 원문과의 대조는 위 증거 자료로 수행한다.
